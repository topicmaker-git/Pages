### 運用ルール(設計20 で追加)

- **API ドキュメントが書いていない契約(送信形式・認証ヘッダ・HTTP
  ステータス)は、指示書の起草前にゲートキーパー調査で埋める**。学習状態
  API の POST は form-urlencoded・`X-XSRF-TOKEN` 必須・失敗時 HTTP 403
  だったが、API ドキュメントには一切書かれていなかった(§2.4)。「API 正」は
  ドキュメントに書かれた範囲についての規則であり、書かれていない契約は
  実装が正。正準実装を逐語複写方式にする指示書では、この種の欠落が
  そのまま実装の穴になる
- **正準実装で規則を言語の標準関数に委ねる前に、標準関数の挙動と規則の差を
  検査する**。ハッシュ算出規則の直列化は一見 `JSON.stringify` で足りるが、
  制御文字の短縮エスケープ(`\b` 等)で規則(`\u00xx` 固定)とずれる。
  独自エスケープにした(§2.4)。テストベクターが通ることは規則全体の
  一致を保証しない(ベクターが踏まない分岐がある)
- **添え書きも器と意味論の分離の対象**。添え書きに書けるのは依頼者にしか
  書けないこと(スコープの要求・確認手順)だけで、特定アプリの意味論
  (何をどの保存単位に記録するか)を列挙しない。設計20 で STATUS の
  添え書き3文目に AB会話アプリの保存対象を書き、高橋さん指摘で汎用化
  (§2.4)。「依頼者固有」と「アプリ固有」を混同した
- **現物例は仮置きでも受け入れテストに出し、実測で差し替える**。API
  ドキュメントのサンプル値で §8 を仮置き(仮置きであることを本文冒頭に
  明記)して受け入れテストに回し、合格後にテストで得た実応答へ差し替えた。
  実応答を待ってから起草すると、実応答を得るための改造が指示書を必要とする
  循環になる

**XSRF・送信形式の実装調査(ゲートキーパー、2026-08-26)** — API
ドキュメントに記載なし

- POST(set / delete)は `validate_xsrf → is_user` の順で検証。失敗時は
  **HTTP 403** + `{ "xsrf": { "ERROR": 1 } }`。GET(get / list)は検証なし
- 検証が認証より前にあるため、トークン不整合なら未ログインでも
  `user.AUTH` ではなく `xsrf.ERROR` が返る
- **Referer がない要求は検証を省く**(ネイティブ経路の救済)。ブラウザの
  同一オリジン fetch は Referer を送るため学習アプリでは常に検証対象
- トークンは cookie `XSRF-TOKEN` の値を**無加工**で `X-XSRF-TOKEN` ヘッダに
  載せる(サーバー側テストヘルパ・account.js と一致。団体コンソールの
  `choi-eigo-org.js` は `decodeURIComponent` を挟んでおり流儀が割れている
  が、正準は無加工の側)
- パラメータは `$c->req->param` で読む。**JSON ボディを解する経路はなく
  form-urlencoded**。`payload` は JSON 文字列を1個のフォーム値として送る

**STATUS.md の契約の要点**

- §2.1 応答規約: HTTP 200 原則の**唯一の例外として XSRF 失敗の 403**を
  明記。正準実装は 200 / 403 のみを JSON 応答として扱い、それ以外は通信
  失敗(例外)
- §2.2 送信形式: `X-XSRF-TOKEN` を常に付け、Referer 省略時の素通りに
  依存しない
- §3 正準実装 `EnhackStatus`(`EnhackLogin` の同居が前提): 正規化8手順 /
  **独自エスケープ**による直列化(`JSON.stringify` は制御文字を短縮形で
  出し規則とずれる)/ Web Crypto による SHA-256 / `request`(GET は
  クエリ、POST は form + XSRF)/ `post`(XSRF エラー時にトークンを取り直して
  **1回だけ再試行**)/ `encodePayload`(10,000 バイト超は例外)/
  `listAll`(`next_cursor` null まで一巡、0件ページを終端としない、
  `cursor: INVALID` で最初から取り直し、2回失敗で例外)
- §4 読み出し: LOGIN `check()` true の後、ユニットごとに `listAll`。一巡
  完了まで未登録を確定しない(C-3)。返ったレコードは**アプリが算出した
  ハッシュ集合と照合**し、一致しないもの(旧ハッシュ)は結び付けない。
  スコープが `NOT_FOUND` / `FORBIDDEN` なら「学習状態を持てない教材」として
  状態なしで動作し書き込みもしない。プリファレンスは `get` で別途。
  セッション中の再読なし
- §5 書き込み: 学習の区切りごとに都度。**1件の書き込みは最新状態の全量**
  (サーバーはマージしない — 要求仕様にない表現だが後着優先から必然。AI が
  差分ペイロードにする誤りを塞ぐ)。失敗してもメモリ上の状態は壊さない。
  delete の `NOT_FOUND` は整理では成功扱い。`LIMIT` は設計誤り
- §6 エラー3分類: `xsrf.ERROR`(再試行後)は `EnhackLogin.check()` で
  切り分け — false なら AUTH と同じ扱い、true なら書き込み失敗
- §1.2 追記(実測由来): 識別子は大文字 UUID 表記、大文字小文字を変えずに
  そのまま送る・比較する / §2.4: レコード内のキー順は不定、キー名で読む
