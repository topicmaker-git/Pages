## 0. 運用ルール(必ず踏襲)

- **確認なしに編集を始めない**。修正方針を提示して合意を得てから手を動かす。解釈が割れる箇所は選択肢を提示する。
- **判断を変えるときは再確認**(黙って方針を変えない)。
- **単一情報源原則**。同じ内容を複数箇所に書かず、相互参照する。誤りを直すときは、同じ記述が複数ファイル/箇所に散っていないか必ず grep で確認して一括で揃える。
- **検討の経緯や自分の判断の独白を仕様文書に残さない**。読者に必要な結論だけを書く(「本仕様では再定義しない」「§1〜§8 は入力で本章は出力」等の自己言及メモは不可)。
- **API 正**。仕様(画面・フロー)と API が食い違う場合、原則 API を正とする。ただし API ドキュメント自体に内部矛盾がある場合は、本体の構成と概念的な筋から「書き損じ」を特定し、確認のうえ正しい側に寄せる(下記の url_issued の例)。
- **佐藤さん管轄の API ドキュメントは編集しない**。`org_invitation.md` / `course_invitation.md` は読み取り専用の参照。修正が要る場合は「佐藤さんへ伝える事項」として記録するに留める。
- **番号は付け替えず末尾に追記**。節番号(WF §8〜§11 等)を振り直すと他ドキュメント/申し送りの参照が壊れるため、新規は末尾追記で対応する。
- **コースメンバー = 共同編集者ロール**であり、閲覧範囲の決定要素ではない(閲覧は 公開設定 + 所属団体 + 外部公開ロック で決まる)。具体権限(編集・削除・表示順の連帯責任、マイの再定義)は §2.9 / 画面一覧「権限モデル」節。
- **属性 vs 規則(制約)の区別**。Unit.公開/コース.公開 = 属性(DB値)、外部公開ロック = 規則(動的評価、DB書き換えなし)。

## 2. 確定した設計判断

### 2.1 メディアパック仕様 §9(出力形式 = デッキ body)
- 配信は「デッキオブジェクトの `body` 属性」の出力形式を定義。
- **`body` は JSON文字列を保持する String 属性**(ORM対象外・非正規化。スキーマ変更/拡張が多くRDBに正規化しづらいため文字列で持つ)。`body` のJSON = `{ type, cards }`。
- **`title` / `analysis` / `image`(デッキ画像)はデッキオブジェクトのプロパティ(body 外、`body` と同階層)**。
- `cards[].talks[]` = `{ person, en, ja1(直訳/語順訳), ja2(和訳), audio }`。`cards[]` = `{ title, image, talks }`。
- メディア(audio / image)は **ファイル名のみ**で保持。パスは §5.3 キー規約 `{ユーザーID}/{ユニットID}/{ファイル名}` から導出。
- `analysis` は既存「ちょい英語」の解析オブジェクトをそのまま保持。**デッキ単位のブロブで talks と非1対1**(解析器が1発話を複数文に分割しうる)。内部構造は既存システム側の定義に従う。
- 配信は**自動生成の全件完了後のみ**(未完了時はアクセス不可)。空値表現は不要。
- §8 のインバウンド会話例にスケルトンを揃えてある。

### 2.2 招待まわり(団体・コース共通の骨子)
- **会員一覧/メンバー一覧には承諾済みの会員/メンバーのみ**を表示。発行済み招待は別画面に分離:
  - 団体: **A-M4 発行済み招待一覧**(A-M1 から[招待の一覧]で遷移、GET `/org/invitation/list`)
  - コース: **A-CM3 発行済みコース招待一覧**(A-CM1 メンバータブから[招待の一覧]、GET `/course/invitation/list`)
- **承諾はログイン必須、辞退はログイン不要(token のみ)。非対称**。承諾はアカウント所属状態を変えるため認証必須、辞退はレコードに declined を立てるだけで token が本人確認を兼ねる。アカウント未取得者(団体 UC-51)も辞退できる。
  - 団体 API は当初 decline がログイン必須だったが、**ユーザーが API をログイン不要に修正済み**。
  - コース API は元から decline がログイン不要(制限なし)。
- **削除操作は無い**(両 API に delete endpoint が無い)。`cancel` は sent(/url_issued)→ expired の状態変更のみ、レコードは残る。
- **送信済(sent)の再送信は無い**。`resend` の対象は expired / declined のみ。
- **accepted も一覧に履歴表示**(操作なし。会員/メンバーとして A-M1/A-CM1 に存在)。
- **団体招待の二重 pending 禁止**(issue #366 / 2026-06-19 確定): 同一メール(解決可時)×同一団体に `sent` が既にあれば新規発行を弾く(重複みなしは `sent` のみ。expired/declined は新規発行可)。「届かない/再送」は新オペレーションを作らず、cancel(→expired)→新規発行、または expired/declined からの resend で対応。状態 enum・遷移・操作は現状維持(`lost` 等は作らない)。招待フロー_団体.md 設計ポイント4 に反映済み。`org POST /create` の挙動追加(佐藤さんへ伝える事項 §3-4)。

### 2.3 コース招待の固有事項
- 方式 3種: `selected`(会員指名)/ `email` / `url`(URL発行・メール送信なし・主催者が手動配布)。
- 状態 enum: `sent` / `url_issued` / `accepted` / `declined` / `expired`。旧「使用済」は API 上 `accepted`(`accepted_user_id` 付き)に相当(状態遷移図で畳んだ)。
- **`url_issued` は辞退できる(辞退可)**。`resend` の直接対象ではない(resend は expired/declined のみ)。
  - 根拠: API 本体(decline エンドポイントの対象に url_issued を含む、状態遷移図、declined_at フィールド)は一貫して url_issued→declined を前提にしている。反しているのは「招待ステータスの遷移」節の注記一文のみ → **書き損じと判断**。
- コース承諾の固有エラー: `org.NOT_JOINED` / `org.DIFFERENT_ORG`(→「先に団体に参加」)、`course.ALREADY_MEMBER`、`invitation.FORBIDDEN`(selected 指名と不一致)。
- **コース招待の作成時バリデーション**: selected/email は作成時に `target_user.DIFFERENT_ORG` / `target_user.ALREADY_MEMBER` を検査。団体招待も発行時チェックを持つ(下記)が、団体は「未登録メールは素通り(ベストエフォート)＋承諾時に確定」の二段構えである点がコースと異なる。
- **団体招待の1会員1団体チェックは二段構え**: 発行時=会員ID／メールが既存アカウントに解決でき別団体所属なら作成時エラー(未登録メールは素通り)、承諾時=`POST /accept` の `ALREADY_JOINED` で確定(フェイルセーフ)。佐藤さんと合意済・`org POST /create` に発行時チェック追加予定。招待フロー_団体.md 設計ポイント1・2 に反映済み。

### 2.4 被招待者ランディング(公開ページ)
- **IV-1 = 団体招待 被招待者ランディング**(旧 B-1 から改名。学習者画面 B-01〜B-07 と番号空間が衝突するため IV 系に)。WF §8。
- **IV-2 = コース招待 被招待者ランディング**。WF §11。IV-1 と対称だが、**「アカウントを作成して承諾」導線は持たない**(コース招待は団体所属済みが前提 = 招待フロー_コース 前提2)。
- 構成: 1ランディング + 状態バリエーション(操作可能/期限切れ/承諾済み/辞退済み/無効なリンク)+ 結果(参加完了/辞退完了)+ 招待メール本文イメージ。
- **招待者名・団体名・主催者名はランディングに出さない**。GET `/get` が返さないため(IV-1: invitation+org、IV-2: invitation+course{id,name} のみ)。

### 2.6 お気に入り・コメント(2026-06-19 確定。佐藤さん回答 = favorite_comment_spec_answers.md)

- **モデレーション = UC-46 新設**: 他者コメント削除。コンテンツ作成者(自作ターゲット)＋団体管理者(自団体メンバーのコンテンツ＝介入編集 UC-19/28 の延長)。物理削除・監査ログ対象外。UC-44 は本人削除と明確化。**WF §12 に反映済み**(2026-06-19、方式確定): タブではなく、コース/ユニット詳細画面(A-MC2/A-C2/A-MU2/A-U2)の**ヘッダにコメント数(集約・クリックで遷移)とお気に入り数(配下レベル別・表示のみ)を表示**し、コメント数から**独立したコメント一覧画面 A-CMT**(新規。A-M4/A-CM3 と同列の遷移先。1仕様/複数host)へ遷移する方式。A-CMT で集約一覧表示=UC-45、行削除=UC-46。投稿日時降順固定・フィルタなし、ページネーション(A-M4/A-CM3 同形・50件/ページ・`has_next`)、層別サマリ(対象種別ごとの全集約件数・表示専用・フィルタなし・クリック不可。お気に入りのヘッダ内訳と粒度対称だが置き場所は遷移先側)、空状態文言あり。介入編集 host(A-C2/A-U2)では A-CMT に介入編集バナー+削除モーダル注記。B 系学習者画面でのその場削除は B 系ワイヤーフレーム化時に対応(本フェーズ対象外)。A-CMT は画面一覧 A 系インベントリに追加済。

### 2.7 コース公開変更時の配下帰属ユニットへの伝播(2026-06-29 確定)

伝播型を本筋に確定。コース帰属ユニットの実効公開範囲を「ユニット単体の `公開` 値=実効値」で読み出せるよう(読み出し時に親コースを辿らない)、コース公開変更時にコース値を配下帰属ユニットへ**上書き伝播**(属性更新・DB 書き換え)。公開系(公開/プライベート公開/団体限定公開)は非公開ユニットを除き上書き。**コース→非公開は元値問わず配下を全て非公開へ**倒す(直接参照=URL を断つため)。元値の退避はしない。**コース非公開→公開系への再変更時のみ、連鎖反映を主催者の選択制**(全追従/全据え置きの二択。将来はユニット個別選択へ拡張可)。外部公開ロックは別層の規則で、伝播後の Unit.公開 に閲覧時の動的格下げが重なる。画面一覧「公開範囲の定義 / コース公開設定の変更時の配下帰属ユニットへの伝播」と UC-12 に反映済。なお、このミューテーション(コース公開変更=配下への連鎖更新)の順序・トランザクション・実行層はオーケストレーション(連鎖契約)側=佐藤さんの領分。

### 2.8 「一般会員のみロック」下のコース構成の不変条件(2026-06-29 確定・設計7)

外部から閲覧可能なコース内で「見える配下 / 見えない配下」の混在を生む唯一の機構は `一般会員のみロック`(投稿者ロールで実効公開範囲が割れる。`全員ロック` は均一格下げで割れない)。この混在を読み出し側で吸収する(コメント集約のマスク行・viewer 依存)のをやめ、**入口で禁じる不変条件を1本**置くことに確定(佐藤さんと大筋合意・レポート = `レポート_一般会員のみロック下のコース構成ルール.md`)。

> 不変条件: `一般会員のみロック` が有効な団体では、実効的に外部公開されるコース(= 管理者が主催する公開 / プライベート公開コース。一般会員主催のコースはロックで団体限定に格下げされ外部公開されないため対象外)に、一般会員が投稿したユニットを含めてはならない。

外部公開ロックと同じ**規則(制約)**。チェックは1つ、適用箇所は3つで、いずれも同一条件違反として一様にリジェクト: (1) ロック変更(UC-02。`off`/`全員ロック`→`一般会員のみロック` 切替時に混在があれば拒否し整理を促す)、(2) ロック下の投稿・コース帰属(UC-20。帰属ユニットはコース公開値に追従するため単体投稿の選択肢非表示では捕捉できない経路を塞ぐ)、(3) コース公開化(UC-12。§2.7 伝播の前段でチェック)。効果: 閲覧できるコースは常に all-or-nothing になり、学習者側コメント集約(UC-45)はマスク行・viewer 依存を持たず host 到達者には全可読。**お気に入り一覧(UC-42)の身元ゲートによるアクセス不可表示(Q1/Q2)は本不変条件の対象外=別機構として据え置き**。反映済: 画面一覧「公開範囲の定義 / 『一般会員のみロック』下のコース構成の不変条件」+ UC-02/12/20 + UC-45、favorite_comment_spec_answers.md(Q5・末尾 visibility 整理)、WF §12 注記。マスク行方式(2026-06-23)は全面撤回。チェックの実行層・トランザクションはオーケストレーション側=佐藤さんの領分。



### 2.9 コースメンバー=共同編集者の権限とマイの再定義(2026-07-01 確定・設計7)

コースメンバー(共同編集者)の権限が未定義だった土台の穴を、権限モデルとして確定。**二ドメイン分離**: 閲覧可否は学習者ドメイン(公開設定・所属団体・外部公開ロック)、コースメンバーは投稿者ドメインで両者は無関係(§1「コースメンバーは閲覧範囲の決定要素ではない」の根拠)。表示順の議論はこの穴を踏み抜いて発見された。

- **共同編集(連帯責任・分与モデル)**: **主催者がコース資産(帰属ユニットとその配下)のオーナーで、帰属ユニットを投稿者を問わず編集・削除・表示順変更できる。コースメンバー(共同編集者)は主催者がこの編集権を招待により分与した会員で、同じ範囲を連帯責任で行える**(UC-15b 新設)。原資=主催者、コースメンバー=その分与、という順序。削除を含むのは作業分散のため。コース自体の設定・メンバー管理・主催者移譲・コース削除・コース表示順は**主催者専権**(＋団体管理者介入)。非帰属ユニットは共同編集対象外(投稿者本人＋管理者のみ)。主催者移譲(UC-15a)しても既存メンバー関係は維持(関係はコースに帰属、新主催者が原資になる)。〔設計7・ゲートキーパー指摘で是正: 当初 UC 主アクター等から主催者が抜け、権限モデル表とのみ食い違っていた。主催者を全所(UC-21/22/24/25/26・導線表「誰が」)に補い三者一致させた。〕
- **表示順のスコープ**: `コース.表示順`=団体スコープ(団体ポータルの学習者順)、`ユニット.表示順`=コーススコープ(コース内の学習者順)。数値・飛び飛び可・重複可・一意性チェックなし。数値指定は詳細編集画面が基本。行内上下は、コースは A-C1(団体全コースが並ぶ)、ユニットは**単一コースに絞り込まれているとき**(活性は画面非依存=絞り込み状態で決まる。A-MU1=投稿者本人＋主催者＋コースメンバー、A-U1=団体管理者の介入 UC-28 で、いずれも単一コース絞り込み時に活性)。コース詳細→帰属ユニット一覧の遷移は当該コース絞り込みをデフォルト適用(A-MC2→A-MU1、A-C2→A-U1 の両対称)。非絞り込み・コース以外の絞り込み時は表示順反映のみ。ソート(基準切替)はどの一覧にも置かない。パート/デッキの表示順はエクセル登場順由来で別系統。
- **「マイ」の再定義(原理=関与)**: 「マイ」は自分が**関与するもの**と原理で定義する(列挙で書くと主催コース由来などの漏れが起きるため。設計7で実際に mermaid とA-MU1注記から主催者が漏れ、ゲートキーパー指摘で是正した)。マイコース=自分が関与するコース(主催／参加)、マイユニット=自投稿＋自分が関与するコース(主催／参加)の帰属ユニット(他メンバー分含む)。A-MU1 はコースでグルーピングし、所有/共同編集をバッジで区別(主催コースの他人ユニットも操作は同じなので「共同編集」に含める=2区分)。A-C1(団体コース一覧)は閲覧のみから改め、団体管理者が行内上下ボタンで団体ポータル順を並べ替えできる(WF 描き直し対象)。**数値入力は一覧に置かず詳細編集画面のみ**(コース=A-MC2/A-C2、ユニット=A-MU2/A-U2)。一覧は数値を表示し、操作は上下ボタン(コース=A-C1、ユニット=単一コース絞り込み時の A-MU1)。

## 5. 概念モデルの粒度メモ(混乱しやすい点)

- 概念モデル: ユニット(ブック) > [パート] > デッキ(チャプター) > カード > センテンス。**パートは任意のグルーピング層**(デッキ一覧の区切り)。デッキはブック直下に必ず帰属し(`Unit → デッキ [1 -- 1..*]`)、パートへの帰属はオプション(`Unit → パート [1 -- 0..*]`、`パート → デッキ [0..1 -- 1..*]`)。ミニブックはパート無し(区切りビュー省略)、単語型ブック等は複数パート可。エクセルの「パート」列・「パート編集ID」列も省略可で連動(メディアパック §1.2〜§1.4)。
- 既存「ちょい英語」配信: 既存システムは body を「デッキオブジェクト」に持つ。`body`(String/JSON)= 1デッキ分。`title`/`analysis`/`image` はデッキオブジェクトのプロパティ。
- TTSボイス: センテンス.話者 を voice キーに使用(`chatterboxtts.csv` で解決、未マッチ時はカード内の行 parity で alloy/ash にフォールバック。詳細はメディアパック §3.3)。
