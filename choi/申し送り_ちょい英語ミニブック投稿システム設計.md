## 1. 運用ルールとファイル体制

### 運用ルール(全スレッド共通・踏襲)

- **確認 → 合意 → 編集 → grep/レンダリング検証 → 出力**。黙って方針を変えない
- **単一情報源原則**。同じ規則を複数箇所に書くときは正本を1つ決め、他は参照
- 整合チェックは grep での一括突き合わせ
- **API 正**(佐藤さんの API ドキュメントが正)。ただし API 内部矛盾は「書き損じ」を特定のうえ確認
- 佐藤さん管轄(`org_invitation.md` / `course_invitation.md`)は**読み取り専用**
- 番号(§・UC・画面ID・エッジID)は**付け替えず末尾追記**。削除時は欠番として明記
- WF修正仕様 = Claude Design 向け指示書。画面遷移図 SVG 4枚 = **Claude が直接編集**(viewBox `0 0 1123 794`)
- 編集後は毎回ハングル混入チェック(過去に混入事故があったため)

### ファイル体制(設計8で変更)

**既存ファイルは GitHub から直接読み出す方式に変更した。**

- マスター: `https://github.com/topicmaker-git/Pages` の `choi/` ディレクトリ(public、raw 取得可)
- セッション冒頭で raw.githubusercontent.com から一括ダウンロードして作業環境に展開する
  (GitHub API はレート制限に当たりやすいので raw 直接取得を使う。URL の日本語ファイル名は percent-encode)
- **佐藤さんの API ドキュメントは別リポジトリ** `topicmaker-git/enHack-Analysis`(**private**)。
  raw 取得不可。必要なファイル(`org_invitation.md` / `course_invitation.md` 等)は
  **ユーザーがメッセージ添付(＋ → GitHub)で都度渡す**運用。全部は不要、必要分のみ

### 検証環境の注意(設計8での教訓)

- **mermaid 検証**: `npx @mermaid-js/mermaid-cli` は Chrome 不在で**静かに失敗する**
  (SVG が生成されないのに正常終了に見える誤検知を一度起こした)。
  `npx puppeteer browsers install chrome-headless-shell` で導入し、
  `-p puppeteer-config.json`(executablePath + `--no-sandbox`)を指定して実行し、
  **exit code と出力 SVG の実在を必ず確認**すること
- **SVG 検証**: XML 妥当性(ElementTree)+ cairosvg で PNG 化して目視
  (検証環境に日本語フォントが無く豆腐になるが、レイアウト確認には足りる)
- **PDF 検証**(Claude Design から受領した WF PDF の検収に毎回必要):
  - 検証環境に **`pdftotext` は無い**。**PyMuPDF(`fitz`)/ pypdf** を使う。
    テキスト抽出・ページ数・見出しの新旧比較は `fitz` の `page.get_text()`、
    ページ画像化は `page.get_pixmap()` で PNG に落として目視
  - **断ち切れ検査は描画要素の座標で行う**: `page.get_drawings()` /
    `page.get_text("dict")` の bbox から各ページの最大 X を取り、
    A4 幅(595pt)超過のページを列挙する(§2.6 の「51/56 ページで超過、
    最大 maxX ≈ 717pt」はこの方法で測った値)。目視だけでは見落とす
  - **フッタの総ページ数表記と実ページ数のオフバイワンは PDF 生成方式に由来する
    既知の挙動であり、不整合ではない**。指摘・修正依頼の対象にしないこと

### 2.2 団体所属 = 全アセット管理下(裁定・佐藤さんの疑問への回答)

佐藤さんの疑問「団体所属前に作成したユニットを団体一覧に出す/管理者が編集する/
コースに帰属させてよいか」に対する裁定:

**団体に所属すると、当該会員のすべてのコンテンツ資産(所属前に作成したユニットを

- 渡したくないユニットは、参加前にダウンロード(UC-23)して削除するか、別アカウントで参加
- 外部公開ロック有効(≠ off)団体では、除外時にコース非帰属ユニットも管理者へ移譲
  (UC-05)されるため、所属前作成分も持ち出せない
- 反映先: UC仕様「システム前提 / 会員と団体の関係」(**単一情報源**)、UC-27、
  WF **§8.6**(IV-1 の注意文言。標準文言 + ロック有効時の条件付き文言、
  state ギャラリーは「ロック off / ロック有効」の2バリエーション)、
  招待フロー_団体.md 設計ポイント5

### 2.5 カテゴリー・サブカテゴリーの確定(出自・検索軸を確定/検索条件詳細は継続)

指摘「カテゴリ/サブカテゴリを誰が定義するのか仕様書全体を通じて不明」→ 過去スレッド
検索で確認: 概念モデル設計時に「ディレクトリ分類用」として既存ちょい英語から引き継いだ
属性で、**定義主体は当初から未議論**(UC-32 の「※別途確認」が名残)。裁定により、
**出自(定義主体・保持形態)と検索軸までを確定し、検索条件の詳細は未確定として残す**:

- **性格(2026-07-13 確定)**: ユニット(ブック)を整理(ディレクトリ分類)・検索する
  ための、**ちょい英語全体にグローバルな統制キー**。カテゴリー=大分類、
  サブカテゴリー=その下位分類(従属・連動絞り込み)。
  例:「試験対策 / TOEIC」「日常英会話 / レストラン・カフェ」(例は説明用)。
  フリータグ=投稿者の自由語彙とは役割分担。団体・コース・投稿者は独自定義不可
- **実装形態(2026-07-16 確定)**: マスターは**フロントエンド同梱の静的 JSON**
  (改廃はフロントのリリース。取得 API なし)。ユニットには選択値を **String** 保存。
  カテゴリコード定義と表示ラベル辞書を分離し保存 String を安定コードとする設計の余地
  あり(名称変更をラベル辞書差し替えで吸収)。表示名をそのまま保存する場合は改名・
  削除時に既存データのマイグレーションが必要。**不変条件: 保存値がマスターと照合可能
  であり続けること**。方式選択は実装側に委ねる
- **未確定として残した範囲**: UC-32 の検索条件の詳細(カテゴリー/サブカテゴリー/
  フリータグの組合せ・一致条件など)。3つとも検索軸に使うことは確定済み。
  UC-32 行の `※` はこの範囲を指すマーカーとして**意図的に残置**している(削らないこと)
- 反映先: UC仕様「システム前提 / カテゴリー・サブカテゴリーの定義」(**単一情報源**)、
  未解決事項の UC-32 項(出自・検索軸は確定、検索条件詳細は未確定として明記)、
  概念モデル図の Unit 直前注記、WF **§15**
- **WF §15 は挙動仕様(実装向けの記録)であり再レンダリング不要**(§15.2 冒頭に明記
  済み。選択式 UI 自体は既存 WF に描画済み)
