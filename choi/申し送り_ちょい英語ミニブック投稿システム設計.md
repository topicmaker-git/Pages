### 運用ルール(全スレッド共通・踏襲)

### 運用ルール(設計21 で追加)

- **実測の突き合わせが割れたら、結論を出す前に対象ファイルの同一性を
  確認する**(SHA-256・書庫構成・`docProps/app.xml` の生成アプリ名)。
  CR エスケープの綴り(大文字/小文字)を巡る検収の応酬は、双方の計測が
  正しく、対象が別ファイル(生エクスポートと、Excel の開閉保存を経た
  コピー)だったことが原因。xlsx は同一内容でも経路により文字列の
  格納方式・エスケープの綴り・出現件数が変わる
- **入力のユースケース(誰が何のために作るデータか)を確定してから
  入力契約を検分・裁定する**。変換ツールの入力をプロトタイプの
  エクスポートファイルと誤認したまま検分と裁定を進め、入力の出所
  (生成AIと人間による量産・人間校正後)が判明した時点で数量前提の
  妥当性が未決に戻った。2026-09-02 に裁定し数量固定を全面撤回(§3)

### ファイル体制(踏襲)

**既存ファイルは GitHub から直接読み出す方式。**

- マスター: `https://github.com/topicmaker-git/Pages` の `choi/` ディレクトリ(public、raw 取得可)
- セッション冒頭で clone または raw.githubusercontent.com から一括取得して展開
  (URL の日本語ファイル名は percent-encode。**fetch 系ツールは URL 長超過で
  弾くことがあるため、コンテナの curl / sparse clone が確実**。GitHub API は
  未認証だとレート制限に当たりやすく、sparse clone が安定。設計21 も
  fetch は URL 長で失敗し、curl と sparse clone で取得した)
- **佐藤さんの API ドキュメントは別リポジトリ** `topicmaker-git/enHack-Analysis`(**private**)。
  raw 取得不可。必要なファイルは**ユーザーがメッセージ添付で都度渡す**運用。
  実装コードの調査はゲートキーパー経由
- **devel 環境の API レスポンスは BASIC 認証下**のため、コンテナから直接
  取得できない。高橋さんがコピペまたはファイル添付で渡す(巨大レスポンスは
  ファイル添付が確実)

### 2.2 設計21: 変換ツール要件.md の改訂(全量変換への着手)

AB会話データ → ミニブック形式の全量変換に着手した。**分担**: 仕様残件の
消化は仕様側スレッド、変換ツールの実装実務(リポジトリ構成・音声/画像
生成方法の検討を含む)は独立開発ディレクトリ `~/dev/ChoiABConverter/` で
Claude Code 管轄。実装本体は従来どおり Pages 管理外(要件 §0)。

**改訂内容**(すべて追記。既存行の変更・削除なし):

- **§8 新設「成立条件の保証(ハッシュ規則 v1)」**: 要求仕様 §3.4 が
  教材作成ツールに課す成立条件の保証責務を受領(既決の転記)。規則の
  正本は要求仕様 §3.2/§3.3 で転記しない。参照実装は STATUS.md §3 の
  `normalize` / `quote` / `sha256hex` / `sentenceHash` / `cardHash` の
  5関数(`sha256hex` を外した移植は成立しない)。要求仕様 §3.3.1 の
  テストベクター照合を必須とし、ただし通過は規則全体の一致を保証しない。
  **ハッシュは納品物に含めない**(学習アプリが自ら算出する設計のため、
  マニフェストを納品しても照合の受け手が存在しない)。違反は変換エラー
  停止・元データ側の修正で解消
- **§6 検査13〜16 追加**: 成立条件1〜3(カード内センテンス重複 /
  デッキ内カードハッシュ重複 / 空正規化)と CR 残留(literal
  `_x000D_` / `_x000d_`・生 CR)。条件4(順序確定)は出力形態
  (1データ行 = 1センテンス・固定行順)が構造的に保証するため検査なし
- **§1.2 追記(セル内改行・空行)**: CR は OOXML エスケープ `_xHHHH_`
  形式で格納され、綴りと格納方式は生成元依存。openpyxl 等は復号せず
  綴りのまま返すため、除去 → LF 分割 → 空行読み飛ばしの順で処理する
  (この順序のみが CRLF の空行を正しく捌く)。**空行の読み飛ばしは記法の
  解釈規則であって内容の補正ではない**(「黙って補正しない」の対象外。
  元データ ID 76〜80 に実例)
- **§0 ユースケース追記**: 入力は生成AIと人間が量産し人間校正(内容面)を
  経た 7列 xlsx。プロトタイプのエクスポートは形式の見本であって入力では
  ない(現物を sample/ に収載)。本ツールは量産データに対する機械的検査
  (形式面)の受け入れゲートを兼ねる。**投稿システムへの投稿は要求範囲外**
  (ツールへの投稿機能併載は将来の含みとして言及されたのみで、本書では
  要求しない)
- **§1.1 シート同定規則追記**: ヘッダー行が7列に完全一致するシートを
  読む。該当0件・複数件は変換エラー(付帯シートの有無に依存しない)

**検収**(すべて反映済み): 教材サーバーのハッシュ受領に関する事実誤りの
句の削除(要求仕様 §3.3 と衝突)/ `sha256hex` の列挙漏れ / 検査16 の

### 2.3 設計21: 元データ現物の検分とユースケースの確定

プロトタイプのエクスポートデータを要件 §1 と全件突き合わせた(検分は
生エクスポートに対して実施。`sample/AB教材Excelパック_2026-09-01-08-21.xlsx`
は同一データを Excel で開いて保存した現物で、全数検証の結果はそのまま
有効)。

- **数量前提は完全一致**: 300 ID 通し番号(欠番・重複なし)・
  3カテゴリー × 各100 ID・60テーマ × 各5セット・全テーマが ID 連続ブロック
- **チャンク対応(英文スラッシュ数 = 語順訳区切り数)は全1,800
  センテンスで一致**。テーマ和名は隣接・全体とも重複なし。ハングル・
  想定外の制御文字・空セルなし。ID 1〜5 は設計14 サンプルと同一テーマで、
  センテンス1 はテストベクターの原文と一致
- **ID 76〜80(1テーマ「逆に、会話レベルアップ！」)は 2会話・
  類似フレーズ各セルのペア間に空行を1行含む**。§1.2 の空行読み飛ばし
  規則で吸収(データと密に結合したパーサーが意味論的に空行を無視する、
  との裁定)
- **xlsx の器の2形態を実測で確定**: 生エクスポート(SheetJS 製)は
  文字列をシート XML に直接埋め込み・CR エスケープ小文字 `_x000d_`
  3,315箇所。Excel の開閉保存を経たコピー(sample/ に収めた現物は
  こちら)は共有文字列方式・大文字 `_x000D_` 3,048箇所(共有文字列の
