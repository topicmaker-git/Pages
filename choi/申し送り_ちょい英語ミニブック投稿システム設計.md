### 運用ルール(全スレッド共通・踏襲)

- **確認 → 合意 → 編集 → grep/レンダリング検証 → 出力**。黙って方針を変えない
- **単一情報源原則**。同じ規則を複数箇所に書くときは正本を1つ決め、他は参照
- 整合チェックは grep での一括突き合わせ
- **API 正**(佐藤さんの API ドキュメントが正)。ただし API 内部矛盾は「書き損じ」を特定のうえ確認
- **仕様を書く前に実装の現況を確認する(設計9で追加)**。「仕様未確定」に見える
  論点でも、実装側が既に設計判断を済ませていることがある。API ドキュメント・
  既存ワイヤーフレームの現物を先に当たり、既決なら「仕様化(実装への追随)」として
  整える。設計9では、未確定とされた7項目のうち6項目が実装側で決着済みだった
  (§2.1・§2.2 参照)。要求を新規に決めるのか、既決を文書に写すだけなのかを最初に
  切り分けること
- 佐藤さん管轄(`org_invitation.md` / `course_invitation.md`)は**読み取り専用**
- 番号(§・UC・画面ID・エッジID)は**付け替えず末尾追記**。削除時は欠番として明記。
  **枝番(例: §9.0b・§10.0b)で挿入する**(設計9で既存 §10.0 と番号衝突しかけた。
  挿入前に該当番号の既存有無を grep すること)
- WF修正仕様 = Claude Design 向け指示書。画面遷移図 SVG 4枚 = **Claude が直接編集**(viewBox `0 0 1123 794`)
- 編集後は毎回ハングル混入チェック(過去に混入事故があったため)

### 検証環境の注意(踏襲)

- **mermaid 検証**: `npx @mermaid-js/mermaid-cli` は Chrome 不在で**静かに失敗する**。
  `npx puppeteer browsers install chrome-headless-shell` で導入し、
  `-p puppeteer-config.json`(executablePath + `--no-sandbox`)を指定して実行し、
  **exit code と出力 SVG の実在を必ず確認**すること。設計9では状態遷移図・メイン
  フロー図を編集後に毎回この方法で再描画し、追加した遷移・ノードのラベルが SVG に
  出力されていることを grep で確認した
- **SVG 検証**: XML 妥当性(ElementTree)+ 画像化して目視
  (検証環境に日本語フォントが無く豆腐になるが、レイアウト確認には足りる)
- **PDF 検証**(Claude Design から受領した WF PDF の検収に毎回必要):
  - 検証環境に **`pdftotext` は無い**。**PyMuPDF(`fitz`)/ pypdf** を使う
    (`pip install pymupdf --break-system-packages`)。テキスト抽出・ページ数・
    見出しの新旧比較は `fitz` の `page.get_text()`、ページ画像化は
    `page.get_pixmap()` で PNG に落として目視
  - **断ち切れ検査は描画要素の座標で行う**: `page.get_drawings()` /
    `page.get_text("dict")` の bbox から各ページの最大 X を取り、A4 幅(595pt)
    超過のページを列挙する。目視だけでは見落とす
  - **フッタの総ページ数表記と実ページ数のオフバイワンは PDF 生成方式に由来する
    既知の挙動であり、不整合ではない**。指摘・修正依頼の対象にしないこと
  - **セッション冒頭で取得する WF PDF は master の最新コミット時点である**。
    Claude Design が作っても**未コミットの新版は手元に来ない**。ページ番号が
    ユーザーの見ている版とずれたら、版のずれをまず疑う(設計9で発生。当時は
    再描画が未コミットだった。§4 参照)

## 2. 設計9の確定事項

設計9は、開発リポジトリ(GitHub)の招待フロー関連 issue 群(#392 / #399 / #380、
resend トークン再利用、A-M3 エラー文言、A-CM2 誤記)を起点に、**仕様と実装の
食い違いを解消**する作業が中心だった。多くが「仕様未確定」ではなく「実装が既決で
文書が未追随」だった。

### 2.1 招待フローの未確定7項目 → 6項目が実装側で決着済みと判明

`招待フロー_団体.md` の「設計判断が必要な事項」7項目を、API ドキュメント
(`org_invitation.md` / `course_invitation.md`)と照合して棚卸しした結果:

- **1 トークン仕様** = UUID(実装確定)
- **2 期限切れの再招待** = 同一トークン再利用(実装確定。resend はトークン再発行しない)
- **3 辞退の取り扱い** = レコード保持(delete API 無し)、再招待可
- **4 CSV一括の失敗処理** = 全行ロールバック(1件エラーで全件未作成、最大100行)
- **5 会員ID指名のメール送信** = 送信する(指名でもメール送る。ゆえに対象は
  メール確認済み・アドレス登録済みに限る)
- **6 アカウント作成後の復帰** = WF §8.4 で確定済み(token 引き回し・完了後 IV-1 へ)
- **7 辞退後の再招待** = 再度案内する(declined → resend 可)

→ **節を「設計判断が必要な事項」から「設計判断(決定済み)」に改称**し、7項目に
決着内容と参照先を明記。空の「実装設計上の判断事項」節を分離して新設(今後
「決定済みの要求」と「実装機構の選択」を混ぜない構造にした)。

**節タイトルの教訓(ユーザー指摘)**: 「設計判断が必要な事項」という見出しは、
実際には「実装設計上判断を要する事項(場合により要求仕様の調整を要する)」の意味
だった。要求として未確定なのか、実装機構が未確定なのかを区別せず放置したため、
実装側から「7項目すべてが仕様待ち」に見える状態を作っていた。今後この種のリストは
両者を分けて書く。

### 2.2 cancel / resend の意味論 = B案「取消は再招待までの無効化」(裁定)

resend トークン再利用の issue(cancel した招待を resend すると同一トークンで復活)
への裁定:

- **現実装のまま(B案)を採用**。cancel は当該招待を expired にし、その時点で
  招待URLは無効。resend は同一トークンのまま再有効化する(有効期限も再設定)。
  「resend するまでは無効なので、管理者意思は各時点で正しく現実化している」
- URL を今後使わせたくない場合は **resend せず、レコードは expired のまま残して
  新規発行(cancel + create)**。二重 pending 禁止は `sent` かつ期限内のみが対象
  なので、期限切れレコードが残っていても新規発行は通る
- API 変更不要(佐藤さんへの依頼なし)。`url` 方式でも token 再生成なしは API に
  明記あり(`course_invitation.md` POST /resend)
- 反映先: 招待フロー_団体 **設計ポイント6**、招待フロー_コース **設計ポイント8**、
  WF §9.2/§10.2 の注記
- B案の前提「管理者が挙動を知っている」を担保するため、**再招待は確認ダイアログ
  を伴う**(WF §9.3/§10.3。注意文言の要点: ①以前配布した URL が再び通る
  ②使わせたくないなら新規発行 ③有効期限が再設定される)

### 2.3 再招待ダイアログ(有効期限指定) = 実装済みと判明・仕様化

A-M4 / A-CM3 の再招待は、有効期限を指定するダイアログが**実装済み**(団体・コース
とも)。resend は `expires_days`(1〜365、省略可デフォルト7)を取る。

- WF **§9.3(A-M4)/ §10.3(A-CM3)** として仕様化。見出しは「(描画済み・仕様化)」
- 変更できるのは有効期限のみ(宛先・ロール等は resend が受け取らない)。変えたい
  場合は新規発行
- **有効期限は「任意」項目・「任意」バッジを付ける**(必須ではない。A-M3/A-CM2 と揃える)
- A-CM3 は `selected`/`email` 由来と `url` 由来で文言分岐(url 由来はメール送信なし、
  主催者が URL を手動で配り直す)

### 2.4 招待URL再表示(A-CM3) = 実装済みと判明・仕様化

`url` 方式のレコードは A-CM3 の操作欄「URL表示」で招待URLを再表示・コピーできる
(実装済み)。`GET /list` が url 方式のみ `token` を返す。resend 後も `POST /resend`
が token を返す。

- WF **§10.3(2)** に仕様化。表示対象は `url_issued` 行のみ
  (expired/declined/accepted には出さない。無効URLの誤配布防止)
- 招待フロー_コース **設計ポイント8**、A-CM3 操作表・注記に反映

### 2.5 発行時エラーコードの1本化 = フロー図は分岐維持・文言は同一(裁定)

団体 API の `ALREADY_JOINED` は「招待先が既にいずれかの団体に所属」で、**他団体
所属と自団体所属済みを区別しない**(単一コード)。

- **裁定**: フロー図は状態理解のため理由別に分岐したまま(E1 1会員1団体制約 /
  E2 既に所属済み)、**A-M3 のエラーメッセージは理由によらず同一表現**にする。
  文言:「このユーザーは新規に団体会員として招待できません(すでにいずれかの
  団体に所属しています)。」
- あわせてフロー図を正確化: 旧「E2 重複招待」は API 上 `ALREADY_JOINED`(所属済み)
  であって pending の重複ではないため **E2 を「既に所属済み」に改称**し、二重招待
  (`ALREADY_PENDING`)は **E4「二重招待の禁止」**として別ノードに分離
- 承諾時(IV-1)の `org.ALREADY_JOINED`(フロー E3)は被招待者向けの別文言:
  「すでにいずれかの団体に所属しているため、この招待を承諾できません。」
  ※ WF §8.4 の旧文言「脱退してから参加してください」は**自発的脱退が仕様に無い**
  ため実行不能な案内だった。E3 ノード・§8.4 とも新文言に修正済み
- **コース側は非対称**: `DIFFERENT_ORG`(別団体・無所属)と `ALREADY_MEMBER`
  (既メンバー/主催者本人)を**別コードで返す**ため、1本化不要・フロー図の分岐
  どおり文言を分けられる
- 反映先: 招待フロー_団体 メインフロー図 + 「エラー表示に関する注記」、WF **§9.0b**

### 2.6 A-CM2 招待対象の誤記訂正 = 実装(p18)は反映済み・仕様を規定形化

A-CM2 に「団体所属の有無を問わず招待可能」「団体外・団体未所属会員も可」という
決定違反の記述があった。**コースメンバーは主催者と同じ団体所属の会員に限る**
(全方式)。PDF p18 は既に修正済みだったため、WF **§10.0b** を「(反映済み)」の
規定形で記述(「これから直す」形にしない)。

### 2.7 二重pending の条件・指名の前提(API 正で文書修正)

- 二重 pending 禁止の条件を **`sent` かつ期限内**に修正(旧記述は「`sent` のみ」で、
  期限切れ sent が重複扱いされない実装と食い違っていた)。招待フロー_団体 設計ポイント4
- `target_user_id` / `selected` 指名の前提(メール確認済み・アドレス登録済み)を
  団体・コース両方に追記
