### 運用ルール(全スレッド共通・踏襲)

- **確認 → 合意 → 編集 → grep/レンダリング検証 → 出力**。黙って方針を変えない
- **単一情報源原則**。同じ規則を複数箇所に書くときは正本を1つ決め、他は参照
- 整合チェックは grep での一括突き合わせ(言い換え表現込み)
- **API 正**(佐藤さんの API ドキュメントが正)。ただし API 内部矛盾は「書き損じ」を特定のうえ確認
- **仕様を書く前に実装の現況を確認する**。要求を新規に決めるのか、
  既決を文書に写すだけなのかを最初に切り分けること
- 佐藤さん管轄(`org_invitation.md` / `course_invitation.md`)は**読み取り専用**
- 番号(§・UC・画面ID・エッジID)は**付け替えず末尾追記**。削除時は欠番として明記。
  **枝番で挿入する**。挿入前に該当番号の既存有無を grep すること
- WF修正仕様 = Claude Design 向け指示書。画面遷移図 SVG 4枚 = **Claude が直接編集**(viewBox `0 0 1123 794`)
- 編集後は毎回ハングル混入チェック
- **切り分けの根拠に使う「規定あり側」も、規定として成立しているかを検証する**
- 実応答規約の確認(**Maker API はアプリケーションエラーも常に HTTP 200 +
  `status: 0`**)/ 実装済み機能に隣接する裁定依頼は裁定案より調査を先行 /
  Claude Design 一時指示書で「NOTE — 」を本文直書きしない / 検収の差分件数は
  **`git diff -U0` のハンク数**を基準にする / 一時ファイルは ASCII 名で運用可 /
  長文成果物は同一ターン内で高橋さんに渡し切る — の設計13 追加分はそのまま
  踏襲(詳細は git 履歴の設計13→14 版)

### 運用ルール(設計17 で追加)

- **要求の実行主体を文ごとに明示する**。「確認する」「判別する」「返さない」の
  主語がサーバーか、変換ツールか、学習アプリかを曖昧にしない。特に、
  **サーバー上に実体を持たない対象(カード・センテンス。実装は
  `deck_t.content` jsonb にデッキ丸ごと格納で card / sentence テーブル
  不存在)への生成・検証・帰属確認・新旧判別をサーバーに要求しない**。
  ハッシュの算出・照合は教材内容を知る側(教材作成ツール・学習アプリ)の
  責務で、サーバーは不透明な識別子として保持するのみ(設計17 の
  ゲートキーパー補正 F-1・G-1 の教訓)
- **ハッシュ規則等のアルゴリズム仕様には、実データから導出した検証用
  テストベクターを本文に収録する**。検証は、文書に記載した値を文書自身から
  抽出して再計算・照合する方式(転記ミスと編集破壊を同時に検出できる)。
  受益者は教材作成ツールとアプリ作成 AI(vibe/ 指示書には参照でなく
  コピーを内包させる — 自己完結原則)
- **ドラフト状態の文書は節番号を振り直してよい**。番号踏襲ルール
  (付け替えず末尾追記・枝番挿入)はリリース済み文書の参照安定性のための
  もので、リリース後に適用する。**基準はコミットの有無ではなく承認の有無**
  とする — 承認前のドラフトは、公開済みでも節構成を変更してよい
  (設計17 の要求仕様が該当。承認後は番号固定)

### ファイル体制(踏襲)

**既存ファイルは GitHub から直接読み出す方式。**

- マスター: `https://github.com/topicmaker-git/Pages` の `choi/` ディレクトリ(public、raw 取得可)
- セッション冒頭で clone または raw.githubusercontent.com から一括取得して展開
  (URL の日本語ファイル名は percent-encode。**fetch 系ツールは URL 長超過で
  弾くことがあるため、コンテナの curl / sparse clone が確実**。GitHub API は
  未認証だとレート制限に当たりやすく、sparse clone が安定)
- **佐藤さんの API ドキュメントは別リポジトリ** `topicmaker-git/enHack-Analysis`(**private**)。
  raw 取得不可。必要なファイルは**ユーザーがメッセージ添付で都度渡す**運用。
  実装コードの調査はゲートキーパー経由
- **devel 環境の API レスポンスは BASIC 認証下**のため、コンテナから直接
  取得できない。高橋さんがコピペまたはファイル添付で渡す(巨大レスポンスは
  ファイル添付が確実)

## 2. 設計17 の確定事項

### 2.1 ユーザー別学習状態・プリファレンス保存取得_要求仕様.md の起草(完了・ゲートキーパー検収済み / サーバーサイド承認待ち)

STATUS.md(vibe/ 続編)の前提となるサーバー側拡張の要求仕様を起草し、
ゲートキーパー検収を通した。学習成果の保存モデルの正本。

**文書はドラフトのまま公開する**(タイトルに「(ドラフト)」、index.md にも
その旨を明示)。サーバーサイドの実装上の制約を開発担当者に検討してもらい、
**承認が取れた時点で正式な要求仕様となる**(高橋さん方針)。ドラフト解除時は
文書タイトルと index.md の表記2か所を直す。主な確定事項:

- **保存単位は8種**(認証ユーザー / コース / ユニット / パート / デッキ /
  カード / センテンス / センテンス×学習方法)。固定フィールド+
  自由形式 JSON ペイロード(サーバー無解釈 = 不可知コンテナ原則の
  学習状態版)。最新1件のみ保持・last-write-wins・全試行履歴なし
- **識別体系**: コース〜デッキは教材サーバーの**既存の恒久識別子**
  (UUID 要求は撤回・読み替え)。**投稿データの編集IDは行同定用であり
  本ドメインでは使わない**(高橋さん裁定)。カード・センテンスは
  **コンテンツハッシュ**(SHA-256、正規化・直列化規則 v1 を §3.2 / §3.3 に
  正本化)。教材修正でハッシュが変われば教材入れ替え扱い
  (連続性なし・移行なし・残置可)
- **ハッシュの責務分界(F-1)**: 算出は教材作成ツールと学習アプリ、
  サーバーは不透明保持のみ。成立条件(§3.4: カード内正規化後重複禁止ほか)は
  **AB会話データ変換ツール(予定課題)が保証**し、サーバー登録時検査は
  非要求。話者を持たない教材は `speaker` 空文字列で直列化(登録不可に
  しない)。開発中につき既登録教材の遡及移行は不要
- **書き込み**: 学習方法識別子は ASCII 英小文字・数字・アンダースコア
  64文字以内 / ペイロードは**32,767 文字以上を下限保証**(拡張属性の
  実効上限と同水準。上限超過は失敗・既存データ保全)/ 保存単位ごとの
  **削除**(未登録状態へ戻る)を要求
- **一括読み出し**: 認証ユーザー単位(全教材・存在するデータのみ)/
  コース単位 / ユニット / パート / デッキの5系統+プリファレンス独立。
  未登録判別は実体のある階層(コース〜デッキ)のみサーバー責務、
  カード以下はアプリが自算出ハッシュ集合との差分で判別(旧ハッシュ
  データの混在も同じ扱い — G-1)
- **B1 学習成果モデルとの関係(F-2)**: 本書の学習状態モデルは
  学習者アプリ概念モデル B1 の**集約成績モデル(カード〜コース成績)を
  置き換える**(サーバーに集約・履歴を持たず最新結果からアプリが導出)。
  **単語成績は対象外・企画上保留**
- **お気に入りの役割分担**: コース〜デッキは概念モデル既存の
  「お気に入り」(ポリモーフィック関連)で実装。本機構はアプリが
  カード・センテンスに**アプリ私的**なお気に入りを提供する場合のみ
