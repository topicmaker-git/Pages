### 運用ルール(全スレッド共通・踏襲)

- **確認 → 合意 → 編集 → grep/レンダリング検証 → 出力**。黙って方針を変えない
- **単一情報源原則**。同じ規則を複数箇所に書くときは正本を1つ決め、他は参照
- 整合チェックは grep での一括突き合わせ(言い換え表現込み)
- **API 正**(佐藤さんの API ドキュメントが正)。ただし API 内部矛盾は「書き損じ」を特定のうえ確認
- **仕様を書く前に実装の現況を確認する**。要求を新規に決めるのか、
  既決を文書に写すだけなのかを最初に切り分けること
- 佐藤さん管轄(`org_invitation.md` / `course_invitation.md`)は**読み取り専用**
- 番号(§・UC・画面ID・エッジID)は**付け替えず末尾追記**。削除時は欠番として明記。
  **枝番で挿入する**。挿入前に該当番号の既存有無を grep すること
- WF修正仕様 = Claude Design 向け指示書。画面遷移図 SVG 4枚 = **Claude が直接編集**(viewBox `0 0 1123 794`)
- 編集後は毎回ハングル混入チェック
- **切り分けの根拠に使う「規定あり側」も、規定として成立しているかを検証する**
- WF・mermaid・PDF・複数ファイル納品・台帳記録・申し送り参照禁止の各ルールは
  設計10/11 で追加のとおり踏襲(詳細は git 履歴の設計11→12 版)

### 運用ルール(設計12 で追加)

- **実装の現況確認は、ゲートキーパー(Claude Code)にリポジトリを読ませて
  行える**。佐藤さんへの確認キュー(人待ち)に積む前に、コードで一次判定
  できる問いはゲートキーパー調査で消化する。設計12 では4件の確認事項の
  すべてをこの方式で解決し、人待ちゼロで仕様を確定できた。佐藤さんに残す
  のは「改修依頼」と「実装で判定できない運用判断」のみ
- **人間チームへの伝達は見出し1〜2行+仕様書参照で行う**。詳細は受け手が
  各自の AI に仕様書を読ませて自分の文脈(実装・UI影響)に展開する。
  仕様書から詳細が導出できないなら、それは伝達文の不足ではなく仕様書の
  欠陥として直す
- **拡張属性列(§1.7.2)の中身はプラットフォーム文書に書かない**。教材
  ファミリー固有の規約(スキーマ・記法)は生産側ツールと消費側アプリの
  ペア内合意であり、choi/ 直下の仕様は無解釈のコンテナ契約に徹する。
  ファミリー規約の文書化は choi/ab/ など**ファミリー区画**で行い、
  依存は「ファミリー → プラットフォーム」の一方通行とする

## 2. 設計12 の確定事項

テーマ: **AB会話教材(万次郎語アプリ系)を投稿可能にするミニブックデータ
形式の拡張**。プロトタイプ(単一HTML アプリ + 7列 xlsx + 事前生成音声
manifest)の実物解析から出発し、仕様改訂まで完了した。

### 2.1 受け入れ方針: mini の自然な拡張(不可知コンテナ路線)

- **新デッキタイプは作らない**。`type: "mini"` のまま、拡張属性(§2.2)で
  ファミリー固有メタデータを運ぶ。投稿システムは AB の意味論を一切知らない
  (仕様全文に「AB」という語は導入していない)
- **AB規約(話者4値・6行周期・extra スキーマ・チャンク記法等)は、
  変換ツール(AB→mini 展開 + AB形式の出口検査)と消費側アプリ
  (mini→内部形式アダプター)のペア内合意**。文書化は choi/ab/(§4)
- **階層写像**: ユニット=カテゴリー(3ユニット、名前・category 属性は
  UI 設定)/ パート=不使用 / デッキ=テーマ(チャプター名列)/
  カード=セット(シーン名列=「セット1」〜「セットn」の機械命名)/
  センテンス=発話(話者列= A / B / 類似A / 類似B の4値。行順は
  A, B, 類似A, 類似B, 類似A, 類似B — 奇数行=A側・偶数行=B側となり
  §3.3 偶奇フォールバックとも整合)
- **音声**: メディアパックモード本線(§3.3 無改修)。ボイスは変換ツールが
  話者プロファイル由来のプロンプトで生成(レディメイドの対応表方式は
  不成立 — プロファイルは生成のたび無限に湧く自由文のため)
- **画像**: `image_mode=pack` + **多対一参照**で無改修。テーマ画像
  (アプリでは coverSvg 実行時生成)を変換ツールが生成して画像パックに
  入れ、デッキ先頭行とカード先頭行が同一ファイルを参照(§1.6 の既定・
  実装確認済み。セットのトビラがテーマ画像を表示する現行挙動の忠実な
  データ化)。スプラッシュ画像 → ユニットカバー(`cover`、無改修)。
  話者ポートレート・口形(lipsync)はアプリ側資産で教材データ外
- **消費側**: 添付 HTML アプリ(またはその後継)が配信データを読む。
  各アプリの生成 AI がデータ契約文書(DATA.md、後続)を読んでアダプターを
  実装する構想(BYOAI 的)

### 2.2 仕様改訂の内容(投稿データ_メディアパック仕様.md ほか)

- **§1.2**: 拡張2列を追加(列16「カード属性」・列17「デッキ属性」、
  最大構成 15列 → 17列、区分「拡張」)。**列の同定はヘッダー名で行う**
  ことを明文化(列番号は標準テンプレート・DL 出力の標準列順の定義。
  任意列は個別省略可・並べ替え許容)
- **§1.3**: 境界判定の方式を注記(直前行比較・正規化後値の完全一致・
  非連続同名は別要素になる)— 実装挙動の追認明文化
- **§1.7 新設**:
  - **1.7.1 セル値の正規化(全列共通)**: 改行→半角スペース / 連続空白
    圧縮(**U+3000・NBSP 含む**)/ 前後トリム。**既存実装(`_cell`)の
    挙動の追認明文化であり、新規要求ではない**(高橋さん承認済みの裁定)。
    帰結: セル内改行は保存されない(英日2行タイトル等は extra へ)/
    語順訳のチャンク区切りは保存形で半角スペース(保存形に全角空白は
    存在し得ず、既存データも同様)/ セルは文字列型を推奨
  - **1.7.2 拡張属性列**: 先頭行のみ記入・JSON文字列・**無解釈**・
    長さ上限なし(セル上限 32,767 文字が天井。実需は数百バイト級)・
    **往復保証**(下記)
- **§4.1**: ヘッダー行の検査(必須列ヘッダーの存在・**未知ヘッダーは
  無警告で読み飛ばし**、誤記=無警告欠落のリスク注意)/ 拡張属性の
  先頭行違反・JSON パース不能の2項を追加
- **§7 手順2**: DL 出力の列構成を規定 — 拡張属性2列を反映 / **列12
  「チェック」は DB 非保存のため DL 出力に含まれない**(標準 DL は最大
  16列・パート未使用は14列。作業フラグは往復で保持されない)。検収2巡目の
  指摘(規定がないと「往復でチェックが消えるのはバグでは」と再燃する類 —
  社員ID・一括DL と同じ機序)を受けて追加
- **§9**: `body.extra`(デッキ属性)・`cards[].extra`(カード属性)を追加。
  **JSON 文字列値のまま格納(パース済みオブジェクトではない。消費側は
  二段パース)**。DL は保存済み文字列をそのまま出力(**再シリアライズ
  禁止**)し、正規化の冪等性で往復不変を保証。extra を body 内に置く
  理由(永続化・変更判定が body 全体単位 → DB スキーマ変更・差分検出
  改修が不要)と、行対応付けは編集ID(§1.4/§7)という二層の書き分けを
  明記。§9.2 に**フィールド欠落規定**(talks 系=キー常在・空文字列 /
  image・extra=記入時のみ)。§9.5 対応表・§9.6 例を追随
- **概念モデル図**: デッキ・カードに `+String 拡張属性` を追加
- **UC仕様**: 列数言及3箇所を17列に更新(うち3箇所とも設計10 の15列化に
  未追随で「14列」のまま腐っていた既存不整合を同時解消)

### 2.3 実装調査の成果(ゲートキーパー実施・仕様確定の根拠)

- `_cell` 正規化(§1.7.1 の出典)。**回帰テスト不在**(仕様=実装=テストの
  三点固定のためテスト追加を佐藤さんへ提案 — §4)
- 列解決はヘッダー名(`%HEADER_MAP`)・未知列は黙って読み飛ばし・
  `MISSING_COLUMN` は chapter / scene / en の3列のみ
- 変更検出はデッキ単位(4カラム個別 + content の canonical JSON 比較)。
  カード以下の個別差分判定は存在しない → body 内の拡張は自動で乗る
- デッキ・カードの Web UI 更新 API は現状存在しない(エクセル経由のみ)。
  TTS ワーカーは in-place 更新で未知キー保持・解析ワーカーは content 非接触
- `_build_body` はホワイトリストでゼロから再構築(既存 body から引き継ぐ
  のは type のみ)→ extra はエクセル由来とすることで消失問題を回避。
  **DL 出力(generate)への2列追加が往復の生命線**
- 画像列の境界行チェックは Media.pm より手前の Excel.pm パース時
  (REQUIRED はセル空欄チェック、zip 実在は別系 MISSING/EXTRA)。
  多対一参照(境界行に同一ファイル名)は合法で配置・配信まで成立
- 検証順序: モード一貫性(REQUIRED)→ zip 突合(MISSING/EXTRA)の
  早期リターン
- `filename` 制約 `^[A-Za-z0-9_\-\.]+$`(命名案 `id001_a0.mp3` 適合)
- 数値・日付セルは表示書式適用後の文字列になる(§1.7.1 のセル型推奨の出典)
