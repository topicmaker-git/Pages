### 運用ルール(全スレッド共通・踏襲)

- **確認 → 合意 → 編集 → grep/レンダリング検証 → 出力**。黙って方針を変えない
- **単一情報源原則**。同じ規則を複数箇所に書くときは正本を1つ決め、他は参照
- 整合チェックは grep での一括突き合わせ(言い換え表現込み)
- **API 正**(佐藤さんの API ドキュメントが正)。ただし API 内部矛盾は「書き損じ」を特定のうえ確認
- **仕様を書く前に実装の現況を確認する**。要求を新規に決めるのか、
  既決を文書に写すだけなのかを最初に切り分けること
- 佐藤さん管轄(`org_invitation.md` / `course_invitation.md`)は**読み取り専用**
- 番号(§・UC・画面ID・エッジID)は**付け替えず末尾追記**。削除時は欠番として明記。
  **枝番で挿入する**。挿入前に該当番号の既存有無を grep すること
- WF修正仕様 = Claude Design 向け指示書。画面遷移図 SVG 4枚 = **Claude が直接編集**(viewBox `0 0 1123 794`)
- 編集後は毎回ハングル混入チェック
- **切り分けの根拠に使う「規定あり側」も、規定として成立しているかを検証する**
- 実応答規約の確認(**Maker API はアプリケーションエラーも常に HTTP 200 +
  `status: 0`**)/ 実装済み機能に隣接する裁定依頼は裁定案より調査を先行 /
  Claude Design 一時指示書で「NOTE — 」を本文直書きしない / 検収の差分件数は
  **`git diff -U0` のハンク数**を基準にする / 一時ファイルは ASCII 名で運用可 /
  長文成果物は同一ターン内で高橋さんに渡し切る — の設計13 追加分はそのまま
  踏襲(詳細は git 履歴の設計13→14 版)
- 実装現況の一次判定はゲートキーパー調査で消化し、佐藤さんには改修依頼と
  運用判断のみ残す / 人間チームへの伝達は見出し1〜2行+仕様書参照 /
  拡張属性列の中身はファミリー区画(choi/ab/)で文書化 — の設計12 追加分も
  そのまま踏襲(詳細は git 履歴)
- issue の状態追跡はしない(裁定依頼として渡された論点のみ扱う)/
  サンプルデータは生成スクリプト+出口検査をセットで納品 — の設計14 追加分も
  踏襲(詳細は git 履歴の設計14→15 版)
- WF・mermaid・PDF・複数ファイル納品・台帳記録・申し送り参照禁止の各ルールは
  設計10/11 で追加のとおり踏襲(詳細は git 履歴)

### 運用ルール(設計16 で追加)

- **vibe/ 指示書の設計原則**(choi/vibe/ 配下・アプリ開発 AI 向け
  自己改造指示書): (1) **器と意味論の分離** — 器(API・データ構造の型・
  起動規約)はこちらが宣言し、中身の意味論(値の解釈・スキーマ)は教材
  ファミリーの合意に委譲する(アプリ開発者が正)。(2) **自己完結** —
  他文書の参照なしで読める。(3) **実装非言及** — 対象アプリの内部実装・
  読み替え方法を指定しない(指定すると特定アプリへの手紙になり、アプリ
  ごとに専用文書が要る構造が再生産される)。(4) **行動指針を含む** —
  内部階層の捉え直し・実データの吟味・境界層(コンバーター/フィルター)
  実装・入口1箇所の経路分岐、の自己改造の進め方は指示してよい
- **vibe/ 指示書は受け入れテストで検収してからリリースする**(設計16 実績:
  DATA.md をアプリ開発 AI に読ませ、devel での動作確認まで到達)。指示書の
  穴は受け入れ側の質問として正確に浮上する
- **添え書きは3文で足りる**(任務1文・人間のプロキシ宣言1文・受け入れ基準
  1文。choi/vibe/添え書きDATA.md が正本)。書き手はチャットで開発する
  非技術者の人間であり、添え書きの設計圧力は「AI が何を欲しいか」ではなく
  「人間が何を書けるか」に置く
- **実装正裁定(2026-08-17)**: API 境界のフィールド名・応答形は実装が正。
  具体的には (1) body は API では `content` 名でパース済みオブジェクト、
  (2) 空欄列のフィールドはキー欠落(旧「talks はキー常在・空文字列」を
  §9.2 で改訂)、(3) デッキ画像プロパティは `image_filename`

### ファイル体制(踏襲)

**既存ファイルは GitHub から直接読み出す方式。**

- マスター: `https://github.com/topicmaker-git/Pages` の `choi/` ディレクトリ(public、raw 取得可)
- セッション冒頭で clone または raw.githubusercontent.com から一括取得して展開
  (URL の日本語ファイル名は percent-encode。**fetch 系ツールは URL 長超過で
  弾くことがあるため、コンテナの curl / sparse clone が確実**)
- **佐藤さんの API ドキュメントは別リポジトリ** `topicmaker-git/enHack-Analysis`(**private**)。
  raw 取得不可。必要なファイルは**ユーザーがメッセージ添付で都度渡す**運用。
  実装コードの調査はゲートキーパー経由
- **devel 環境の API レスポンスは BASIC 認証下**のため、コンテナから直接
  取得できない。高橋さんがコピペまたはファイル添付で渡す(設計16 実績。
  巨大レスポンスはファイル添付が確実)
