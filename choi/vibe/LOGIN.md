# LOGIN.md — ログイン状態の確認規約と自己改造指針

## 0. 本書の性格

本書は、`*.enhack.app` ドメインに配置される学習アプリが、利用者の
**ログイン状態を確認し、未ログインを利用者に知らせる**ための共通規約と、
そのための自己改造の行動指針である。読者はアプリの開発者(生成 AI を含む)を
想定する。DATA.md(教材データ読み込み規約)の姉妹編であり、起動規約
(同一ドメイン配置・ルートからのパス指定)は DATA.md §2 を踏襲する。

- 本書が定めるのは**判定と通知**である: ログイン状態の確認方法、確認結果の
  解釈、未ログイン時に利用者へ知らせる義務
- 本書(version 1)が答える問いは**「サーバーへ記録できる状態か」の一点**で
  ある。利用者の属性を得ることは目的ではない(§2)。属性を必要とする機能は、
  それを必要とする指示書が本書とは別に規定する
- **ログイン画面への誘導(遷移・復帰)は本書のスコープ外である**。誘導先の
  復帰仕様が未確定のため、アプリは画面遷移を実装せず、メッセージの提示に
  とどめる(§4)。誘導は復帰仕様の確定後、本書の改訂で追加される
- メッセージの文言・見た目・提示方法(バナー、ダイアログ等)はアプリの
  裁量とする
- ログイン状態を**必要とする機能の範囲**もアプリの裁量に属する(教材の
  閲覧は DATA.md の範囲でログインなしに可能である)。ただしユーザー別
  データをサーバーへ保存・取得する機能(別途の指示書が扱う)は、本書の
  判定でログイン済みのときにだけ呼び出すこと

## 1. 判定の二層構造(重要)

ログイン確認には **HTTP レイヤーと JSON レイヤーの2つの status** が現れる。
混同しないこと。

| レイヤー | 見るもの | 意味 |
|---|---|---|
| HTTP | `response.ok`(200 か否か) | 通信とサーバーの成否。**ログイン状態とは無関係** |
| JSON | `body.status` | **1: ログイン済み / 0: 未ログイン** |

- **ログイン切れでも HTTP は 200 で返る**。HTTP ステータスでログイン状態を
  判定してはならない
- HTTP が 200 でない(またはネットワークエラーの)場合は**判定不能**で
  あり、未ログインともログイン済みとも同一視しないこと(§4)

## 2. ログインチェック API

- パス(ルートから): `GET /maker/api/user/info`
- 応答(共通形式):

```json
{
    "status": 1,
    "error": null,
    "data": { ... }
}
```

- **本書がアプリに読むことを認めるのは `status` のみ**である。`data` は
  ログイン済み・未ログインのいずれの場合も**使用しない**(DATA.md §4 と
  同じ防御規定)。`data` には会員のプロフィール・団体・契約等のフィールドが
  同居するが、本書の範囲ではすべて読み飛ばすこと
- 利用者名等の表示にこの応答を使ってよいかは**本書では定めない**。表示に
  用いる属性の所在と編集責務は別途の合意に属し、それを必要とする指示書が
  その時点で規定する

## 3. 正準実装

次のコードを**改変せず**アプリに組み込むこと(依存ライブラリなし)。

```javascript
const EnhackLogin = {
    loggedIn: false,
    check: async function () {
        const response = await fetch( "/maker/api/user/info", {
            method: "GET",
            credentials: "same-origin"
        } );
        if ( ! response.ok ) {
            throw new Error( "login check failed: HTTP " + response.status );
        }
        const body = await response.json();
        this.loggedIn = body.status ? true : false;
        return this.loggedIn;
    },
    getXSRFToken: function () {
        let token = null;
        document.cookie.split( /;\s*/ ).forEach( ( pair ) => {
            const kv = pair.split( "=" );
            if ( kv[ 0 ] === "XSRF-TOKEN" ) {
                token = kv[ 1 ];
            }
        } );
        return token;
    }
};
```

- `check()` は呼ばれるたびに `loggedIn` を**最新の応答で更新する**
  (ログイン済み → 失効後の再チェックで false に戻る)。呼び出し回数に
  制約はない
- **応答の `data` を保持しないのは意図的である**(§2)。判定に必要なのは
  `status` だけであり、器を持たないことで未規定のフィールドを読む余地を
  実装の側で塞ぐ。属性が必要になった時点で、それを必要とする指示書と
  ともに本書を改訂する
- `getXSRFToken()` は POST を伴う API(ユーザー別データの保存等)が要求する
  `X-XSRF-TOKEN` ヘッダの値を返す。本書の範囲では使用箇所はなく、別途の
  指示書のための**予約**である。cookie の値は加工(デコード)せず
  そのまま用いる

## 4. アプリの振る舞い

- **起動時に `check()` を1回実行する**。教材読み込み(DATA.md)と並行して
  よい
- 判定結果による分岐:
  - **ログイン済み**: 通常どおり動作する
  - **未ログイン**(`check()` が false): **ログインが必要である旨を利用者に
    メッセージで知らせる**。画面遷移・リンクによる誘導は行わない(§0)。
    メッセージ後にアプリを止めるか、ログインなしで使える範囲で続行するかは
    アプリの裁量
  - **判定不能**(`check()` が例外): 確認できなかった旨の通知はアプリの
    裁量とするが、ログイン済みとして扱ってはならない
- ログイン状態はセッションの失効により**アプリの動作中に変わりうる**。
  動作中の失効は、ユーザー別データ API が共通応答の `error` に
  `{ "user": { "AUTH": 1 } }` を載せて返すことで検知される(取り扱いは
  当該指示書が定める。本書の範囲では起動時の1回で足りる)

## 5. 自己改造の行動指針

1. **組み込みは境界層に置く**。§3 の正準実装と §4 の分岐(メッセージ提示)
   を起動処理の入口に置き、既存の内部モデル・表示・演出のコードには
   手を入れない(DATA.md §6 指針3 と同じ原則)
2. **メッセージは自アプリの流儀で**。文言・見た目は自アプリの UI 資産で
   実装してよい。伝えるべき内容は「この機能の利用にはログインが必要である」
   ことだけである
3. **検証は開発環境で2状態を実測する**。(a) ログイン済みブラウザで起動して
   通常動作すること、(b) 未ログイン(プライベートウィンドウ等)で起動して
   メッセージが提示されること。判定不能系(ネットワーク遮断)は任意
