# DATA.md — enHack 教材データ読み込み規約と自己改造指針

## 0. 本書の性格

本書は、`*.enhack.app` ドメインに配置される学習アプリが、教材データを
enHack サーバー(Maker API)から読み込んで動作するための**共通規約**と、
そのための**自己改造の行動指針**である。読者はアプリの開発者
(生成 AI を含む)を想定する。

- 本書が宣言するのは**器**である: 教材の階層、API、応答規約、データの
  構造(型)、メディアの解決、起動規約
- **中身の意味論**(各フィールドの値がアプリにとって何を意味するか、
  拡張属性のスキーマ)は本書のスコープ外である。それらは教材の作成側と
  アプリ側の合意(教材ファミリーごとの規約)に属し、**アプリ開発者の側が
  本書の読者の誰よりもよく知っている**
- 取得したデータをアプリ内部の形式へ変換するのは**アプリ側の責務**である
  (§6 の行動指針を参照)
- 言語解析データ(§3.3)は教材本文とは別系統の**付加データ**である。それを
  用いるか否かはアプリの側が知っており、用いるアプリだけが取得する
- 成績・お気に入り・ログイン等、ユーザーセッションのもとでサーバーに
  書き込む機能は本書の対象外(別途の指示書が扱う)

## 1. enHack の教材階層

enHack は教材を次の階層で管理・配信する。

```
コース(course)
└─ ユニット(unit)          … 配信・投稿の単位。本書の取得起点
   └─ [パート(part)]        … 任意の中間階層(使わない教材では不在)
      └─ デッキ(deck)       … 教材本体を持つ単位
         └─ カード(card)
            └─ センテンス   … API 上は talks[] として現れる
```

- アプリがデータ読み込みに用いる起点は**ユニット**である(コースは
  ユニットの上位文脈であり、教材取得には不要)
- パートを使わない教材では、デッキはユニット直下に並ぶ
  (デッキの `part_id` が null)
- **あなたのアプリが内部で表現している教材構造も、この階層への写像として
  捉え直せる**はずである(§6 指針1)

## 2. 起動規約(*.enhack.app 共通)

- アプリは API と**同じドメインのサーバーに配置される**。API へは
  **ルートからのパス指定**(`/maker/api/…`)でアクセスし、ドメインを
  コードや設定に持たない(開発・ステージング・本番のドメイン差は配置で
  解決される)
- **起動時のクエリパラメータ `unit_id` でユニット ID が指定された場合、
  アプリは本書の API で教材データを取得し、内部形式へ変換して使用する**。
  複数ユニットはカンマ区切りで渡されうる
- `unit_id` の指定がない場合の挙動(内蔵教材の使用等)はアプリの裁量と
  する(既存の動作を保存してよい)

## 3. API 仕様

### 3.1 応答規約(重要)

- 全エンドポイントは GET・JSON 応答
- **アプリケーションエラーでも常に HTTP 200** が返る。成否は JSON の
  `status` で判定する — **`status: 1` が成功、`status: 0` がエラー**
  (エラー内容は `error`)。HTTP ステータスコードで成否を分岐しないこと
- 成功時の本体は `data` に入る

### 3.2 エンドポイント

3段構成で取得する。

| # | パス(ルートから) | パラメータ | 得るもの |
|---|---|---|---|
| 1 | `/maker/api/unit/detail` | `id`(ユニットID) | ユニット属性・処理状態・メディア一括 URL(`data.unit`) |
| 2 | `/maker/api/deck/list` | `unit_id` | デッキの一覧(`data.decks`)。表示順は `sort` 昇順 |
| 3 | `/maker/api/deck/detail` | `id`(デッキID)。解析データを用いるアプリは `analysis=1` を添える | デッキの教材本体(`data.deck`) |

- 手順1で `data.unit` の **`audio_status` / `image_status` がともに
  `"done"`** であることを確認してから教材として扱うこと(未完了ユニットは
  メディアが欠落しうる)。**解析データ(§3.3)を用いるアプリは、さらに
  `analysis_status` が `"done"` であること**を確認する。いずれかを満たさ
  ないユニットは未完了として扱い、教材として使わない
- 言語解析はメディア生成とは別系統で、教材の登録時には実行されない
  (登録済みの教材に対して事後に実行される)。解析データを用いないアプリは
  `analysis_status` を判定に含めない
- 手順2の一覧要素は軽量表現であり、教材本体を含まない。本体は必ず手順3で
  取得する
- 手順3の `analysis` パラメータは、真値 `1` を指定したときだけ応答に解析
  データを載せる。指定しなければ `data.deck.analysis` は常に null で返る。
  解析データは1デッキあたり数十〜数百 KB あるため、用いないアプリが付ける
  ものではない

### 3.3 教材本体の構造

`deck/detail` の `data.deck` から、教材として読むフィールド:

| フィールド | 型 | 内容 |
|---|---|---|
| `title` | string | デッキのタイトル |
| `image_filename` | string | デッキ画像のファイル名(§5) |
| `content` | object | 教材本体(下記)。パース済みオブジェクトとして返る |

教材ではないが、目的に応じて読んでよいフィールド:

| フィールド | 型 | 内容 |
|---|---|---|
| `analysis` | object\|null | 言語解析データ(付加データ)。手順3で `analysis=1` を指定し、かつ解析済みのデッキでのみ非 null。デッキ単位のブロブであり、`talks[]` と件数が1対1に対応しない(解析器が1発話を複数の文に分けることがある)。**内部の構造は本書のスコープ外**(本書は型を宣言しない)。用いるアプリは §3.2 手順1 の `analysis_status` 確認を経ること |
| `part_id` | string\|null | 所属パートの恒久識別子。パートを使わない教材では null。学習状態の保存単位の識別に用いる(STATUS.md §1.2) |

同じく識別のために、手順1の `data.unit` から `course_id`(string|null。
コースに帰属しないユニットでは null)を読んでよい(STATUS.md §1.2)。

`content` の構造(器としての型のみを宣言する。値の意味は教材ファミリーの
合意に従う):

```
content
├─ type        : string   … デッキ種別(ミニブック教材は "mini")
├─ extra       : string   … デッキの拡張属性。JSON文字列(§3.4)
└─ cards[]     : array    … カードの配列(教材で定めた表示順)
   ├─ title    : string   … カードのタイトル
   ├─ image    : string   … カード画像のファイル名(§5)
   ├─ extra    : string   … カードの拡張属性。JSON文字列(§3.4)
   └─ talks[]  : array    … センテンスの配列(教材で定めた順)
      ├─ person : string  … 話者ラベル
      ├─ en     : string  … 英文
      ├─ ja1    : string  … 直訳・語順訳
      ├─ ja2    : string  … 和訳(自然な訳)
      └─ audio  : string  … 音声のファイル名(§5)
```

- **記入のない列のフィールドは、キー自体が出力されない**(空文字列では
  なく欠落)。たとえば和訳を記入していない教材では `talks[]` に `ja2` は
  現れない。どのフィールドを記入するかは教材の作成側の選択であり、
  実データで確認すること(§6 指針2)

### 3.4 拡張属性(`extra`)

- `content.extra` と `cards[].extra` は **JSON 文字列**として格納されている
  (オブジェクトではない)。アプリ側で `JSON.parse` して用いる
- システムは中身を解釈せず、投稿された文字列をそのまま保持・配信する。
  **どのキーがあり何を意味するかは、教材の作成側とアプリ側の合意**であり、
  実データを吟味して確認すること(§6 指針2)
- `extra` も記入がなければキー欠落となる(§3.3 の欠落規定どおり)

## 4. 器の保証と防御規定

配信データについて、アプリは次を**前提としてよい**:

- `audio_status` / `image_status` が `done` のユニットでは、`talks[].audio` /
  `cards[].image` / `image_filename` は常に有効なファイル名で埋まり、
  メディア一括 zip(§5)の内容と一致する(「未生成」を表す空値は出現しない)
- デッキ・カード・センテンスの並び順は教材の作成側が定めた順で保存される

アプリは次を**守ること**:

- `extra` のパース結果の**未知キーは無視**する(教材側でキーは追加されうる)
- レスポンス中の**本書に列挙されていないフィールドは読み飛ばす**
  (投稿・管理系のフィールドが多数同居する)
- `data.deck.analysis` は教材本文ではない(§3.3)。用いないアプリは
  `analysis` パラメータを付けず、応答中の `analysis` キー(常に存在し、
  値は null)を読み飛ばす
- 解析データを用いるアプリは、次のいずれかに当たるとき、その教材の提供を
  中断する(解析データなしで代用して提供しない):
  - a) `data.unit.analysis_status` が `"done"` でない(§3.2 手順1)
  - b) `analysis=1` を指定して取得した `data.deck.analysis` が null
    (解析エラー等で起こりうる)

  中断の範囲(ユニット全体を止めるか、当該デッキだけ落として続けるか)は
  アプリの裁量である
- フィールドはキーの存在チェックを介して読む(存在しないキーへの直接
  アクセスで停止しない)
- `content` は本文未設定のデッキでは **null になりうる**。null チェックを
  介して読むこと

## 5. メディアの取得

- 音声・画像は `data.unit` の**一括 URL** で取得できる:
  - `audio_pack_url`: 音声ファイル一式の zip(フラット構成)
  - `image_pack_url`: 画像ファイル一式の zip(フラット構成)
  - いずれも**完全 URL がレスポンスに載る**ので、その値をそのまま用いる
    (自分で組み立てない)
- **メディアの配信オリジンは API と異なりうる**(配信基盤のドメイン。
  §2 の「同一ドメイン」規定は API アクセスについてのものであり、メディア
  URL には適用されない)。クロスオリジン取得となるため、レスポンスに
  載った URL をそのまま fetch すること
- **メディアの配信ホストは、アプリの配置オリジン(§2。API と同じ
  ドメイン)からのクロスオリジン取得を許可する CORS 設定で配信される**
  (`GET` / `HEAD`。`Access-Control-Allow-Origin` に配置オリジンが返る)。
  `fetch` で取得したバイト列は、そのまま Web Audio(`decodeAudioData`)や
  Blob URL に渡せる。個別配信への縮退経路や同一オリジン中継は不要である
- 許可されるのは配置オリジンのみ。§2 の同一ドメイン配置規約に従わない
  配置(別サブドメイン・ローカル)からは、メディアの取得はブラウザに
  拒否される
- `talks[].audio`・`cards[].image`・`deck.image_filename` の値は、その
  zip 内の**ファイル名**である。同一ファイルを複数箇所から参照する教材も
  ある(例: デッキとその配下カードが同じ画像を共用)
- zip を一括取得して展開するか、個別に解決するかはアプリの裁量。個別に
  解決する場合の配信パスは `{data.unit.user_id}/{ユニットID}/{ファイル名}`
- ユニットのカバー画像は `data.unit.cover_url`(完全 URL)
- 演出用素材(キャラクター画像・リップシンク等)は教材データに含まれない
  (アプリ側資産のまま維持する)

## 6. 自己改造の行動指針

ローカルファイル・内蔵データから教材を読んでいるアプリを、本書の API 読み込み
へ移行する際の指針。

1. **内部階層を捉え直す**。あなたのアプリが内部で表現している教材構造
   (どんな名前で呼んでいるにせよ)を、§1 の
   コース/ユニット/パート/デッキ/カード/センテンス階層への写像として
   捉え直す。どの内部概念がデッキに、どれがカードに、どれがセンテンスに
   当たるかを最初に確定させる — 以後の変換設計はすべてこの写像から導かれる
2. **実データを取得して吟味する**。写像の仮説は、実際に §3 の API で
   サンプルユニット(§7)を取得し、自アプリが現在使っている教材データと
   突き合わせて検証する。特に `extra` の中身・`person` の値・並び順など、
   本書が型しか宣言していない部分は、実データと自アプリの教材ファミリーの
   合意を照らして確認する
3. **変換層を独立に実装し、内部への影響を最小化する**。API 応答 → 内部
   形式のデータコンバーター/フィルターを**独立した境界層**として実装し、
   既存の内部モデル・表示・演出のコードには手を入れない。内部形式が今後も
   アプリの正であり、API はその供給源の一つにすぎない — 境界層より内側が
   API の形を知る必要はない
4. **読み込み経路を差し替える**。§2 の起動規約に従い、`unit_id` があれば
   API 経由(変換層を通す)、なければ従来経路、という分岐を読み込みの
   入口1箇所に置く。メディアの参照解決(§5)も同じ境界層に含める

## 7. 現物例(開発環境・実測 2026-08-17)

開発環境に投稿済みのサンプルユニットで、本書の全項目が実測確認されている。
