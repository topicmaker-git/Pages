## システム前提

本システムの管理系画面(A画面群)は、すべての団体が共通で利用できる
(各団体が自団体の範囲で管理を行う)。

ちょい英語サービスの運営会社である株式会社トピックメーカーは
システム内で唯一の特別な立場にあり、同社が主催するコースは、
学習者向けの既存B画面(B-01ホーム等のコース一覧)に掲載される
対象となる。各団体がそれぞれ主催するコースを自団体メンバー向けに
一覧表示するローカルなコース一覧(学習者向け)画面は、本設計の
スコープ外である。

トピックメーカーは団体モデルの`isトピックメーカー`属性(boolean)で
識別される(true の団体はシステム内で唯一)。

### 会員と団体の関係

- 1人の会員は最大1つの団体にのみ所属する(複数団体所属は不可)
- 団体に所属しない会員(無所属会員)も存在する
- 会員は団体に所属するかどうかに関わらず、ちょい英語アカウントを
  保持してログインできる

**団体所属 = 全アセット管理下**: 団体に所属すると、当該会員のすべての
コンテンツ資産(投稿ユニット。**所属前に作成したものを含む**)が団体の
管理下に置かれる。すなわち団体管理者の集約管理ビュー(A-U1)に表示され、
介入編集・削除(UC-28)の対象となり、団体内コースへの帰属(UC-24)も
可能となる。この点は団体招待の承諾時に被招待者へ明示する(IV-1、
ワイヤーフレーム修正仕様 §8.6)。団体に渡したくないユニットがある場合は、
参加前にデータをダウンロード(UC-23)したうえでユニットを削除するか、
別のアカウントを取得して団体に参加する。なお、外部公開ロックが有効
(≠ off)な団体では、団体からの除外時にコース非帰属ユニットも団体管理者
へ移譲される(UC-05「投稿ユニットの所有権処理」)ため、所属前に作成した
ユニットであっても持ち出せない。

### 会員アカウント(ちょい英語アカウント)との関係

本仕様書が扱うのは「**団体への所属関係**」の管理であり、ちょい英語
アカウントそのもの(認証情報、有料/無料ステータス等)の管理は
本仕様書のスコープ外である。

アカウントの属性構造(enHack 認証基盤 / ちょい英語 profile / 本サブ
システム拡張の3層)と、本体・団体コンソール間の表示・編集責務の区分は
`ユーザー属性について.md` を単一情報源とする。

- 本仕様書の「会員削除(団体からの除外)」操作は**団体所属関係の
  解消**のみを意味し、ちょい英語アカウント自体は削除されない
- ちょい英語アカウント自体の削除は、アカウント保有者本人のみが
  実行できる(本仕様書のスコープ外)
- したがって、団体管理者が他会員のちょい英語アカウントを勝手に
  削除することはない

#### ちょい英語側の退会フローに対する制約

本仕様の団体管理モデル(団体管理者が一元的に会員管理を統制する設計)
を成立させるため、ちょい英語側の退会フローに対して以下の制約を要求する:

- **団体所属中の会員は、自身のちょい英語アカウントを自己削除できない**
  - アカウントを削除したい場合は、先に団体管理者に依頼して UC-05 で
    団体から除外してもらう必要がある
  - 除外の前段として、本人が主催コースを持つ場合は、主催者移譲
    (UC-15a)またはコース削除(UC-17)の処分が完了している必要がある
    (詳細は「データ削除の連鎖規則」参照)
- **動機**:
  - 雇用・契約関係が継続している間に本人が一方的にアカウントを消すと、
    団体管理者の管理権限と矛盾する(管理経路の迂回路を作らない)
  - 主催コースの処分を待たずにアカウントを消すと、コースデータの
    整合性が破綻する
  - UC-05(本人による自発的脱退を設けない方針)と同じ理屈で、団体所属
    の「抜け方」をすべて団体管理者経由に一元化する
- **無所属会員**(団体に所属していない会員)は、ちょい英語側の退会
  フローに従って自己削除可能

### カテゴリー・サブカテゴリーの定義(グローバル統制キー)

**カテゴリー・サブカテゴリー**は、ユニット(ブック)を整理(ディレクトリ
分類)・検索するための、**ちょい英語全体にグローバルな統制キー**である。
カテゴリーが大分類、サブカテゴリーがその下位分類を表す。

例: 「試験対策 / TOEIC」「試験対策 / 英検」「日常英会話 / レストラン・
カフェ」「日常英会話 / 買い物」「ビジネス英語 / 会議・プレゼン」
(※ 例は説明用。実際の語彙はマスターに従う)

- マスター(語彙の定義・改廃)は既存ちょい英語側で管理され、本仕様書の
  スコープ外(UC-06 の `isトピックメーカー` と同様)。団体・コース・
  投稿者が独自のカテゴリを定義することはできない
- マスターはフロントエンド同梱の**静的 JSON** で定義する(改廃はフロント
  エンドのリリースで行う。マスター取得 API は設けない)。ユニットには
  選択値を **String** として保存する
- 実装上は、**カテゴリコード定義と表示ラベル辞書を分離**し、保存 String
  を安定したコードとする設計がありうる(名称変更をラベル辞書の差し替え
  のみで吸収できる)。保存 String を表示名そのものとする場合は、語彙の
  改名・削除時に既存ユニットの保存値のマイグレーションが必要になる
  (分類・検索は保存値との一致で行われるため)。方式の選択は実装側に
  委ねるが、**保存値がマスターと照合可能であり続けること**を不変条件とする
- 投稿者はユニット投稿・編集時(UC-20/21)にマスターから選択する。
  サブカテゴリーはカテゴリーに従属し、カテゴリー選択に応じて選択肢が
  絞り込まれる(「試験対策」を選ぶと「TOEIC」「英検」等が現れる)
- **フリータグとの役割分担**: カテゴリー/サブカテゴリー = システム統制
  語彙(グローバルキー)、フリータグ = 投稿者の自由語彙。学習者側の検索
  (UC-32、B-04)は両方を条件に使える

## アクター（会員のロール）

会員のロールは2つの軸で識別される。

### 軸1: 団体所属階層(投稿可否や閲覧範囲を決める)

| ロール | 説明 |
|--------|------|
| 無所属会員 | ちょい英語のアカウントを持つが、団体に所属していない会員 |
| 団体一般会員 | 団体に所属する会員。Account.団体ロール=一般 |
| 団体管理者 | 団体の登録・管理、メンバー管理を行う会員。Account.団体ロール=管理者 |
| 運営管理者 | `isトピックメーカー=true` の運営団体に所属する団体管理者。スーパーユーザー権限を持つ(下記参照) |

**運営管理者のスーパーユーザー権限**:

運営管理者は、自団体(運営団体=`isトピックメーカー=true` の団体)
の管理に加え、**他のすべての団体に対して、その団体管理者と同等の権限**
を持つ。具体的には以下の操作が可能:

- 他団体の団体情報を編集(団体名、管理部署、団体電話、外部公開ロック)
- 他団体への会員招待、会員ロール変更、会員削除
- 他団体の団体コース・団体ユニットへの介入編集・削除(UC-19, UC-28
  と同等)
- 他団体メンバーの非公開・プライベート公開・団体限定公開コンテンツ
  すべての閲覧
- 他団体の `isトピックメーカー` 属性の設定(UC-06、運用ツール経由)
- 他団体の登録・削除(団体管理者であれば自団体に対して可能な操作と同等)

運営管理者は実質的にシステム全体の最上位管理者であり、ちょい英語サー
ビスの運営者(株式会社トピックメーカー)が持つべき管理権限を表現する。

**本フェーズでの実装スコープ**:

運営管理者の他団体管理機能は、**仕様としてのみ明記**し、画面・実装は
将来フェーズで提供する。本フェーズの A 画面群は、自団体に対する管理
操作のみをサポートする。フェーズ1のドッグフーディングでは、運営団体
(株式会社トピックメーカー)の管理者は自団体に対する操作を試行すれば
十分とする。

### 軸2: コンテンツに対する関係(コースやユニットに対するふるまい)

| ロール | 説明 |
|--------|------|
| コース主催者 | コースの作成・設定・管理を行う会員。コースに対する主催関係で定義される |
| コースメンバー | コースに参加し、ユニットを投稿できる会員。コースに対するメンバー関係で定義される |
| 投稿者 | ユニットの投稿を行う会員。次のいずれか: (a) コース主催者、(b) コースメンバー、(c) コース非帰属ユニットを投稿する任意の会員 |
| 学習者 | 投稿された教材を学習する会員 |

※ 1人の会員は軸1のロールを必ず1つ持ち、軸2のロールを文脈に応じて持つ
※ 「投稿者」「学習者」は独立した属性ではなく、会員がユニット投稿または学習を行う際の関係性として現れるロール
※ アカウント管理（登録・ログイン・プロフィール編集等）は実装済のため省略

## 公開範囲の定義

コース・ユニットの公開設定は以下の4値を取る:

| 公開レベル | 意味 |
|---|---|
| 公開 | 全ユーザーに公開 |
| プライベート公開 | 公開メニュー・一覧・検索に露出しない(unlisted)。参照(リンク・お気に入り等)を持つ会員はアクセス可能。参照の再配布は本人責任で自由 |
| 団体限定公開 | 投稿者の所属団体に所属する会員のみアクセス可能 |
| 非公開 | 投稿者本人のみアクセス可能 |

> 「プライベート公開」は*発見の抑制*(unlisted)であって、URL を秘密トークンとして
> 守る方式ではない。「URLを知っている会員のみ」は「参照を持つ会員はアクセス可」の
> 略記であり、参照の形態(保存/共有リンク・お気に入り)は問わない。
> お気に入り一覧は公開インデックスではなく本人専用の一覧なので、unlisted の抑制対象
> ではない。したがってコンテンツが公開→プライベート公開に変わっても、お気に入り一覧
> での表示・アクセスは変わらない(放置でよい)。一覧で出し分け(`public_id` 抑制・
> `is_accessible:false`)が要るのは、身元ゲート(非公開・団体限定公開・外部公開ロック
> による格下げ)で本人が閲覧資格を失った場合に限る。

### 「団体限定公開」の対象団体

「団体限定公開」を選択した場合の対象団体は、**コース主催者または
ユニット投稿者の所属団体に自動的に固定される**(任意の団体を指定する
ことはできない)。

理由: 1会員は1団体にのみ所属するという制約と、コースは主催者の所属団体
内での共同作業の場として閉じる設計から、対象団体は一意に確定する。
他団体を指定する余地は構造的に存在しない。

UI 上の挙動:

- A-MC2 / A-MC3 / A-C2(コース): 対象団体は主催者の所属団体名を
  **参照表示**(セレクト不可、選択操作なし)
- A-MU2 / A-MU3(ユニット、コース非帰属時): 対象団体は投稿者の所属
  団体名を **参照表示**
- 投稿者・主催者が無所属の場合は「団体限定公開」の選択肢自体が
  表示されない(または disabled)。投稿可否マトリクスを参照

### 公開範囲を決める2系統: 属性と規則(制約)

公開範囲は、**コース・ユニットそれぞれが持つ「公開」属性**と、
**所属団体が課す「外部公開ロック」という規則(制約)**の2系統で決まる。
両者は外見上似た結果(コンテンツの見え方の制限)をもたらすが、
データ上の扱いが異なるため区別する。

| | 属性 | 規則(制約) |
|---|---|---|
| 例 | `コース.公開`、`Unit.公開` | `団体.外部公開ロック` |
| データの持ち方 | 実体が値を保持する | 設定値は持つが、適用結果の値はDBに格納しない |
| 値の確定タイミング | 変更操作時にDBに書き込み | 閲覧・配信時に動的評価 |
| 名称規則 | 「公開ステータス / 公開設定」 | 「ロック」 |

具体的な現れ方:

- **コース帰属切替時の公開値の上書き**(後述) → **属性更新**。
  Unit.公開 のDB値を実体的に書き換える(投稿者の意思を反映する変更操作)
- **コース公開設定の変更時の配下帰属ユニットへの上書き伝播**(後述) → **属性更新**。
  コース帰属ユニットの Unit.公開 をコースの新しい公開値で上書きする(非公開は不変)
- **団体の外部公開ロックによる格下げ**(後述) → **規則(制約)の適用**。
  Unit.公開 や コース.公開 のDB値は書き換えない。閲覧・配信判断時に
  動的評価される

> 規則(制約)変更時の既存コンテンツの扱い(例: `off` → `全員ロック`に
> 切り替えた時点で既に「公開」で投稿されている既存ユニット)は、
> 配信時の動的評価で自動的に格下げされる。投稿者の指定値(DB上の
> `Unit.公開`)は書き換えない。

**コース帰属ユニットの公開範囲**:
コース帰属ユニットの実効的な公開範囲は、所属コースの公開設定に従う。ユニット自身の公開設定は「公開 / 非公開」のみをUIで選択可能とし、コースの公開範囲内で当該ユニットを公開するか否かを決定する。

**コース非帰属ユニットの公開範囲**:
ユニット自身が4値すべてを選択可能。

### ユニットの公開属性のデータ保持

ユニットの`公開`属性はモデル上は常に4値enum(公開 / プライベート公開 / 団体限定公開 / 非公開)として保持する。UIでの選択可能な値はコース帰属状態に応じて2値または4値に絞られるが、DB層では常に4値のいずれかが格納される。

### コース帰属状態の変更時の公開値の扱い(属性更新)

ユニットのコース帰属状態が切り替わる際の`公開`値は、以下のルールに従う。これは**属性更新**であり、Unit.公開 のDB値が実体的に書き換えられる。

**コース非帰属 → コース帰属 への切替時**:

- ユニットの公開値が「非公開」の場合: コース側の公開値にかかわらず「非公開」のまま不変
- ユニットの公開値が「公開 / プライベート公開 / 団体限定公開」のいずれかの場合:
  - コース側の公開値と一致していれば不変
  - 不一致であればコース側の公開値でユニットの公開値を強制上書きする

具体例:

| 切替前のユニット公開値 | コースの公開値 | 切替後のユニット公開値 |
|---|---|---|
| 非公開 | (任意) | 非公開(不変) |
| 公開 | 公開 | 公開(不変) |
| 公開 | プライベート公開 | プライベート公開(上書き) |
| 公開 | 団体限定公開 | 団体限定公開(上書き) |
| プライベート公開 | 団体限定公開 | 団体限定公開(上書き) |
| 団体限定公開 | 公開 | 公開(上書き) |

上書きが発生する場合、UI側では保存前にユーザーに確認を行うことが望ましい(警告モーダル等)。

**コース帰属 → コース非帰属 への切替時**:

- DBに保持されている公開値をそのまま引き継ぐ
- UIは4値ラジオに切り替わり、現在のユニット公開値を初期選択として表示する

**新規投稿時(A-MU3)**:

- 切替前の値が存在しないため、コース帰属を選択した時点でUIは2値(公開/非公開)のみを表示し、ユーザーが選択した値を保存する

### コース公開設定の変更時の配下帰属ユニットへの伝播(属性更新)

コース主催者がコースの公開設定を変更したとき(UC-12)、その配下の**コース帰属ユニット**の `公開` 値を、コースの新しい公開値で**上書き伝播**する。これは帰属切替時の上書きと同じ**属性更新**であり、Unit.公開 のDB値を実体的に書き換える。

目的: 「ユニット単体の公開値 = 実効値」という不変条件を、帰属時だけでなくコース公開変更時にも保つため。これにより、アクセス制御の評価が(コース非帰属ユニットと同様に)ユニット単体の `公開` 値だけで完結し、読み出し時に親コースを辿る必要がない。

- ユニットの公開値が「非公開」の場合: コースの新しい公開値にかかわらず「非公開」のまま不変(オーナーが意図的に伏せたユニットは、コースの公開変更に引きずられない)
- それ以外(公開 / プライベート公開 / 団体限定公開)の場合: コースの新しい公開値で上書きする

| 変更後のコース公開値 | 配下帰属ユニットの公開値(非公開ユニットを除く) |
|---|---|
| 公開 | 公開 |
| プライベート公開 | プライベート公開 |
| 団体限定公開 | 団体限定公開 |
| 非公開 | 全帰属ユニットを非公開へ(元値を問わず。下記「コース = 非公開の別扱い」参照) |

#### コース = 非公開の別扱い(潰れと再公開)

コースを非公開にすると、配下の帰属ユニットは**元の公開値にかかわらず、すべて非公開へ
倒す**(上の3行と違い「非公開ユニットは不変」の例外は問題にならない。全ユニットが非公開に
なるため)。これは、コースを伏せても配下ユニットへの直接参照(URL)が生き残るのを防ぐ
ために必要で、「コースを非公開にした」という意図を配下まで貫徹する。

この時点で「もともと公開だったユニット」と「もともと非公開だったユニット」の区別は失われる。
元値の退避は**行わない**(公開コースを非公開へ戻すこと自体がレアな非常時オペレーションで
あり、その再公開時の利便のために常時退避状態を抱えるのは割に合わないため)。

コース = 非公開 → 公開系(公開 / プライベート公開 / 団体限定公開)への再変更時は、配下
帰属ユニットへの連鎖反映を**主催者の選択制**とする。すべて非公開に倒れている状態から戻す
ため、システムには「どれを公開へ戻すべきか」の情報が残っておらず機械的に復元できない。
判断を、それを知っている主催者に委ねる。本フェーズの選択肢は二択:

- 配下の帰属ユニットを**すべてコースの新しい公開値に合わせる**(連鎖反映する)
- 配下の帰属ユニットを**すべて非公開のまま据え置く**(連鎖反映しない。必要なユニットは
  主催者が個別に公開へ変更する)

将来拡張: 連鎖反映の対象を主催者がユニット単位で選ぶ方向に広げられる(本フェーズは
二択)。退避機構を設けないため、この拡張も「再公開時に主催者が選ぶ」線の延長で実現でき、
過去値の自動復元には依存しない。

補足:

- コース非帰属(独立)ユニットには伝播しない(コースに属さないため対象外)。
- 外部公開ロックによる格下げは別層の**規則(制約)**であり、本伝播(属性更新)で確定した Unit.公開 に対し、閲覧・配信時の動的評価として重なる(DB値は書き換えない)。
- これはコース公開変更というミューテーションが配下ユニットへ連鎖する**属性更新**なので、実装上の連鎖・トランザクションの扱いはオーケストレーション(連鎖契約)側の対象となる。

### 団体の外部公開ロック(規則(制約))

団体管理者が設定する団体ポリシー `団体.外部公開ロック : enum`
(デフォルト `off`)により、団体所属メンバーが投稿できる公開設定の
選択肢を制限し、また既に投稿されたコンテンツの実効公開範囲にも影響を
与える。これは**規則(制約)** であり、各投稿の Unit.公開 や コース.公開
のDB値は書き換えない。

**3値enum**:

| 設定値 | ロック対象 | 動機 |
|---|---|---|
| `off` | 誰もロックされない | デフォルト。秘匿要件のない団体 |
| `全員ロック` | 一般会員 + 団体管理者 | 秘匿性の高い教材を扱う団体。組織として外部公開を一律制限 |
| `一般会員のみロック` | 一般会員のみ(管理者除外) | 一般会員の誤投稿を防ぎつつ、団体管理者は広報的な教材を外部公開できる運用 |

**動機**:

- 秘匿性の高い教材を団体外に出さないようにする(秘密保持)
- 加えて、団体内向け教材とは別に**外部向けの広報的な教材**を団体管理者が直接作成・外部公開する運用に対応(`一般会員のみロック`)

**ロック対象判定**:

外部公開ロック設定と投稿者の団体ロールの組み合わせで、当該投稿者が
「ロック対象」になるかが決まる。

| 外部公開ロック | 一般会員 | 団体管理者 |
|---|---|---|
| `off` | 対象でない | 対象でない |
| `全員ロック` | 対象 | 対象 |
| `一般会員のみロック` | 対象 | 対象でない |

**対象範囲**: コースおよびユニット(コース非帰属ユニットの場合)。
コース帰属ユニットは所属コースの公開設定に従うため、コース側でロックが
効いていれば自動的にユニットも影響を受ける。

#### 投稿可否への影響(新規投稿・編集時)

ロック対象の投稿者には、UI 上で「公開」「プライベート公開」を選択肢
から **非表示または disabled** にする。ロック対象でない投稿者は4値
すべてを選択可能。

| 公開設定 | ロック対象でない | ロック対象である |
|---|---|---|
| 公開 | ○ | × (UI で選択不可) |
| プライベート公開 | ○ | × (UI で選択不可) |
| 団体限定公開 | ○ | ○ |
| 非公開 | ○ | ○ |

この方式により、ロック適用下では「公開」「プライベート公開」で投稿
されること自体を構造的に防ぐ(投稿側で弾く)。

UI 上の表示例(ロック対象の投稿者向け):

> あなたの所属団体「XX」は外部公開ロックが有効です(全員ロック)。
> このため「公開」「プライベート公開」は選択できません。「団体限定
> 公開」または「非公開」で投稿してください。

> あなたの所属団体「XX」は外部公開ロックが有効です(一般会員のみ
> ロック)。一般会員は「公開」「プライベート公開」を選択できません。
> 団体外への公開が必要な場合は団体管理者にご相談ください。

無所属会員(団体に所属しない会員)はそもそも外部公開ロックの影響を
受けない。ただし「団体限定公開」は対象団体が存在しないため選択不可
(構造的制約。「公開範囲の定義 / 『団体限定公開』の対象団体」参照)。

#### ロックをかけた場合の既存投稿の閲覧範囲の変化

団体管理者が外部公開ロックを `off → 全員ロック`(または `off → 一般
会員のみロック`)に切り替えた場合、それ以前に投稿された既存コンテンツ
への影響:

- 投稿者の指定値(Unit.公開、コース.公開)の **DB値はそのまま維持される**
  (ロックは規則(制約)なので属性を書き換えない)
- **閲覧・配信時に動的に格下げ評価される**:

  | 投稿者の指定値 | ロック対象でない投稿者 | ロック対象になった投稿者 |
  |---|---|---|
  | 公開 | 公開(変化なし) | **団体限定公開**(格下げ) |
  | プライベート公開 | プライベート公開(変化なし) | **団体限定公開**(格下げ) |
  | 団体限定公開 | 団体限定公開(変化なし) | 団体限定公開(変化なし) |
  | 非公開 | 非公開(変化なし) | 非公開(変化なし) |

- ロックを `off` に戻せば、DB値は維持されているため実効公開範囲は
  自動的に元に戻る(投稿者の指定値そのままで閲覧できるようになる)

これは「ロックをかけた瞬間に外に出ていたコンテンツを取り戻す」という
規則(制約)の動機を実現するための動的評価である。投稿者にどう通知
するか、管理画面でどう可視化するかなどの UX 詳細は別途検討
(ディスカッション参照)。

> ただし `一般会員のみロック` への切替は、管理者主催で実効的に外部公開される
> コース(公開 / プライベート公開。一般会員主催は格下げで対象外)に一般会員が
> 投稿したユニットを含む場合はリジェクトされる(混在を入口で禁じる不変条件。
> 次節「『一般会員のみロック』下のコース構成の不変条件」を参照)。本節の動的
> 格下げ評価が適用されるのは、リジェクトされず成立したロック下の既存コンテンツ
> (`全員ロック` 全般、および `一般会員のみロック` で割れを生じない構成)
> に限る。

#### 「一般会員のみロック」下のコース構成の不変条件

外部から閲覧可能なコース内で「見える配下 / 見えない配下」の混在が生じる
唯一の機構は `一般会員のみロック` である(投稿者のロールで実効公開範囲が
割れるため。`全員ロック` は均一格下げで割れない)。この混在を読み出し側で
吸収する(コメント集約のマスク行・viewer 依存)のではなく、混在の発生自体
を入口で禁じる**不変条件**を1本置く。

> **不変条件**: `一般会員のみロック` が有効な団体では、**実効的に外部公開
> されるコース(= 管理者が主催する公開 / プライベート公開コース。一般会員
> 主催のコースはロックで団体限定に格下げされ外部公開されないため対象外)**
> に、一般会員が投稿したユニットを含めてはならない。

この不変条件は外部公開ロックと同じ**規則(制約)** であり、コース帰属
ユニットの公開設定(公開 / 非公開の2値)からは混在が生じないこと、団体限定
公開コースは部外者が到達しないことから、対象は上記の組み合わせに限られる。

**チェックは1つ、適用箇所は複数**。条件を破りうる経路は次の3つで、いずれも
同じ不変条件への違反として一様にリジェクトする(エラー)。

1. **ロック変更**(UC-02): `off` / `全員ロック` → `一般会員のみロック` への
   切替時、管理者主催で実効的に外部公開されるコース(公開 / プライベート公開)
   に一般会員投稿ユニットが含まれていればロックをかけさせず、先に整理(該当
   ユニットの非公開化・コース除外・コース非公開化のいずれか)を促す。
2. **ロック下の投稿・コース帰属**(UC-20): `一般会員のみロック` 下で、一般
   会員が管理者主催で実効的に外部公開されるコース(公開 / プライベート公開)へ
   ユニットを投稿・帰属しようとした時にリジェクトする(一般会員主催のコースは
   格下げで外部公開されないため対象外)。コース帰属ユニットの公開値はコースに
   追従するため、単体投稿の公開選択肢の非表示(「投稿可否への影響」)では
   捕捉できない経路であり、本不変条件で塞ぐ。
3. **コース公開化**(UC-12): 管理者主催の一般会員投稿ユニットを含むコースを
   公開 / プライベート公開へ変更しようとした時にリジェクトする(コース公開
   変更の配下帰属ユニットへの伝播の前段でチェック。一般会員主催コースは格下げ
   で外部公開されないため対象外)。

**効果**: 閲覧できるコースは常に all-or-nothing になり、コース内の割れが
構造的に消える。これにより学習者側のコメント集約一覧(UC-45)はマスク行・
viewer 依存(本文の可読性判定)を持たず、host に到達できる閲覧者にとって
配下の非公開除外コメントはすべて可読になる。代償はレアな書き込み時の1
チェックとエラー表示のみで、お気に入り一覧(UC-42)の身元ゲートによる
アクセス不可表示は本不変条件の対象外(別機構)として据え置く。

### お気に入り・コメント数の集約範囲

お気に入り数・コメント数は、コンテンツの「賑わい(価値)」を示すメトリクスで
あり、各コンテンツ詳細画面(A-MC2 / A-C2 / A-MU2 / A-U2)のヘッダに表示する
(お気に入り数は表示専用、コメント数はコメント一覧画面 A-CMT への遷移リンク)。
本節はその**集計範囲**の単一情報源である。

**集計軸(価値メトリクス)**: 算入可否は閲覧者に依らず、コンテンツ自身が
「非公開」か否かだけで決まる。

- 算入する: 公開 / プライベート公開 / 団体限定公開(外部公開ロックで org に
  格下げされた配下も「非公開」ではないので算入)
- 除外する: 非公開(主催者 / 投稿者本人のみ)の配下

閲覧者非依存であり、閲覧者ごとに評価し直す必要はない。これは「誰に見えるか」
を判定する visibility 評価(=お気に入り一覧 UC-42 の表示可否・対象詳細への
遷移時のフェイルセーフに効く動的評価)とは**別軸**なので混同しないこと。

**配下レベル別の集約**(作成者の分析用。どの層が賑わっているかを見るため、
配下を種別ごとに分けて集約する):

- コース系(A-MC2 / A-C2): 直接 / ユニット集約 / パート集約 / デッキ集約 の4値
- ユニット系(A-MU2 / A-U2): 直接 / パート集約 / デッキ集約 の3値
- 保存は各レベルのまま、読み出し側で配下を種別ごとに巻き取る。重複名寄せは
  しない(各種別とも延べ数)

**お気に入り数とコメント数は同一の集計軸**を用いる。コメント数は非公開を除いた
集約総数であり、学習者側のコメント集約一覧(UC-45)は「『一般会員のみロック』
下のコース構成の不変条件」により host 到達者には全可読で返るため、**一覧行数=
コメント数が一致**する(非公開配下のみ行ごと除外)。実装は配下種別ごとの集約数を
返す想定(佐藤さんへの API 依頼として伝達済み。経緯は申し送りの git 履歴)。

## 教材階層のIDの二系統(公開ID と 編集ID)

教材階層(パート/デッキ/カード/センテンス)の各要素は、目的の異なる
2系統のIDを持つ。実装時のID設計と、投稿データ(エクセル)更新フロー
の理解のために、両者を区別する。

### 公開ID (Public ID)

- **目的**: URL用、外部公開される識別子
- **保持する階層**: パート、デッキ
- **用途**: 学習者向けB画面でURLパスとして使用される
  (例: `/decks/{デッキ公開ID}` のような形)
- カード、センテンスは公開IDを持たない(外部からの個別参照を想定しないため)

### 編集ID (Editing ID)

- **目的**: 投稿データ(エクセル)の行同定用、内部のみで使用
- **保持する階層**: パート、デッキ、カード、センテンス(全階層)
- **用途**: 投稿データ更新(UC-22)時の create / update 判定に用いる
  - エクセルにダウンロード時、各行に編集IDが付与される
  - アップロード時、編集IDが空欄の行は新規作成、入っている行は更新と判定
- 詳細(エクセル列構成、記入ルール)は `投稿データ_メディアパック仕様.md`
  を参照

### 投稿者にとっての扱い

- 初回投稿時はすべて空欄でよい(システムが投稿成功時に発行)
- 更新時は、UC-23 でダウンロードしたエクセルを編集してアップロードする
- 投稿者向けガイド: 「**編集ID列は触らないでください**」と
  ヘルプテキストおよびエクセル列ヘッダのコメントで案内

## 権限モデル(編集・操作の権限)

コンテンツに対する**編集・操作の権限**(投稿者ドメイン)を、アクター×操作で一元的に定義する。本節が権限の単一情報源であり、各UCはここを参照する。

**原則**: **主催者はコース資産(帰属ユニットとその配下)のオーナーであり、帰属ユニットを投稿者を問わず編集・削除・表示順変更できる。コースメンバー(共同編集者)は、主催者がこの編集権を招待により分与した会員であり、同じ範囲を連帯責任で行える。** コース自体の設定・メンバー管理・主催者移譲・コース削除・コース表示順は**主催者の専権**(＋団体管理者の介入)。

**別軸の注意**: ここは「誰が編集・操作できるか」=投稿者ドメインの話である。「誰にコンテンツが見えるか」=学習者ドメインの閲覧可否は、公開設定・所属団体・外部公開ロックのみで決まり(公開範囲の定義参照)、本表とは無関係。コースメンバーであることは閲覧可否に一切干渉しない。

| 操作 | 投稿者本人 | コースメンバー | 主催者 | 団体管理者 |
|---|---|---|---|---|
| ユニット新規投稿・コース帰属 (UC-20/24) | ○ | 投稿者制限=メンバーなら○ | ○ | ○(介入) |
| コース帰属ユニットの編集 (UC-21/22) | ○ | ○ | ○ | ○(UC-28) |
| コース帰属ユニットの削除 (UC-26) | ○ | ○(連帯責任) | ○ | ○(UC-28) |
| コース帰属ユニットの表示順=コース内 (UC-25) | ○ | ○ | ○ | ○(UC-28) |
| コース設定(公開/制約/投稿者制限 UC-12/13/14) | — | — | ○ | ○(UC-19) |
| コースメンバー管理 (UC-15) | — | — | ○ | ○ |
| 主催者移譲 (UC-15a) | — | — | ○ | ○ |
| コース表示順=団体スコープ (UC-16) | — | — | ○ | ○(A-C1 介入) |
| コース削除 (UC-17) | — | — | ○ | ○(UC-19) |
| コメントのモデレーション削除 (UC-46) | ○(自コンテンツ配下) | ○(コース帰属分・連帯責任) | ○(コース資産全体) | ○(介入) |
| 投稿データ・メディアの DL (UC-23) | ○ | ○(コース帰属分・連帯責任) | ○(コース資産全体) | ○(UC-28) |

**非帰属(standalone)ユニットの非対称**: コースに属さないユニットは共同作業の資産ではないため、**共同編集の対象外**。その編集・削除・表示順は**投稿者本人＋団体管理者のみ**(コースメンバーの列は適用されない)。上表の「コース帰属ユニットの…」行は、コースに帰属したユニットについての権限である。

**コース表示順・コース削除の主催者専権**: ユニット(コースの資産)は連帯責任で共同編集できるが、コース自体の位置(団体ポータルでの表示順)・存廃(削除)は主宰事項として主催者専権とする(団体管理者は介入可)。

**コメントのモデレーション削除 (UC-46) の位置づけ**(2026-07-30 確定): コメントのモデレーションは、コースの構造・存廃(主催者専権)ではなく**コース資産の衛生管理**であり、共同編集の範囲に含まれる。したがって**コース対象そのものに付いたコメントを含め**、主催者・コースメンバーが連帯責任で削除できる(団体管理者は介入)。非帰属(standalone)ユニットのコメントは共同編集の対象外で、投稿者本人+団体管理者のみ。画面仕様と経緯はワイヤーフレーム修正仕様 §12.5 / §12.7。

## 表示順の操作と導線

表示順を「誰が・どのように・どの画面遷移で」操作するかの単一情報源。スコープ・数値ルール・活性条件の詳細は UC-16 / UC-25、権限は「権限モデル」節を参照。

**共通原則**:
- 表示順は**学習者画面での並び順**であり、アクターに紐づかない。`コース.表示順`=団体スコープ、`ユニット.表示順`=コーススコープ(ユニットは高々1コース)。
- **数値の指定は詳細編集画面のみ**。一覧は数値を表示するだけで、数値入力欄は置かない。
- **一覧の行内上下ボタンは、その一覧の構成範囲が表示順の正規スコープと一致するときだけ**成立する(相対入れ替えが絶対順と一致するため)。ソート(基準切替)はどの一覧にも置かない。
- 数値は飛び飛び可・重複可・一意性チェックなし。主催者/メンバー間の調整はシステム外、最終調整は管理者が介入可。

| | コースの表示順(スコープ=団体) | ユニットの表示順(スコープ=コース) |
|---|---|---|
| **誰が** | コース主催者本人＋団体管理者(介入)。コースメンバー不可(主催者専権) | 投稿者本人＋そのコースの主催者＋当該コースのコースメンバー(共同編集者・連帯責任)＋団体管理者(介入)。非帰属ユニットは投稿者本人＋管理者のみ |
| **どのように(数値)** | 詳細編集画面 A-MC2(主催者)/ A-C2(管理者介入)で数値入力 | 詳細編集画面 A-MU2 / A-U2(管理者介入)で数値入力 |
| **どのように(上下)** | **A-C1 団体コース一覧**の行内上下(団体の全コースが表示順で並ぶ=正規スコープ一致) | 帰属コースで絞り込み**単一コースの配下ユニットだけが並んだとき**の行内上下(A-MU1=投稿者本人・主催者・コースメンバー / A-U1=団体管理者の介入。活性は絞り込み状態で決まり画面非依存) |
| **どの画面遷移で** | 団体ダッシュボード → A-C1(上下)/ A-MC2・A-C2(数値)。A-MC1 マイコース一覧は数値を表示するのみ(操作なし) | コース詳細から帰属ユニット一覧へ遷移すると**当該コース絞り込みがデフォルト適用**され、その塊内で上下: 主催者・コースメンバーは A-MC2 → A-MU1、団体管理者は A-C2 → A-U1。数値は A-MU2・A-U2。上下の活性は絞り込み状態で決まり(画面非依存)、非絞り込み・コース以外の絞り込み時は非活性(表示のみ) |

**なぜコースとユニットで導線が違うか**(佐藤さん指摘の回収): コースの表示順スコープは団体なので、全コースが並ぶ A-C1 で上下が成立する。ユニットの表示順スコープはコースなので、上下が成立するのは**単一コースに絞り込まれているとき**に限る。この活性条件は画面ではなく**絞り込み状態**で決まるので、A-MU1(投稿者本人＋主催者＋コースメンバー)でも A-U1(団体管理者の介入)でも、単一コースに絞り込めば上下は活性になる(両者は対称で、操作主体が権限モデルで異なるだけ)。逆に非絞り込みの横断表示やコース以外の絞り込みでは、大小関係が定義できず部分集合の移動で歯抜けが出るため非活性とする。

## ユースケース一覧

### 1. 団体管理（団体管理者）
- UC-01: 団体を登録する
  - 前提: ちょい英語のアカウントでログイン済みの会員が実行
  - 前提: 実行会員は団体未所属であること(1会員は1団体のみ所属)
  - 事後条件: 登録された団体が作成され、実行会員がその団体の
    デフォルト管理者となる(Account.団体ロール=管理者)
  - 管理者権限は後でUC-04により変更可能(招待した他の会員を
    管理者にすることもできる)
- UC-02: 団体情報を編集する（団体名、管理部署、電話、外部公開ロック）
  - 外部公開ロックは 3値 enum 属性 (`off` / `全員ロック` /
    `一般会員のみロック`) で、`off` 以外にすると当該団体メンバーの
    投稿の実効公開状態が「団体限定公開」を上限に制限される
  - 詳細は「公開範囲の定義」セクション「団体の外部公開ロック」を参照
  - `一般会員のみロック` への切替は、管理者主催で実効的に外部公開されるコース
    (公開 / プライベート公開。一般会員主催は格下げで対象外)に一般会員
    投稿ユニットが含まれる場合はエラーで拒否する(混在を入口で禁じる不変条件。
    詳細は「公開範囲の定義」セクション「『一般会員のみロック』下のコース構成
    の不変条件」を参照)
- UC-03: 会員を招待・追加する
  - 招待対象は団体未所属の会員のみ(1会員は1団体のみ所属の
    制約による)
- UC-04: 会員のロールを変更する（管理者 / 一般）
  - **最後の管理者制約**: 自分自身を一般に降格しようとして、結果として
    団体管理者が0人になる場合はエラー。先に他会員を管理者に
    昇格させる必要がある(下記 UC-05 と同じ制約)
- UC-05: 会員を団体から削除する(団体からの追い出し)
  - **本UCの意味**: 団体所属関係の強制解消。Account.所属団体 を null
    にする操作であり、ちょい英語アカウント自体は削除されない
    (詳細は「会員アカウント(ちょい英語アカウント)との関係」参照)
  - 主アクター: 団体管理者
  - 効果:
    - 対象会員の Account.所属団体 を null にする(無所属化)
    - 対象会員が他のコースのコースメンバーであった場合、その関係も解消
      (主催者と同じ団体にいなくなるため)
    - **対象会員が投稿したユニットの所有権を、種別に応じて処理する**
      (下記「投稿ユニットの所有権処理」参照)
  - **制約**:
    - 対象会員が団体管理者で、かつ削除すると管理者0人になる場合はエラー
      (先に他会員を管理者に昇格、または UC-04 でロール変更)
    - 対象会員が主催コースを持つ場合は、**事前に主催者移譲(UC-15a)
      またはコース削除(UC-17)が完了している必要がある**
      (団体管理者は介入編集権限の延長として代理で移譲・削除操作を
      行うことができる)。この制約により、団体未所属になった会員が
      コースを保持し続けることはない
  - **投稿ユニットの所有権処理**:
    対象会員が投稿したユニットは、種別および団体の外部公開ロック設定に
    応じて以下のように処理する。動機: コースは団体内の共有物であること、
    および外部公開ロック適用下では団体所属中に作成したコンテンツの
    持ち出しを禁止すること。

    | 条件 | コース帰属ユニット | コース非帰属ユニット |
    |---|---|---|
    | 外部公開ロック ≠ off | 当該コースの**主催者**へ所有権移譲 | **団体管理者(指定)**へ所有権移譲 |
    | 外部公開ロック = off | 当該コースの**主催者**へ所有権移譲 | 除外者のアカウントに**残る** |

    - 「コース帰属ユニットの主催者」は、除外実行時点での当該コースの
      主催者を指す(除外対象が主催者のコースは事前条件で排除済みなので、
      除外対象 ≠ 主催者)
    - 外部公開ロック ≠ off の場合の「団体管理者(指定)」は、UC-05 実行
      時に指定する。団体管理者が1人しかいない場合はその人にデフォルト
      で決まる。複数いる場合は UI で指定させる
    - 所有権移譲の効果: Account → Unit [投稿] の関連を付け替え、新所有者
      の「マイユニット」一覧に表示される。所有権移譲されたユニットの
      コース帰属関係(Unit が属する コース)は維持される
    - 公開設定の値は所有権移譲によって変化しない(規則による格下げの
      評価は新所有者の所属団体・ロールで再計算される)
  - 補足: 対象会員のユニットのデータについて、上記表で「除外者の
    アカウントに残る」となるもの以外は所有権が移譲されるため、除外者の
    マイユニットには含まれなくなる。詳細は本セクション末尾「データ削除
    の連鎖規則」参照

> **本仕様には「本人による自発的な団体脱退」のユースケースは設けない。**
> 団体への加入(UC-03)・ロール変更(UC-04)・除外(UC-05)はすべて団体
> 管理者が主導する設計であり、一般会員が一方的に団体から抜ける操作は
> この管理モデルと整合しない(実運用でも、雇用・契約関係の解消は組織側
> の手続きが起点になる)。会員側で団体を抜けたい意図がある場合は、
> 団体管理者に依頼して UC-05 を実行してもらう。

### 2. コース管理（コース主催者）
- UC-10: コースを作成する
  - 前提: 実行会員は団体所属であること
  - 無所属会員はコースを作成できない(コースは主催者の所属団体内での
    共同作業の場として閉じる設計のため)
- UC-11: コース情報を編集する(コース名、紹介、紹介ビデオ)
- UC-12: コースの公開設定を変更する(公開 / プライベート公開 / 団体限定公開 / 非公開)
  - 「団体限定公開」選択時の対象団体は **主催者の所属団体に自動的に
    固定される**(主催者は団体所属を前提とし、主催者は1団体にのみ
    所属するため)。UI 上は対象団体を表示するが、選択操作は不可
    (参照表示のみ)
  - 主催者の所属団体の `外部公開ロック` の設定値と主催者のロールにより
    実効公開状態が決まる(詳細は「公開範囲の定義」セクション参照):
    - `off`: 主催者の指定値そのまま
    - `全員ロック`: 主催者(管理者を含む)が「公開」「プライベート公開」を
       選択しても「団体限定公開」相当に格下げされる
    - `一般会員のみロック`: 一般会員が主催者の場合のみ格下げ。管理者は
       格下げなし(広報的なコース公開の運用を想定)
  - UI 上は格下げが発生する選択時に inline 警告を表示する
  - コースの公開設定を変更すると、配下の**コース帰属ユニット**の `公開` 値が新しいコース値で**上書き伝播**される(公開系の場合。非公開ユニットは不変)。コースを**非公開**にした場合は配下帰属ユニットを元値問わず全て非公開へ倒し、非公開→公開系への再変更時は連鎖反映の有無を主催者の選択制(全追従 / 全据え置きの二択)とする。詳細は「公開範囲の定義 / コース公開設定の変更時の配下帰属ユニットへの伝播」セクション参照
  - 主催者の所属団体が `一般会員のみロック` の場合、管理者が主催する一般会員
    投稿ユニットを含むコースを公開 / プライベート公開へ変更しようとするとエラーで
    拒否する(一般会員主催コースは格下げで外部公開されないため対象外。伝播の
    前段でチェック。混在を入口で禁じる不変条件。詳細は「公開範囲の定義」セクション
    「『一般会員のみロック』下のコース構成の不変条件」を参照)
- UC-13: 投稿者制限を設定する(主催者のみ / メンバー)
  - 「主催者のみ」: コースの主催者のみが投稿可能
  - 「メンバー」: 主催者 + コースメンバーが投稿可能
  - 「メンバー以外も投稿可」のオプションは設けない(コースは主催者の
    所属団体内での共同作業の場として閉じる設計のため)
- UC-14: コースの制約値(最大ユニット数、最大デッキ数、デッキ内最大カード数)を参照する
  - 本項目はコース主催者が設定するものではなく、システムが
    コースの所属文脈(団体への帰属、isトピックメーカーか、
    将来的には課金プランや法人契約等)に応じて自動的に設定する
  - コース作成時にシステムが値を決定してコース属性にセットし、
    以降は変更不可(モデル属性としては保持、UIでは情報提示のみ)
  - コース主催者・団体管理者はこの値を画面上で**参照**できる
- UC-15: コースにメンバーを招待する
  - **招待対象は主催者と同じ団体に所属する会員のみ**
  - 他団体所属者・無所属会員は招待不可
  - 団体管理者の介入編集権限としても、この制約は外れない
  - 詳細フローは `招待フロー_コース.md` 参照
- UC-15a: コース主催者を他会員に移譲する(本フェーズで新規実装)
  - 主アクター: 現主催者本人 / または団体管理者(介入編集権限による代理実行)
  - 効果: コースの主催関係(Account → コース [主催])を新主催者に
    付け替える
  - **既存コースメンバー関係は維持**される。コースメンバー関係は主催者個人ではなく
    コースに帰属する(概念モデル `コース o-- Account : メンバー`)ため、主催者が交代しても
    分与済みの共同編集権はそのまま継続する(再設定不要)。新主催者が原資となる
  - **制約**: 移譲先は主催者と同じ団体に所属する会員のみ
    (主催者の団体所属制約を維持)
  - **発火タイミング**:
    - 現主催者が団体から削除(UC-05)される際の前提条件の一つ。
      削除前に、主催コースについて主催者移譲(本UC)またはコース削除
      (UC-17)のいずれかが完了している必要がある
    - 通常時にも実行可能(主催者を交代する運用)
  - UI: A-MC2(主催者本人)、A-C2(団体管理者の介入編集)に
    「主催者を移譲」操作を配置
- UC-15b: コースメンバーとして共同編集する(本フェーズで新規定義)
  - 主アクター: コースメンバー(共同編集者)
  - 効果: コースメンバーは、**主催者から招待により編集権を分与された共同編集者**として、当該コースの**帰属ユニット(投稿者を問わず)**に対し、主催者と同じ範囲を**連帯責任**で行える:
    ユニット編集(UC-21/22)・投稿/帰属(UC-20/24、投稿者制限に従う)・
    表示順変更(UC-25、コース内スコープ)・**削除(UC-26)**。
    削除を含むのは「共同=連帯責任」で作業を分散するため
  - 範囲外(主催者の専権): コース自体の設定(UC-12/13/14)、メンバー管理
    (UC-15)、主催者移譲(UC-15a)、コース表示順(UC-16)、コース削除(UC-17)
  - 非帰属(standalone)ユニットは共同編集の対象外(投稿者本人＋団体管理者のみ)
  - 別軸の注意: 本UCは編集権限(投稿者ドメイン)であり、閲覧可否(学習者
    ドメイン=公開設定・所属団体・外部公開ロック)には干渉しない
  - 権限の一覧は「権限モデル」節を参照。UC-21/22/24/25/26 の主語は本UCを含む
- UC-16: コースの表示順を変更する
  - 主アクター: コース主催者本人 / 団体管理者(介入。A-C1)。主催者専権(コースメンバー不可)
  - **スコープ=団体**: `コース.表示順` は団体の学習者向けコース一覧(団体ポータル)での並び順。団体内グローバルな数値
  - 数値は**飛び飛び可・重複可・一意性チェックなし**。主催者間の並びの調整はシステム外(相談)で行い、各主催者が自コースに値を入れる。最終調整は団体管理者が A-C1 で行える(Q2=b の介入)
  - 編集入口: **数値指定は詳細編集画面のみ**(A-MC2 主催者 / A-C2 管理者介入)。マイコース一覧(A-MC1)は自コースの数値を**表示**(読み取り専用)し数値順に並ぶ(=団体順の部分列)が、数値入力欄は置かない。**行内上下ボタンによる並べ替えは、団体の全コースが表示順順に並ぶ A-C1(団体コース一覧)でのみ**成立(正規スコープ全体が並ぶため)。A-MC1 には上下ボタンも置かない
  - 誰が・どのように・どの画面遷移での操作かの一覧は「表示順の操作と導線」節を参照
- UC-17: コースを削除する
  - 主アクター: コース主催者本人 / 団体管理者(UC-19)。**主催者専権**(コースメンバー不可)
  - **連鎖削除の挙動**:
    - 当該コースに帰属するユニット → **連鎖削除**
    - 連鎖削除されるユニットの音声・画像メディア → S3 から削除
    - コースメンバー関係 → 削除(関係レコードのみ。会員アカウントは残る)
    - 当該コースおよび配下のユニット・パート・デッキを対象とする
      お気に入り・コメント → 削除
  - 削除前の確認モーダルで配下件数(ユニットN件、メンバーM件等)を
    強く警告する

### 3. ユニット投稿（投稿者）

ユニット投稿には、エクセル(教材データ)・音声パック(zip)・画像パック(zip)
の3種のファイルが関わる。エクセルは14列構成(編集ID 4列 + 表示用10列)
で、詳細は `投稿データ_メディアパック仕様.md` を参照。

**投稿フローの基本方針**: 「**本登録 → 自動生成 → A-MU2 でレビュー(必要なら修正)**」

A-MU3 では教材データとユニット定義を入力し、「投稿する」(または
「下書き保存」)で本登録する。本登録の直後、サーバー側で TTS / AI画像
の自動生成が非同期で開始される。完成したコンテンツは A-MU2 上で
レビューでき、必要なら修正できる。

このフローの主眼は、**サーバー側生成処理を伴うコンテンツでは登録前
プレビューが原理的に成立しないこと**である(生成物がまだ存在しない
ため)。したがって A-MU3 から登録前のプレビュー画面は廃止し、
本登録後のコンテンツ確認は A-MU2 が担う。

公開設定は A-MU3 / A-MU2 のいずれでも設定・変更でき、A-MU3 投稿時の
「下書き保存」は公開設定を「非公開」固定にする利便機能として
従来通り残る。

詳細は UC-20 / UC-21 を参照。

- UC-20: ユニットを新規作成・投稿する
    - ユニット定義（ユニット名、紹介、カテゴリー、サブカテゴリー、フリータグ、画像、公開設定、料金設定）
    - エクセルファイルのアップロード(14列構成、`投稿データ_メディアパック仕様.md` 参照)
    - **メディア供給モードの選択**(音声・画像それぞれ独立に、排他選択):
      - メディアパックモード: 該当 zip をアップロード
      - 自動生成モード: TTS / AI画像で生成(zipアップロードなし)
    - エクセルとzipの不整合(モード不一致、参照されているファイルがzipに
      ない、余剰ファイル等)はエラーとして投稿を拒否する
    - 一般会員が `一般会員のみロック` 下で、管理者主催で実効的に外部公開される
      コース(公開 / プライベート公開。一般会員主催は格下げで対象外)へ
      ユニットを投稿・帰属しようとした場合はエラーで拒否する(コース帰属
      ユニットの公開値はコースに追従し、単体投稿の公開選択肢非表示では
      捕捉できない経路のため。混在を入口で禁じる不変条件。詳細は「公開範囲
      の定義」セクション「『一般会員のみロック』下のコース構成の不変条件」
      を参照)
    - **登録前プレビュー画面は提供しない**(生成処理が完了するまで
      コンテンツ全体は確定しないため)
    - 投稿時の挙動:
      1. 投稿者が「投稿する」(または「下書き保存」)ボタンを押下
      2. システムがバリデーション(エクセル/zip整合性、モード一貫性、
         スキーマ制約)を実行
      3. ユニットIDを発行、DBに保存
         - 「投稿する」: 投稿者が選択した公開設定で本登録
         - 「下書き保存」: 公開設定を「非公開」固定で本登録
      4. メディア供給モードに応じた処理:
         - メディアパックモード: zip を S3 `packs/` に保存 + 展開
         - 自動生成モード: TTS / AI画像生成ジョブを非同期投入
      5. A-MU2 編集画面に遷移
    - 自動生成の完了は A-MU2 上で表示される(進捗表示、完了通知)
- UC-21: ユニット情報を編集する
    - 主アクター: 投稿者本人。コース帰属ユニットは、そのコースの**主催者**＋当該コースのコースメンバー(共同編集者、UC-15b)も可(主催者が原資、コースメンバーはその分与)。団体管理者は介入可(UC-28)。非帰属(standalone)ユニットは投稿者本人＋団体管理者のみ(コースがないため主催者・コースメンバーの列は適用されない)。詳細は「権限モデル」節
    - ユニット定義(名称、紹介、カテゴリ等)、コース帰属、公開設定、
      料金等を編集する
    - 自動生成された音声・画像のレビュー、必要に応じた差し替え(UC-22)
      もここで行う
    - 公開設定の変更も通常の編集の一環として可能
      (例: 投稿時「非公開」で本登録した下書きを、レビュー後に「公開」
      に切り替える、など)
    - コース非帰属時は4値、コース帰属時は2値(公開/非公開)を選択可能
- UC-22: 投稿データを更新する（差分処理）
    - 主アクター: UC-21 と同じ(投稿者本人 / コース帰属ユニットは主催者＋当該コースのコースメンバー / 団体管理者。非帰属は本人＋管理者。権限モデル節参照)

    - エクセルファイル自体のバージョン管理は行わない
    - **メディアパック(音声zip / 画像zip)は一括差し替え方式**
      (個別ファイル単位の差分処理は行わない)
    - **メディア供給モードの切替も可能**: A-MU2 上で音声・画像のモードを
      自動生成 ↔ メディアパック の間で切り替えられる。切替時は既存
      メディアを全削除して新モードに置き換える(投稿データ・メディア
      パック仕様書 §3.5 参照)
    - 差分処理(create/update/ignore の判定、編集IDによる行同定、S3操作、
      モード切替時の挙動)の詳細は `投稿データ_メディアパック仕様.md` 参照
- UC-23: 投稿データをダウンロードする

## データ削除の連鎖規則

各エンティティが削除された場合の連鎖の挙動を整理する。本フェーズでは
本仕様書のスコープ内(団体所属関係およびそれに紐づくコース・ユニット
等のデータ)のみを扱い、ちょい英語アカウント自体の削除は対象外。

> 削除の**実行主体**(誰が削除できるか)は本節ではなく「権限モデル」節で定義する。特に**コース帰属ユニットの削除は、投稿者本人だけでなく当該コースのコースメンバー(共同編集者)も実行できる**(連帯責任。UC-15b/UC-26)。実行主体がコースメンバーであっても、以下の連鎖の挙動は同一。

### 団体が削除された場合

団体削除UCは本フェーズでは UI 提供せず、運用操作扱いとする(運営管理者
の UC-65 として将来実装予定)。挙動の仕様は以下:

- **会員** → 無所属化(Account.所属団体 を null にする。アカウント自体は残る)
- **団体所有コース**(団体所属メンバーが主催するコース) → 削除
  - 削除されるコースの**コース帰属ユニット** → 連鎖削除
  - 連鎖削除されるユニットのメディアファイル → S3 から削除
- **コース非帰属の個人ユニット** → 削除されない(会員のアカウントに残る)
  - ただし、**公開設定が「団体限定公開」のユニットは「非公開」に
    切り替える**(参照先団体が消滅するため、団体限定公開という公開設定
    が意味を失う。安全側に倒して非公開にする)
  - 「公開」「プライベート公開」「非公開」のユニットは公開設定を維持

事前にユーザーは UC-23 等で投稿データを退避できる(退避はユーザー責任)。
削除前の確認モーダルで配下件数を強く警告する。

### コースが削除された場合(UC-17 / UC-19)

- **コース帰属ユニット** → 連鎖削除
- 連鎖削除されるユニットのメディアファイル → S3 から削除
- **コースメンバー関係** → 削除(関係レコードのみ。会員アカウントは残る)
- **お気に入り・コメント**(コース対象、コース帰属ユニット対象、その配下
  のパート対象、デッキ対象) → 削除

事前にユーザー(主催者・メンバー)は UC-23 等で投稿データを退避できる
(退避はユーザー責任)。削除前の確認モーダルで強く警告する。

### ユニット内のパート・デッキが単体で削除された場合(UC-22 / UC-26 / UC-28)

ユニット全体ではなく、配下のパート・デッキを個別に削除した場合
(A-MU2 の「デッキ/カード削除」Web UI、パート削除等):

- 削除されたパート・デッキを**対象とするお気に入り・コメント** → 削除
- パート削除時は、配下デッキを対象とするお気に入り・コメントも連鎖削除
- **差分更新(UC-22)でデッキを全て失ったパートが自動削除される場合**
  (メディアパック仕様 §1.3「パートの実在」)、削除されるのは空になった
  パート本体のみで、**デッキの連鎖削除は伴わない**(配下デッキは削除時点で
  0件。他パートへ移動して生存しているデッキとそのお気に入り・コメントには
  影響しない)。パート自体を対象とするお気に入り・コメントは上記のとおり削除
- お気に入り・コメントの対象はコース/ユニット/パート/デッキの4種(ポリモー
  フィック)であり、パート・デッキ単体の削除でもその対象の `favorite_t` /
  `comment_t` を連鎖削除する(コース・ユニット削除と同じ原則)

- **削除/ロール変更**いずれも、最後の管理者(自分が抜けると管理者
  0人になる)はエラー
- 最後の管理者は他の会員を管理者に昇格させてから操作する必要
- 一般会員が0人の団体で唯一の管理者を抜きたい場合は、団体削除を選ぶ
  (上記「団体が削除された場合」へ)

### コース主催者(会員)が団体から削除される場合(UC-04 はロール変更のため対象外、UC-05)

- 削除前に、主催コースについて主催者を別の人(同団体内の他会員)に
  **移譲(UC-15a)するか、コースを削除(UC-17)するか** のいずれかを
  完了している必要がある
- 完了するまで削除操作はエラー
- 団体管理者が代理で移譲または削除の操作を行う(介入編集権限の延長として)
- この制約により、団体未所属になった会員がコースを保持し続ける状態は
  発生しない

### 除外される会員(コース主催者でない場合も含む)の投稿ユニットの所有権処理(UC-05)

団体から除外される会員が投稿したユニットの所有権は、種別および団体の
外部公開ロック設定に応じて以下のように処理する。詳細は UC-05 の
「投稿ユニットの所有権処理」を参照。

| 条件 | コース帰属ユニット | コース非帰属ユニット |
|---|---|---|
| 外部公開ロック ≠ off | 当該コースの主催者へ所有権移譲 | 団体管理者(指定)へ所有権移譲 |
| 外部公開ロック = off | 当該コースの主催者へ所有権移譲 | 除外者のアカウントに残る |

動機: コースは団体内の共有物として団体側で守る。外部公開ロック適用下
では団体所属中に作成したコンテンツの持ち出しを禁止する。

### 会員(ちょい英語アカウント自体)が削除された場合

ちょい英語アカウント自体の削除は本仕様書のスコープ外であり、
ちょい英語側の本人による退会フローで実施される。

本仕様書としては、ちょい英語側に対して以下を要求する(詳細は「会員
アカウント(ちょい英語アカウント)との関係」参照):

- **団体所属中の会員はアカウントを自己削除できない**ように、ちょい英語
  側の退会フローでブロックする
- アカウント削除には、先に UC-05 による団体からの除外が完了している
  必要がある(さらにその前段として、主催コースの処分: 移譲 UC-15a
  または コース削除 UC-17 が完了している必要がある)
- 結果として、ちょい英語アカウントが削除されるタイミングでは、当該会員
  は団体未所属の状態であり、コース主催関係も持たない。本仕様書の管理
  データに対する追加の連鎖処理は発生しない
- 当該会員が投稿していたユニット(個人保有のマイユニット)の扱いは、
  ちょい英語側の退会フローで定義する(本仕様書のスコープ外)

## S3 データの公開範囲(フェーズ別方針)

メディアファイル(音声、画像)の S3 公開範囲は、フェーズに応じて
段階的に厳格化する。

### フェーズ1: トピックメーカー社内ドッグフーディング

- S3 バケットは **全公開** とする
- メディアURLは固定の S3 公開URL でクライアントから直接参照可能
- 社内ドッグフーディング期間中は外部公開ロック等の規則(制約)による
  「閲覧不可化」が完全には機能しない(URL を知っていれば誰でも見える)。
  ただし社内利用のみのためリスクは限定的

### フェーズ2: 他団体受け入れ可能化以降

- **署名付きURL方式** に移行する
- メディア配信時に動的に署名付きURLを発行し、有効期限と
  閲覧権限のチェックを伴う形で配信する
- 外部公開ロック(規則(制約))・コース公開設定・ユニット公開設定(属性)が、
  メディアファイルの実際の閲覧可否にも有効に効くようになる
- メディアURLの形式が変わるため、**クライアント側でメディアURLを
  ハードコードしない設計を推奨**

### 設計上の含意

外部公開ロック機能の真の効果はフェーズ2の署名付きURL導入で発揮される。
フェーズ1では「投稿者の意思を妨げない範囲で運用上のガードレールを
設ける」程度の効果に留まることを、運用関係者は了解しておく必要がある。

## 補足事項

- **パートの扱い**: ユニット内部に任意のグルーピング層としてパートを持てる(デッキ一覧の区切り)。デッキはブック直下に必ず帰属し、パートへの帰属はオプション(`Unit → パート [1 -- 0..*]`、`パート → デッキ [0..1 -- 1..*]`)。「ちょい英語ミニブック」はパートを持たず(デッキがブック直下)、パート区切りビューは UI に露出しない。単語型ブック等は複数パートを持ちうる
- **料金設定**: 課金システムは既存「ちょい英語」を利用。ユニット側は`無料 / 有料`フラグのみ保持
- **投稿データのバージョン管理**: エクセルファイル自体のバージョン管理は行わない（常に最新版のみ保持）。メディアパック(音声zip / 画像zip)も同様にバージョン管理せず、最新版のみ保持(一括差し替え方式)
- **コース・ユニットの所有関係**: コース・ユニットは会員個人が主催/投稿する(団体の所有物ではない)。団体所属の有無に関わらず、会員はコース・ユニットを作成可能。団体管理者は自団体メンバーのコース/ユニットに対して集約管理ビュー(団体〇〇)からアクセスでき、編集・削除などの上位権限を持つ(UC-18, 19, 27, 28)
- **介入編集の履歴**: 団体管理者が他メンバーのコース/ユニットに介入編集を行った際の履歴ログは、本フェーズ対象外(将来拡張点)
- **フェーズ1運用**: 本設計はトピックメーカー社内ドッグフーディング運用を前提とする。社員が各種ロール(無所属/団体一般/団体管理者)のアカウントを使い分けて、フェーズ2で想定される全ユーザー体験を事前検証する。アクセス入口はトピックメーカー専用暫定プロフィール画面(A-P1、URL直接入力)
- **S3 アップロード方式**: クライアントから直接 S3 にアップロードするのではなく、**アプリサーバー経由(プロキシ方式)** で S3 に転送する。バリデーションをサーバー側で確実に実行するため、および AWS 認証情報がクライアントに漏れないため。詳細は `投稿データ_メディアパック仕様.md` 参照

### 招待を受けた側のユースケース/画面(設計済み)

**経緯**:
従来 UC-03「会員を招待・追加する」は団体管理者側の操作のみが
記述されていたが、被招待者側のフローが抜けていた。
これを別途フローチャートとして設計し、本仕様書とは別ドキュメントに

**成果物**:
- `招待フロー_団体.md`(団体招待: UC-03/50/51/52)
- `招待フロー_コース.md`(コース招待: UC-15 + 被招待者側)

両ドキュメントには Mermaid フローチャート、状態遷移図、状態別の
発行済み招待一覧(団体は A-M4、コースは A-CM3)の表示仕様、および
設計判断(決定済み)の一覧を含む。

**正式ユースケース番号**:
- UC-50: 団体への招待メールを受け取って承諾する(アカウント既存)
- UC-51: 団体への招待メールを受け取ってアカウント作成と承諾を行う
- UC-52: 招待状態を管理する(団体管理者側、A-M4 発行済み招待一覧での表示)
- UC-15 拡張: コースメンバー招待の被招待者側フロー
  (アカウント既存・未取得・URL方式の3パターン)

**主な設計上の決定**:

1. **アカウント既存/未取得の判定はシステム側では行わない**
   - 被招待者の招待承諾画面で「お持ちの方はログイン / 未取得の方は
     新規作成」を選択させる方式とした
   - 招待メール発行時のメールアドレス照合や、中間判定画面が不要

2. **団体招待での1会員1団体制約は二段階チェック**
   - 招待時のバリデーションと承諾時のバリデーションの両方で実施
   - 招待発行後に被招待者が他団体に加入する可能性に備える

3. **コース招待には招待URL方式を含む**
   - 自団体会員から選択 / メール招待 / URL発行 の3方式
     (主催者本人・団体管理者ともに使用可)
   - URL方式は被招待者が事前に確定しないため、A-CM1 一覧で
     「URL発行中」として1レコードのみ表示する特別な扱い
   - URLを受け取った人が**主催者と同じ団体所属の会員ならば承諾可、
     それ以外はエラー**

4. **コースメンバーは主催者と同じ団体所属の会員のみ**
   - コース主催者は団体所属を前提とする(無所属会員はコースを作らない)
   - コースメンバー(共同編集者)も主催者と同じ団体に所属する必要がある
   - 他団体所属者・無所属会員は招待不可
   - 団体管理者の介入編集権限としても、この制約は外れない
   - 動機: コースは主催者の所属団体内での共同作業の場として閉じる

5. **招待状態の管理**
   - 状態 enum: 送信済 / URL発行済(コース招待のみ) / 承諾済 /
     辞退 / 期限切れ
   - 期限切れからは管理者の「再招待」操作で送信済に戻せる

6. **団体招待の承諾時に profile を反映**
   - 招待に記載された氏名・部署を、承諾時に被招待者の
     `profile.name` / `profile.department` へ反映する(記載のある項目のみ。
     既存値があっても上書き)。単一情報源は 招待フロー_団体.md
     設計ポイント7、被招待者への開示はワイヤーフレーム修正仕様 §8.6
