ちょい英語ミニブック投稿システム フェーズ1の各種論点決着に伴う、
ワイヤーフレーム(A-MU3 / A-MU2 / A-U2 / A-MC2 / A-MC3 / A-C2 / A-M2)

修正対象は Claude Design で作成した HTML(ワイヤーフレームPDFの元)。
本書の指示に従って HTML を修正し、PDF を再生成する。

## 0. 背景: 改訂の主眼

### 主眼

サーバー側の自動生成処理(TTS / AI画像)を伴うコンテンツでは、
**登録前のプレビューは原理的に成立しない**(生成物がまだ存在しない
ため)。したがって A-MU3 から登録前プレビュー画面を廃止し、本登録後の
コンテンツ確認は A-MU2 で行う。

### 旧フロー(現行ワイヤーフレーム)

```
A-MU3 [教材データ + ユニット定義 + 公開設定 + 料金 を入力]
  → [投稿内容をプレビュー] ボタン
    → プレビュー画面 ← これが原理的に意味をなさない
      → [投稿する] ボタン
        → A-MU2
```

### 新フロー

```
A-MU3 [教材データ + ユニット定義 + 公開設定 + 料金 を入力]
  → [投稿する] または [下書き保存(非公開で作成)] ボタン
    → A-MU2(本登録された状態)
       自動生成が非同期で進行中
       → 完了をA-MU2で待ち、必要ならレビュー・修正
```

### 変えないこと

- A-MU3 の「公開設定 & 料金」セクションは残す
  (投稿者が公開設定・料金を選んで本登録する従来の挙動を維持)
- 「下書き保存(非公開で作成)」ボタンは残す
  (公開設定を「非公開」固定にする利便機能として有用)
- 「投稿する」ボタンも残す(投稿者が選択した公開設定で本登録)
- A-MU2 の「公開設定 & 料金」セクションは残す
  (投稿後の編集として変更できる、既存の挙動)

### 変えること

- A-MU3 の「投稿内容をプレビュー」ボタンを削除(本書の主たる修正)
- A-MU2 上で自動生成の進捗を可視化する仕組みを追加
- A-MU2 の「プレビュー(学習者視点)」ボタンの位置づけを明確化

詳細はユースケース仕様書「3. ユニット投稿」セクション冒頭の
「投稿フローの基本方針」、および投稿データ・メディアパック仕様書 §6
の処理フローを参照。

## 1. A-MU3「マイユニットを新規投稿」修正指示

### 1.1 削除する要素

#### 1.1.1 「投稿内容をプレビュー」ボタン

- フッター右側のボタン群にある「**投稿内容をプレビュー**」ボタンを削除
- 削除後のフッター右側は **「キャンセル」「投稿する → A-MU2」** の2ボタン
  構成にする

理由: サーバー側生成処理を伴うコンテンツでは、登録前にコンテンツ全体を
プレビューすることは原理的に成立しない(生成物がまだ存在しないため)。

### 1.2 修正する要素

#### 1.2.1 ページ冒頭の説明文

現状: 「ユニット定義と教材データ(エクセル / 音声zip / 画像zip)を一括
登録します。」

修正後:

> ユニット定義と教材データ(エクセル / 音声zip / 画像zip)を一括登録
> します。投稿後はマイユニット詳細画面(A-MU2)に遷移します。
> サーバー側で音声・画像の自動生成が進行している場合は、A-MU2 上で
> 完了状況を確認できます。

文意が伝わる範囲で文言は調整可。要点は「本登録後に A-MU2 に遷移する
こと」「自動生成は本登録後に走り、A-MU2 で完了確認すること」が伝わる
ようにする。

### 1.3 メディア供給モードの排他選択への変更

#### 背景

メディアパック仕様 §3 の改訂により、音声・画像のメディア供給は
**メディアパックモード**(zipアップロード)と **自動生成モード**(TTS /
AI画像)の **排他選択** になった(行レベルの混在は不可)。

#### 現状

A-MU3 の「教材データアップロード」セクションには、各メディアの欄
(音声パック / 画像パック)の下にチェックボックスが配置されている:

- 音声: 「☐ アップロードの代わりに TTS で自動生成する」
- 画像: 「☑ デッキに自動で画像を割り当てる(画像自動)」

これらのチェックボックスは、行レベルでの混在(空欄行のみ自動生成)を
前提とした文言になっている。

#### 修正

各メディア欄を、**ラジオボタン2択** に置き換える:

- **音声メディア**:
  - ○ メディアパック(zip)をアップロード ← 選択時、zipアップロード
    欄が表示される
  - ○ TTS で自動生成 ← 選択時、zipアップロード欄を非表示にする
- **画像メディア**:
  - ○ メディアパック(zip)をアップロード ← 選択時、zipアップロード
    欄が表示される
  - ○ AI画像で自動生成 ← 選択時、zipアップロード欄を非表示にする

各モードのデフォルト選択:
- 音声: 「TTS で自動生成」(投稿者の負担を減らす方向)
- 画像: 「AI画像で自動生成」(同上)

モード切替時の補足:
- 自動生成モード選択中は、エクセルの該当列(音声ファイル / デッキ画像 /
  カード画像)はすべて空欄である必要がある。アップロード前に投稿者が
  確認するためのバリデーション警告を表示する

### 1.4 維持する要素(明示)

以下は本改訂で**変更しない**:

- 「教材データアップロード」セクション全体
- 「コース帰属」セクション
- 「ユニット定義」セクション
- 「公開設定 & 料金」セクション
- フッター左下「**下書き保存(非公開で作成)**」ボタン
- フッター右側「**キャンセル**」ボタン
- フッター右側「**投稿する → A-MU2**」ボタン

### 1.5 修正後のセクション構成

修正後の A-MU3 は以下の構成になる:

1. 教材データアップロード(メディア供給モードのラジオUIを排他化 §1.3)
2. コース帰属(変更なし)
3. ユニット定義(変更なし)
4. 公開設定 & 料金(変更なし)
5. フッター
   - 下書き保存(非公開で作成)(変更なし)
   - キャンセル / ~~投稿内容をプレビュー~~ ← **削除** / 投稿する → A-MU2

## 2. A-MU2「マイユニット 詳細/編集」修正指示

A-MU2 は本登録後の編集・コンテンツレビュー・公開設定変更の場として
中心的な役割を担う。本改訂では、自動生成の進捗可視化と、
「プレビュー(学習者視点)」ボタンの位置づけ明確化を行う。

### 2.1 自動生成ステータス表示の追加

#### 追加位置

ページタイトル直下のメタ情報行の下、または「投稿データ更新(差分処理)」
セクションの直前に、**自動生成ステータス**を表示するセクションを追加する。

#### 表示内容

自動生成(TTS / AI画像)のジョブ状態を表示する。例:

```
自動生成ステータス
─────────────────
🎙 音声(TTS):    生成中  3 / 12 件完了 (進捗バー)
🖼 画像(AI画像): 完了    16 件
```

- 生成中: 進捗バーまたは「N / M 件完了」の表示
- 完了: 「完了」バッジまたは ✓
- 失敗: 失敗件数および再試行ボタン(※失敗時UXは未確定、§4 残論点)
- 該当なし(自動生成OFFまたは zip ですべてアップロード済): 「自動生成は使用していません」表示、またはセクション自体を非表示

#### 自動更新

ジョブ状態は定期的にポーリングして自動更新する(または WebSocket 等
リアルタイム通知)。実装方式は後で別途設計。

### 2.2 「プレビュー(学習者視点)」ボタンの位置づけ明確化

#### 現状

ページ右上に「プレビュー(学習者視点)」ボタンがある。

#### 修正

- ボタンは残す
- ツールチップまたはボタン下の補足説明として、以下を追加:

  > 学習者から見える表示を、現在の状態でプレビューします。

理由: A-MU3 から登録前プレビューが廃止された結果、「学習者視点での
コンテンツ確認はここで行う」という位置づけが明確になる。レビュー目的の
主要動線として重要性が増した。

### 2.3 「投稿データ更新」セクションの整理(メディア供給モードの可視化と切替)

#### 現状

「投稿データ更新(差分処理) UC-22 / UC-23」のセクションは、エクセル
ファイルの差分処理と、音声パック/画像パックの差し替えが同居している。

#### 修正

メディアパック仕様 §3 のモード排他化を反映するため、以下の修正を行う:

**1. 現在のメディア供給モードを明示表示**

セクションの最上部に、音声・画像それぞれの現在のモードを表示する:

> 音声メディア: メディアパック(zip)
> 画像メディア: AI画像自動生成

**2. モード切替UIの追加**

音声・画像それぞれに、モード切替ラジオを配置する(A-MU3 §1.3 と同じ
ラジオ構成):

- 音声: ○ メディアパック ○ TTS自動生成
- 画像: ○ メディアパック ○ AI画像自動生成

現在のモードがデフォルトで選択された状態。投稿者が別モードを選択すると、
切替時の挙動の警告を inline 表示する:

> モードを「メディアパック」に切り替えると、現在の自動生成された
> 音声ファイルはすべて削除され、アップロードされた zip の内容で
> 置き換わります。

> モードを「TTS自動生成」に切り替えると、現在のメディアパック zip と
> 展開ファイルはすべて削除され、TTSによる自動生成が再実行されます。

**3. ダウンロードリンク**

「投稿データをダウンロード(ID付き .xlsx)」ボタンの近くに、メディアの
ダウンロードリンクを配置する(UC-23 の一部):

> ⭳ 音声ファイルを一括ダウンロード(.zip)
> ⭳ 画像ファイルを一括ダウンロード(.zip)

実装上の挙動: **モードを問わず S3 `packs/` 配下の zip をそのまま取得**
する。

- メディアパックモード: アップロードされた zip 原本(ファイル名はユーザー
  命名)
- 自動生成モード: 全件生成完了時にシステムが作成した zip(ファイル名は
  システム生成名)

自動生成モードで **ジョブ未完了の場合**(zipがまだ作られていない)、
ダウンロードボタンは **disable**(または「生成中...」のラベル付き)に
する。完了通知と連動して自動的に有効化される。

ユーザー視点ではどちらのモードでも一様に「メディアファイルを zip で
ダウンロード」できる。これは、自動生成で本登録 → ダウンロード → 手元
編集 → メディアパックモードへ切替アップロード、という運用フロー
(メディアパック仕様 §3.5 の運用例)を可能にするため。

**4. メディアパック側の挙動の注記**

メディアパックモード選択時の zip アップロード欄の下に、一括差し替えの
注記を追加:

> メディアパック(zip)は **一括差し替え** です。新しい zip を
> アップロードすると、従来の音声・画像はすべて新しい内容で
> 置き換わります(個別差分処理は行いません)。

### 2.4 維持する要素(明示)

以下は本改訂で**変更しない**:

- ページタイトル + メタ情報行(投稿者・公開バッジ・ID・更新日時)
  - 公開バッジは A-MU3 で投稿者が選択した公開設定がそのまま反映される
    (「下書き保存」を選んだ場合は「非公開」、「投稿する」で公開設定を
    「公開」にした場合は「公開」など)
- ページ右上「← マイユニット一覧」リンク
- デッキ/カード削除(Web UI 限定) セクション
- コース帰属 セクション
- ユニット定義 セクション
- 公開設定 & 料金 セクション
  - 投稿後の編集として通常通り変更できる
- フッター: ユニットを削除 / キャンセル / 変更を保存

### 2.5 修正後のセクション構成

修正後の A-MU2 は以下の構成になる:

1. ページタイトル + メタ情報行(変更なし)
2. **(新規)自動生成ステータス表示**(§2.1)
3. 投稿データ更新(差分処理) ── 一括差し替え注記とパック原本DLを追加(§2.3)
4. デッキ/カード削除(Web UI 限定)(変更なし)
5. コース帰属(変更なし)
6. ユニット定義(変更なし)
7. 公開設定 & 料金(変更なし)
8. フッター: ユニットを削除 / キャンセル / 変更を保存(変更なし)

## 3. コース系画面の修正(A-MC2 / A-MC3 / A-C2)

コース系画面に対して、以下の2つの修正を行う:

1. **コース主催者の他会員への移譲操作の追加**(UC-15a 新設に伴う)
2. **「団体限定公開」選択時の対象団体を主催者の所属団体に固定**

### 3.1 コース主催者を他会員に移譲する操作の追加

#### 背景

UC-15a「コース主催者を他会員に移譲する」が新設された(ユースケース仕様書
参照)。この操作の主な発火タイミング:

- 現主催者が団体から削除(UC-05)される際の前提条件
  (削除前に、主催コースについて **主催者移譲 または コース削除**
  のいずれかが完了している必要がある。コースが移譲も削除もされていない
  まま主催者が団体未所属になる状態は許容しない)
- 通常時の主催者交代(運用上の必要に応じて)

#### A-MC2(マイコース 詳細/編集、主催者本人の画面)への追加

**追加位置**: フォーム下部、フッター付近(「コースを削除(UC-17)」
ボタンの近く)

**追加要素**: 「**主催者を移譲する...**」ボタン(危険操作色ではなく
中立色、「コースを削除」よりは控えめな見た目)

**操作フロー**:

1. 「主催者を移譲する...」ボタンをクリック
2. モーダルが開く:
   - タイトル: 「主催者を移譲する」
   - 説明文: 「このコースの主催者を別の会員に交代させます。移譲先は
     あなたと同じ団体に所属する会員のみ選択できます。」
   - 移譲先選択: 自団体会員のサジェスト/セレクト(現主催者は除外)
   - 注意文: 「移譲後、このコースに対するあなたの権限は通常の
     コースメンバー(または非メンバー)になります。元に戻すには
     新主催者に再度移譲してもらう必要があります。」
3. 「移譲を実行」ボタン → 確認ダイアログ「本当に移譲しますか?」
4. 確定 → コース.主催関係 を新主催者に付け替え、コース詳細画面に戻る
   (ヘッダの「主催: あなた」表示が変わる、または A-MC1 一覧に戻る)

**バリデーション**:

- 移譲先が選択されていない → エラー
- 移譲先が主催者と異なる団体所属 → エラー(UI上はそもそも候補に
  出ないので、サーバ側のフォールバック)
- 移譲先が既にこのコースのメンバー: 問題なし(主催者になり、
  メンバー関係から外れる/または兼ねる、は実装判断)

#### A-C2(団体コース 詳細/編集、団体管理者の介入編集画面)への追加

A-MC2 と同等の「主催者を移譲する...」ボタンを配置する。介入編集モード
(現状の警告バー表示の流儀)に従い、操作の文言に「介入編集として」を
含める:

- ボタン文言: 「主催者を移譲する...(介入編集 / UC-19)」
- モーダル内の説明文に「現主催者: 佐藤 花子 さんの代理として主催者を
  移譲します。」を追加
- 移譲先候補は当該コースの所属団体内会員(現主催者と同じ団体)

#### A-MC3(マイコース 新規作成)への追加

**追加なし**(新規作成時には主催者は作成者本人で確定するため、移譲操作
は不要)。

### 3.2 「団体限定公開」選択時の対象団体を主催者の所属団体に固定

#### 背景

現状のワイヤーフレーム(A-MC2 / A-MC3 / A-C2)では、「公開設定」の
「団体限定公開」を選択すると条件表示で「対象団体」セレクトが現れ、
任意の団体を選択できる UI になっている。これは想定外の挙動である。

正しい仕様:

- コース主催者は1団体にのみ所属する(1会員1団体制約)
- コースは主催者の所属団体内での共同作業の場として閉じる
- 「団体限定公開」の対象団体は **主催者の所属団体に自動固定**
- 任意団体を指定する余地は構造的に存在しない

詳細はユースケース仕様書「公開範囲の定義 / 「団体限定公開」の対象団体」
を参照。

#### A-MC2 / A-MC3 / A-C2 の修正内容

「団体限定公開」を選択した際の条件表示部分を以下のように修正する:

- 現状: ラベル「対象団体」+ 選択可能なセレクトボックス(任意団体を
  選べる)
- 修正後: ラベル「対象団体(自動)」+ **読み取り専用の表示**として
  主催者の所属団体名を表示
  - 例: 「対象団体: 株式会社トピックメーカー(主催者の所属団体)」
  - セレクトボックスは disabled な見た目(またはセレクト自体を
    廃止してテキスト表示に)
  - 補足説明: 「対象団体は主催者の所属団体に自動的に決まります。
    1人の会員は1団体にのみ所属できるため、他の団体は選択できません。」

A-C2(介入編集モード)では、「主催者の所属団体」のラベルが正確
(団体管理者自身の団体ではなく、コース主催者の所属団体)。本仕様の
スコープでは現主催者と団体管理者は同じ団体に所属するため見た目は
変わらないが、文言は「主催者の所属団体」で統一する。

### 3.3 ユニット側(A-MU2 / A-MU3)の対応

ユニットがコース非帰属の場合に「団体限定公開」を選べる(UI が4値表示)。
このときも対象団体は **投稿者の所属団体に固定** される。

#### A-MU3 / A-MU2(コース非帰属モード)の修正内容

「公開設定」セクションで「団体限定公開」を選択した際:

- A-MU3: 現状「公開設定 & 料金」セクションは2値(公開/非公開)のみが
  選べる(コース帰属時)。コース非帰属を選んだ場合に4値表示となる
  実装の場合は、A-MC2 と同様に「対象団体(自動)」表示を行う
- A-MU2: 同上。コース非帰属時のみ4値表示、団体限定公開選択時に
  「対象団体(自動): 投稿者の所属団体名」を読み取り専用で表示

(現状のワイヤーフレームPDFを見る限り、A-MU3 / A-MU2 の「公開設定 &
料金」セクションには「団体限定公開」の対象団体UI は存在せず、コース
帰属時のみ表示前提で2値ラジオになっている。コース非帰属モードへの
切替UI追加と合わせて実装フェーズで詳細設計する。)

### 3.4 投稿者制限UIの2値化

#### 背景

コース招待フローの打ち合わせ(招待フロー_コース.md §設計判断 4)で
決定された通り、コースの投稿者制限から「一般(メンバー以外も投稿可)」
は廃止された。コースの投稿者制限は `主催者のみ / メンバー` の2値となる。

これに伴い、ユースケース仕様書 UC-13 と概念モデル図のコース.投稿者制限
enum も2値に修正済み。

動機: コースは主催者の所属団体内での共同作業の場として閉じる設計で
あり、「メンバー以外も投稿可」は構造的にあり得ない。

#### A-MC3 / A-MC2 / A-C2 の修正内容

「投稿者制限」セクションのラジオを **3択 → 2択** に変更する:

- 現状: ラジオ3択
  - ○ 主催者のみ ── コースの主催者(あなた)だけが投稿可
  - ○ メンバー ── 主催者 + コースメンバー
  - ○ 一般 ── コースメンバー以外の任意の会員も投稿可能
- 修正後: ラジオ2択
  - ○ 主催者のみ ── コースの主催者だけが投稿可
  - ○ メンバー ── 主催者 + コースメンバー(デフォルト)

「一般」のラジオオプションを削除する。3画面とも同じ修正(A-MC3 新規
作成、A-MC2 主催者本人画面、A-C2 介入編集画面)。

#### A-CM2(コースメンバー招待画面)の補助情報

A-CM2 のメンバー招待画面で、現在のコースの投稿者制限を補助情報として
表示している場合は、その表示も2値ベースに更新する(該当する表示が
あればの話。現状のワイヤーフレームでは確認されない)。

## 4. 会員系画面の修正(A-M2)

UC-05(団体からの除外)の効果欄に「投稿ユニットの所有権処理」ルールが
追加された(ユースケース仕様書参照)。これに伴い、A-M2(会員 詳細/編集)
の除外操作にユニット所有権処理のオプションを追加する。

### 4.1 除外モーダルへの所有権処理オプション追加

#### 背景

UC-05 の新ルールでは、除外対象会員の投稿ユニットを次のように処理する:

| 条件 | コース帰属ユニット | コース非帰属ユニット |
|---|---|---|
| 外部公開ロック ≠ off | 当該コースの主催者へ移譲 | **団体管理者(指定)**へ移譲 |
| 外部公開ロック = off | 当該コースの主催者へ移譲 | 除外者のアカウントに残る |

このうち「団体管理者(指定)へ移譲」のケースは、複数の団体管理者が
いる場合に **どの管理者を所有者に指定するか** を除外実行者に選ばせる
必要がある(管理者が1人しかいない場合はその人にデフォルトで決まる)。

#### A-M2 除外操作の現状

A-M2 のフッター付近に「**団体から削除...**」ボタンがあり、押下すると
削除前の確認モーダルで以下の警告が表示される:

> NOTE — 削除前の確認事項(モーダルで警告):
> - この会員が主催するコース(1件)・投稿ユニット(4件)の所有者は
>   削除後も残り、該当会員の個人アカウントに紐づいたままとなります
> - 「団体コース」「団体ユニット」の集約ビューからは自動的に消えます
> - コースメンバーからも自動的に除外されます

#### 修正後のモーダル仕様

確認モーダルを以下のように再構成する:

**1. 主催コースの事前処分の表示と確認**(UC-05 の事前条件)

- 対象会員が主催するコースが存在する場合、ボタン押下時点でモーダルを
  開かず、別UIで「主催者移譲(UC-15a)またはコース削除(UC-17)が必要」
  メッセージとリンクを表示する
- 主催コースがゼロの場合のみ、除外モーダルに進む

**2. 除外モーダル本体**

モーダル内に以下の項目を表示する:

- 警告メッセージ(現状を更新):

  > この会員を団体から除外します。除外後の処理:
  > - 会員アカウントは無所属になります(ちょい英語アカウント自体は残る)
  > - 他のコースのメンバー関係から除外されます
  > - 投稿ユニットの所有権は、以下のルールに従って処理されます:

- **ユニット所有権処理の予告サマリ表**:

  | カテゴリ | 件数 | 処理 |
  |---|---|---|
  | コース帰属ユニット(コース別) | 3件 | コース主催者(山田/佐藤)へ移譲 |
  | コース非帰属ユニット(ロックにより団体管理者に渡る) | 5件 | 下記で指定する管理者へ移譲 |
  | コース非帰属ユニット(除外者のアカウントに残る) | 2件 | 除外者(無所属化後)のアカウントに残る |

  ※ 外部公開ロック = off の場合は3行目のみ表示。
  ※ 件数0のカテゴリは行を表示しない。

- **団体管理者(指定)** の選択UI(外部公開ロック ≠ off で、かつ
  コース非帰属ユニットが1件以上ある場合のみ表示):

  - 団体管理者が1人しかいない場合: 「●● さんが所有者になります」と
    表示するのみ(選択UIなし、disabled な見た目)
  - 団体管理者が複数いる場合: ドロップダウン/ラジオで「ユニットの
    新しい所有者を選択してください」 → 自団体の管理者一覧から1名選択
  - デフォルト選択: なし(明示選択を促す)、または除外実行者本人

- 「除外を実行」ボタン → 最終確認ダイアログ「本当に除外しますか?」
- 確定 → 上記ルールに従って Account → Unit 関連を付け替え、Account.
  所属団体 を null にし、A-M1 一覧に戻る

#### バリデーション

- 主催コースが存在する場合は除外モーダル自体に進めない(上記事前処分)
- 「団体管理者(指定)」が必須項目(複数管理者かつコース非帰属の
  ロックされたユニットあり)の場合、未選択でエラー

#### 補足

ユーザビリティの観点で、除外モーダルを開いた時点でユニット件数の
集計とカテゴリ分類が完了している必要がある。これは事前にサーバー側
集計APIを呼び出してから表示する。

## 5. 団体ユニット画面の修正(A-U2: A-MU2 との同期)

A-U2(団体ユニット 詳細/編集、団体管理者の介入編集画面)は、ある時点
からの仕様変更(UC-22 の差分処理仕様化、メディアパック構造の整理、
論点6・9 の決着など)が **A-MU2 にだけ反映されてきた経緯** により、
A-MU2 と比べてかなり古いバージョンで止まっている。

UC-28 の規定では「UC-21〜26 と同等の編集・削除操作を上位権限として
実行可能」とされており、本来 A-U2 は A-MU2 と同等内容のフォームを
提供すべき。本節では A-U2 を A-MU2 と同期させる修正を指示する。

### 5.1 同期の原則

A-U2 のフォームを **A-MU2 のフォームと内容的に同等にする**。
ただし以下の介入編集モード固有の表示・文言は A-U2 固有として残す:

- ヘッダ上部の **「上位権限での介入編集」警告バー**(現状の表示を維持)
- メタ情報行の **「介入編集モード」バッジ**(現状の表示を維持)
- パンくず: 「自団体 › 団体ユニット › ...」(A-U2)
- 右上「← 団体ユニット一覧に戻る」リンク(A-MU2 の「← マイユニット
  一覧」に相当)
- 各セクションの UC 参照: A-U2 では UC-28 / UC-22 相当 など、上位権限の
  介入編集として参照する
- 「ユニットを削除」ボタンのラベル: 「ユニットを削除(UC-28 / 上位権限)」
- 「変更を保存」ボタンのラベル: 「変更を保存(介入編集として記録)」

これらは A-C2 と A-MC2 の関係(警告バー・バッジ・リンク先・UC参照・

追加する:

現在の A-U2 はこのセクションが「ダウンロード」「アップロード」の
最低限の構成しかない。A-MU2 と同等に以下を加える:

- ダウンロードボタンの下の NOTE(ID付きエクセルの create / update
  判定、削除は Web UI で実施)

## 7. 残論点・将来検討

### 7.1 自動生成失敗時の UX

- 自動生成(TTS / AI画像)が失敗した場合の A-MU2 上の表示
- 再試行ボタンの動作
- 部分失敗(N件中3件失敗)の扱い

### 7.2 自動生成完了通知

- A-MU2 を開きっぱなしにしているユーザーへの完了通知
  (ポーリング / WebSocket / プッシュ通知)
- A-MU2 を閉じてしまったユーザーへの通知(メール / アプリ内通知)

### 7.3 「投稿する」または「下書き保存」押下から A-MU2 遷移までの待ち時間

- バリデーション、DB保存、S3アップロード、自動生成ジョブ投入に時間が
  かかる場合のローディング表示
- 部分的に完了した状態で遷移するか、全工程完了まで待つか

### 7.4 「公開」状態で本登録した場合の自動生成中の閲覧体験(決着済み)

論点: A-MU3 で「公開」にして本登録した直後、自動生成の完了前に他ユーザーが
そのユニットを閲覧した場合の挙動。

決着: 生成完了までは閲覧不可。配信されるデッキオブジェクトは自動生成の
全件完了後にのみ配信され、未完了の間はアクセスできない。したがって「公開」
で本登録しても、生成途中のメディア欠落が学習者に露出することはない。
配信ゲートの実装根拠はメディアパック仕様 §9.4 / §3.3 / §5.4.2 を参照。

### 7.5 介入編集画面と本人画面のワンソース化

A-U2 と A-MU2、A-C2 と A-MC2 はそれぞれ同じオブジェクトに対する画面
で、介入編集モード固有の表示要素(警告バー、バッジ、文言、リンク先
など)を除けば内容は完全同等。

現状は別画面として実装する設計判断のもとに2画面ずつ保守しているが、
本改訂の発端となった A-U2 の同期もれのような問題が将来的にも発生する
リスクがある。

将来の選択肢:

- **(A)** 同じコンポーネントを「ロール文脈フラグ」で出し分ける形に
  リファクタする(ワンソース化)。表示の違いは props またはコンテキスト
  で制御
- **(B)** 別画面のまま、CI などで両画面の構造差分を自動検出して同期
  もれを警告する仕組みを導入
- **(C)** 現状維持。手動レビューで同期を保つ

実装フェーズでの実装方式選定と合わせて検討する。

## 8. 新規画面: 団体招待 被招待者フロー(IV 系)

### 8.0 位置づけ

団体招待のうち、**招待を受けた側(被招待者)の画面**がワイヤーフレームに

- 対応 API: `org_invitation.md`(GET `/get`、POST `/accept`、POST `/decline`)
- 対応フロー: `招待フロー_団体.md` の被招待者フロー(B1〜B16)
- **管理コンソールの画面群(A-xx)とは別系統の公開ページ**。サイドバー
  ナビゲーションを持たない、メールリンクから入るスタンドアロン画面
- GET `/get` はログイン不要のため、リンクを開けば誰でも招待内容を閲覧
  できる。**承諾**時にログインを要求する(**辞退**は `token` のみで可)

コース招待の被招待者画面は、対応 API が出た段階で別途追加する(本節の
対象外)。

### 8.1 招待メール(本文イメージ)

ランディング画面(IV-1)の手前に届くメール。送信時(POST `/create` /
`/resend`)にサーバーが生成する。

```
件名: 【ちょい英語】{団体名} からの招待

────────────────────────────────────
ちょい英語 ミニブック投稿

{氏名} 様

{団体名} から、メンバーとして招待が届いています。

  団体        {団体名}
  ロール      {団体一般会員 / 管理者}
  有効期限    {YYYY-MM-DD HH:MM} まで

{招待メッセージがあれば本文として表示}

下のボタンから内容を確認し、参加または辞退を選んでください。

        ┌────────────────────────┐
        │     招待を確認する       │   → IV-1(/invitation?token={token})
        └────────────────────────┘

このリンクは招待された方専用です。心当たりがない場合は破棄してください。
────────────────────────────────────
```

- 宛名 `{氏名}` は招待時に氏名が入力されている場合のみ。無ければ省略
- ロールは `org_role`(`member` → 「団体一般会員」/ `admin` → 「管理者」)
- ボタンのリンク先は IV-1 に `token`(UUID)をクエリで付与
- 招待者(招待した管理者)の氏名は、メールでは送信時に含められる(サーバー
  生成のため)。ただしランディング画面では出さない(§8.5 参照)

### 8.2 IV-1 招待ランディング画面

- 中央寄せの単一カードレイアウト。ヘッダーは「ちょい英語 ミニブック投稿」
  程度のロゴのみ。管理コンソールのサイドバーは無し
- データ取得: GET `/get`(`token`)→ `invitation` と `org`
- 表示要素:
  - 団体名(`org.name`)
  - 部署(`org.department`、任意)
  - 招待されたロール(`invitation.org_role` を `団体一般会員 / 管理者` に表示)
  - 宛名(`invitation.name`、任意)
  - 招待メッセージ(あれば)
  - 有効期限(`invitation.expires_at`)
- クライアントは `invitation.status` と `expires_at` を見て、下記 §8.3 の
  状態に分岐する

### 8.3 状態バリエーション(IV-1 の出し分け)

1画面の状態違いとして、以下を用意する(Claude Design では state ギャラリー
として並べる)。

**操作前の状態**

| 状態 | 条件 | 表示と操作 |
|---|---|---|
| 操作可能 | `status = sent` かつ 現在 < `expires_at` | 招待内容を表示。ボタン:[ログインして承諾]/[アカウントを作成して承諾]/[辞退する]。ログイン済みなら[承諾する]/[辞退する] |
| 期限切れ | `status = expired` または 現在 ≥ `expires_at` | 「この招待は有効期限が切れています」。操作ボタンは出さない。団体管理者への問い合わせを案内 |
| 承諾済み | `status = accepted` | 「この招待はすでに承諾済みです」。ダッシュボード/プロフィールへの導線 |
| 辞退済み | `status = declined` | 「この招待は辞退済みです」 |
| 無効なリンク | GET `/get` が `invitation.NOT_FOUND` | 「招待が見つかりません。リンクが正しいかご確認ください」 |

**操作後の結果状態**

| 状態 | 条件 | 表示 |
|---|---|---|
| 参加完了 | POST `/accept` 成功 | 「{団体名} に参加しました」。プロフィール/ダッシュボードへ誘導 |
| 辞退完了 | POST `/decline` 成功 | 「招待を辞退しました」 |

### 8.4 アクションと API 対応・エラー処理

- **承諾**: ログイン必須 → POST `/accept`(`token`)
  - `org.ALREADY_JOINED` → 「既に別の団体に所属しています。脱退してから参加してください」(フロー E3 相当)
  - `invitation.FORBIDDEN`(`target_user_id` 指名とログインユーザーが不一致)→ 「この招待は別のアカウント宛てです。招待されたアカウントでログインしてください」
  - `invitation.INVALID`(`sent` でない/期限切れ)→ 期限切れ/無効状態の表示に切り替え
- **辞退**: ログイン不要 → POST `/decline`(`token`)。`token` の保持自体が
  被招待者本人であることの証左となるため、辞退に認証は要求しない
  - `invitation.INVALID` → 無効状態の表示に切り替え
- **ログイン/アカウント作成の導線**: 既存「ちょい英語」のログイン・
  アカウント作成画面へ遷移。`token` を引き回し(クエリ等)、完了後に
  IV-1(`?token=...`)へ戻る

### 8.5 注記(設計上の判断点)

- **辞退はログイン不要、承諾はログイン必須(非対称)**。承諾はアカウントの
  所属状態を変える(団体に所属させる)ため認証を要求するが、辞退はレコードに
  `status = declined` を立てるだけでアカウントに触れない。メール招待では
  `token` の保持自体が被招待者本人の証左となるため、辞退は `token` のみで
  実行できる。これにより、アカウント未取得の被招待者(UC-51)も辞退できる。
  POST `/decline` はログイン不要(`token` のみ)。`招待フロー_団体.md` の B8
  (ログイン前に辞退を分岐)とも一致し、フロー図側の修正は不要
- **招待者名はランディングに出さない**。GET `/get` は `invitation` と `org`
  のみを返し、招待者(招待した管理者)の氏名フィールドを持たない。`招待フロー_団体.md`
  の B4 は「招待者を表示」と書いているが、API に無いため IV-1 では表示しない。
  ランディングでも招待者名を出すなら GET `/get` への項目追加が必要
- (別件・解消済み)A-M3(招待する側)のワイヤーフレームが表示する「この
  メールアドレスは既に他団体に所属しているため招待できません」という作成時
  エラーは、当初 POST `/create` に検査が無く未実装だったが、発行時 membership
  チェックとして**実装済み**(2026-06-19 / issue #366。`email` / `target_user_id`
  の `ALREADY_JOINED`)。未登録メールは所属が無いため素通りし、承諾時の
  `org.ALREADY_JOINED` で確定する二段構え(招待フロー_団体.md 設計ポイント
  1・2)。被招待者画面とは別件

### 8.6 参加時の注意文言(全アセット管理下の明示)

団体に所属すると、被招待者のすべてのコンテンツ資産(**所属前に作成した
ユニットを含む**)が団体の管理下に置かれる(原則の単一情報源はユースケース
仕様書「システム前提 / 会員と団体の関係」)。承諾はこの効果への同意を伴う
ため、IV-1 の**操作可能状態**(§8.3)で、招待内容の下・アクションボタン群の
上に、以下の注意文言を表示する:

> 参加すると、あなたが投稿済みのユニット(この団体に参加する前に作成した
> ものを含む)は団体の管理下に置かれ、団体管理者による閲覧・編集・削除の
> 対象になります。

さらに、GET `/get` が返す `org.external_lock` が `off` 以外の場合のみ、
以下を追加表示する(条件付き文言):

> この団体は外部公開ロックが有効です。団体から除外される際、コースに
> 帰属していないユニットは団体管理者へ移譲されます(お手元には残りません)。

- 見た目: 警告調のノート(黄色系)。エラー表示ではない
- 表示条件: 操作可能状態のみ。期限切れ・承諾済み・辞退済み・無効なリンクの
  各状態では表示しない
- 文言は文意が伝わる範囲で調整可(要点は「所属前作成分を含む全ユニットが
  団体管理下に入ること」「ロック有効団体では除外時にコース非帰属ユニットが
  管理者へ移譲されること」の2点。なお本仕様に会員側からの自発的な団体脱退
  は存在せず、団体を離れる経路は管理者による除外 UC-05 のみ)
- state ギャラリー(§8.3)には、操作可能状態を「外部公開ロック off(標準
  文言のみ)」と「外部公開ロック有効(条件付き文言あり)」の2バリエーション
  として並べる

## 9. 会員一覧と招待一覧の分離(A-M1 改修 + A-M4 新規)

### 9.0 位置づけ

A-M1(会員一覧)は「承諾済みで団体に所属している会員」の一覧であるべき
ところ、現状は「招待中」「期限切れ」「辞退」のバッジ付き行(まだ会員で
ない招待レコード)を混在表示している。会員と招待は別のライフサイクルを
持つため分離し、発行済みの招待は新画面 A-M4(発行済み招待一覧)に移す。

- 対応 API: GET `/maker/api/org/invitation/list`(A-M4)
- 対応 UC: UC-03(招待)/ UC-52(招待状態管理)
- 本改修により、`招待フロー_団体.md` の「A-M1 に招待状態を表示する」という
  UC-52 の設計は A-M4 基準に置き換わる(別ファイルで整合を取る)

### 9.1 A-M1「会員 一覧」の改修

削除する要素:

- 「招待中」「期限切れ」「辞退」などの招待ステータスのバッジ表示
- まだ会員でない招待レコードの行(現ワイヤーフレームの「Park Ji-ho 招待中」
  行など)。A-M1 は `status = accepted`(団体所属済み)の会員のみを並べる

追加する要素:

- 一覧右肩、[＋ 会員を招待 → A-M3] の隣に [招待の一覧 → A-M4] ボタンを置く

維持する要素:

- 検索・ロール絞り込み・並び替え、会員行から A-M2(詳細/編集)への遷移

### 9.2 A-M4「発行済み招待 一覧」(新規)

- アクセス: 団体管理者のみ
- データ: GET `/list`(50件/ページ、`created_on` 降順、`has_next` でページング)
- 一覧列: 氏名(`name`)/ メール(`email`)、ロール(`org_role`)、部署
  (`department`)、ステータス(`status`)、有効期限(`expires_at`)、
  作成日(`created_on`)
- 右肩に [＋ 会員を招待 → A-M3](招待台帳から続けて招待できる導線)

ステータスバッジと操作(実装済み API に対応):

| status | バッジ | 操作(対応API) |
|---|---|---|
| sent | 招待中 | 取消(POST `/cancel`) |
| expired | 期限切れ | 再招待(POST `/resend`) |
| declined | 辞退 | 再招待(POST `/resend`) |
| accepted | 承諾済み | なし(履歴として表示。会員としては A-M1 に存在) |

注記:

- **削除操作は置かない**。`org_invitation.md` に delete endpoint が無く、
  招待レコードを物理削除する口が無いため(API を正とする)。`cancel` は
  `sent → expired` に状態を変えるのみで、レコードは残る
- **「送信済(sent)の再送信」は無い**。`resend` の対象は `expired` /
  `declined` のみ。sent に対してできるのは取消(cancel)のみ
- accepted も含めて全ステータスを表示する(招待の発行台帳として監査に有用)。
  accepted 行に操作は無い

## 10. コースメンバー一覧と招待一覧の分離(A-CM1 改修 + A-CM3 新規)

### 10.0 位置づけ

§9 と同じ問題がコースメンバー招待にもある。A-CM1(コースメンバー一覧タブ)は

バッジ付き行(まだメンバーでない招待レコード)を混在表示している。会員一覧
(A-M1)と同様に分離し、発行済みのコース招待は新画面 A-CM3(発行済みコース
招待一覧)に移す。

- 対応 API: GET `/maker/api/course/invitation/list`(`course_id` 必須)
- 対応 UC: UC-15(コースメンバー招待)
- アクセス: 主催者本人 または 同団体の管理者
- 本改修により、`招待フロー_コース.md` の「A-CM1 一覧での招待状態の表示」は
  A-CM3 基準に置き換わる(別ファイルで整合を取る)

### 10.1 A-CM1「コースメンバー 一覧(タブ)」の改修

削除する要素:

- 「招待中」「URL発行中」「期限切れ」「辞退」などの招待ステータスのバッジ表示
- まだメンバーでない招待レコードの行(現ワイヤーフレームの「Park Ji-ho 招待中」
  行など)。A-CM1 はコース参加済みのメンバーのみを並べる

追加する要素:

- メンバータブ右肩、[＋ 招待 → A-CM2] の隣に [招待の一覧 → A-CM3] ボタンを置く

維持する要素:

- メンバー行の除外操作、主催者バッジ表示

### 10.2 A-CM3「発行済みコース招待 一覧」(新規)

- アクセス: 主催者本人 または 同団体の管理者
- データ: GET `/course/invitation/list`(`course_id`、50件/ページ、`created_on`
  降順、`has_next` でページング)
- 一覧列: 宛先(`selected` は会員名、`email` はメールアドレス、`url` は
  「URL招待」)、方式(`method`)、ステータス(`status`)、有効期限
  (`expires_at`)、作成日(`created_on`)、承諾者(`accepted_user_id`、あれば)
- 右肩に [＋ 招待 → A-CM2]

ステータスバッジと操作(実装済み API に対応):

| status | バッジ | 操作(対応API) |
|---|---|---|
| sent(送信済) | 招待中 | 取消(POST `/cancel`) |
| url_issued(URL発行済) | URL発行中(未使用) | 取消=URL無効化(POST `/cancel`) |
| accepted(承諾済) | 承諾済み | なし(メンバーとして A-CM1 に存在) |
| declined(辞退) | 辞退 | 再招待(POST `/resend`) |
| expired(期限切れ) | 期限切れ | 再招待(POST `/resend`) |

注記(団体版 §9 との差分。コース招待 API による):

- **`url_issued`(URL発行済)に対する管理者の操作は取消(`cancel` = URL無効化)
  のみ**。再招待(`resend`)の対象は期限切れ / 辞退のみのため url_issued には
  使えない(被招待者による辞退は url_issued でも可能)。URL方式の承諾は API 上
  `accepted`(`accepted_user_id` 付き)になり、承諾者はメンバーとして A-CM1 に並ぶ
- **削除操作は置かない**(API に delete endpoint が無い)。`cancel` は
  `sent` / `url_issued` → `expired` に状態を変えるのみ
- **送信済(sent)の再送信は無い**。`resend` の対象は `expired` / `declined` のみ
- コース招待の **辞退はログイン不要**(POST `/decline` が制限なし、`token` が
  本人確認を兼ねる)。団体側で統一した方針と一致
- コース招待の **作成時バリデーション**は API 側で行う。`selected` / `email`
  方式では作成時に `target_user.DIFFERENT_ORG`(主催者と異なる団体/無所属)・
  `target_user.ALREADY_MEMBER`(既にメンバー)・`invitation.ALREADY_PENDING`
  (同一コース×同一宛先に有効=`sent` かつ期限内の招待が既にある。二重
  pending 禁止)・`invitation.DUPLICATE_IN_REQUEST`(同一リクエスト内の宛先
  重複)を検査して弾く。`url` 方式は対象外(被招待者が事前に確定しないため)。
  団体招待も発行時チェックを持つが、団体側は「未登録メールは素通り(ベスト
  エフォート)＋承諾時に確定」の二段構えである点がコースと異なる

## 11. 新規画面: コース招待 被招待者ランディング(IV-2)

ちょい英語 ミニブック投稿

### 11.2 IV-2 コース招待ランディング画面

- 中央寄せの単一カード。管理コンソールのサイドバーは無し
- データ取得: GET `/get`(`token`)→ `invitation` と `course`
- 表示要素: コース名(`course.name`)、招待メッセージ(あれば)、有効期限
  (`invitation.expires_at`)
- クライアントは `invitation.status` と `expires_at` を見て §11.3 の状態に分岐

### 11.3 状態バリエーション(IV-2 の出し分け)

操作前:

| 状態 | 条件 | 表示と操作 |
|---|---|---|
| 操作可能 | `status = sent` または `url_issued`、かつ 現在 < `expires_at` | コース情報を表示。ボタン:[ログインして承諾]/[辞退する]。ログイン済みなら[承諾する]/[辞退する] |

| 承諾済み | `status = accepted` | 「この招待はすでに承諾済みです」。コース詳細(B-02)への導線 |
| 辞退済み | `status = declined` | 「この招待は辞退済みです」 |
| 無効なリンク | GET `/get` が `invitation.NOT_FOUND` | 「招待が見つかりません。リンクが正しいかご確認ください」 |

操作後の結果:

| 状態 | 条件 | 表示 |
|---|---|---|
| 参加完了 | POST `/accept` 成功 | 「{コース名} に参加しました」。コース詳細(B-02)へ誘導 |
| 辞退完了 | POST `/decline` 成功 | 「招待を辞退しました」 |

### 11.4 アクションと API 対応・エラー処理

- **承諾**: ログイン必須 → POST `/accept`(`token`)
  - `org.NOT_JOINED`(団体未所属)→ 「このコースに参加するには、先に団体に参加する必要があります」(前提2 / フロー E3)
  - `org.DIFFERENT_ORG`(主催者と異なる団体に所属)→ 「このコースは別の団体のものです。主催者と同じ団体に参加してから承諾してください」(前提2 / フロー E3)
  - `course.ALREADY_MEMBER` → 「既にこのコースのメンバーです」
  - `invitation.FORBIDDEN`(`selected` 指名とログインユーザーが不一致)→ 「この招待は別のアカウント宛てです。招待されたアカウントでログインしてください」
  - `invitation.INVALID`(`sent` / `url_issued` でない / 期限切れ)→ 期限切れ/無効状態へ
- **辞退**: ログイン不要 → POST `/decline`(`token`)。`sent` / `url_issued` の
  いずれも辞退できる(URL招待の辞退を含む)。`token` が本人確認を兼ねる
  - `invitation.INVALID` → 無効状態へ
- **ログイン導線**: 既存「ちょい英語」のログイン画面へ。`token` を引き回し、
  完了後に IV-2(`?token=...`)へ戻る。アカウント作成導線は持たない(前提2)

### 11.5 注記(IV-1 / 団体版との差分)

- **「アカウントを作成して承諾」の導線が無い**。コース招待は団体所属済みを
  前提とするため(前提2)、未取得者向けの作成導線は出さない
- **承諾時のエラーがコース固有**。団体所属の有無・主催者との同団体性を
  `org.NOT_JOINED` / `org.DIFFERENT_ORG` で出し分け、いずれも「先に団体に
  参加」へ誘導する
- **URL方式(url_issued)も辞退できる**。POST `/decline` の対象は `sent` /
  `url_issued` の両方
- 主催者名・団体名はランディングに出さない。GET `/get` は `invitation` と
  `course`(`id` / `name` のみ)を返し、主催者名・団体名のフィールドを持たない
  (IV-1 と同じ制約。出すなら API への項目追加が必要)

## 12. コメント数・お気に入り数のヘッダ表示 と コメント一覧画面(A-CMT)の新規追加

コメント数・お気に入り数とも、同じ**価値メトリクス軸**で集計する:

- 両カウントとも = **非公開のみ除外・閲覧者非依存**。公開/プライベート公開/団体限定公開の

  学習者側マスク方式は撤回。詳細は ユースケース・画面一覧 UC-45)。

  集約範囲」。本節はヘッダ表示に必要な範囲の要約。

### 12.2 新規画面 A-CMT「コメント 一覧」

コメント一覧+モデレーション削除を、**単一の独立画面 A-CMT** として新規に追加する
(A-M4 / A-CM3 と同列の遷移先画面)。A-MC2 / A-C2 / A-MU2 / A-U2 のヘッダのコメント数
から遷移する。1つの画面仕様を host(遷移元)の文脈で振り分ける(A-CM1 と同じ考え方):
集約範囲と削除権限が host で決まる。

- タイトル/パンくず: host のコンテンツ名 + 「コメント」(例:「旅行で使える英会話 初級 ›
  コメント」)。

### 12.3 集約範囲(UC-45 と一致)

A-CMT には host 対象+配下のコメントを**集約表示**する。

- コース host(A-MC2 / A-C2 から遷移): コース対象 + 配下ユニット・パート・デッキ対象
- ユニット host(A-MU2 / A-U2 から遷移): ユニット対象 + 配下パート・デッキ対象

A-CMT は作成者/管理者のモデレーション画面なので、閲覧者は自分のスコープ内(自作コース/ユニット、または自団体メンバーのコンテンツ)を**すべて読める**。したがって A-CMT では**非公開配下も含めて全件を表示し、マスクはしない**。`12.4` の層別サマリも同じく全件。

(学習者側の集約一覧(UC-45。B-02/B-03/B-05。本ワイヤーフレームのスコープ外)は、`一般会員のみロック` 下のコース構成の不変条件により、host 到達者にとって配下が全可読となる方式に確定した(従来のマスク行方式は撤回)。非公開配下のみ行ごと除外。詳細は ユースケース・画面一覧 UC-45 / 申し送り §2.6。)

### 12.4 コメント一覧の表示

一覧の上部に、**層別サマリ**(表示専用)を置く。host 配下の集約コメントを対象種別ごとに
数で示す: コース host = コース / ユニット / パート / デッキ、ユニット host = ユニット /
パート / デッキ。これは**全集約の総数**(ページングと無関係)を示すだけの表示で、フィルタ
は持たない(クリックしても何も起きない。本フェーズはフィルタ・ソート切替なしの方針)。
ヘッダ側のお気に入り内訳と数の粒度は対称に保つが、置き場所は遷移先であるこの一覧側。

A-CMT はモデレーション画面なので、一覧・層別サマリとも**非公開配下のコメントも含む**
(作成者/管理者は自分の非公開ドラフトのコメントも削除対象)。これはヘッダの価値メトリクス数
(非公開除外)とは目的が異なる数字で、両者は一致しないことがある(意図的)。

各コメント行に以下を表示する:

- 投稿者名
- 本文
- 投稿日時
- **対象種別ラベル + リンク**: そのコメントがどの対象(コース/ユニット/パート/デッキ)
  に付いたかを示すバッジと、対象へのリンク(UC-45)
- **削除ボタン**(行末。下記 12.5)

並びは**投稿日時の降順固定**。フィルタ・ソート切替は本フェーズでは設けない
(コメントは過疎前提のため軽く始める。将来必要なら種別フィルタ等を追加)。

ページネーションは A-M4 / A-CM3 と同形(投稿日時降順固定・50件/ページ・`has_next` で
ページング)。層別サマリの数は全集約の総数、一覧本体はページ内の実物を並べる。

空状態: コメントが0件のときは「まだコメントはありません」を表示する。

### 12.5 削除(モデレーション / UC-46)

- 各コメント行に**削除**ボタン。押下で確認モーダル →「削除しますか?」→ 確定で

- 監査ログ(誰が削除したか)は本フェーズ対象外。

host が A-C2 / A-U2 のときは、それらが持つ「⚠ 上位権限での介入編集」の文脈を A-CMT に

## 13. 表示順の編集UIとマイ一覧の再定義(A-MC1 / A-MU1 / A-C1 改修)

### 13.0 位置づけ

設計7で、コースメンバー=共同編集者の権限と表示順のスコープを確定したことに伴う一覧画面の改修。仕様の単一情報源はユースケース・画面一覧「権限モデル」節と UC-15b / UC-16 / UC-25。本節はその WF 反映指示。異常系画面の新設ではなく、既存一覧画面への通常UI追加・改修。

前提(スコープ):
- `コース.表示順` = 団体スコープ(団体ポータルの学習者向けコース並び順)。
- `ユニット.表示順` = コーススコープ(コース内の学習者向けユニット並び順。ユニットは高々1コース)。
- 数値は飛び飛び可・重複可・一意性チェックなし。ソート(基準切替)はどの一覧にも置かない。

### 13.1 A-MC1「マイコース 一覧」

- 一覧の範囲を「主催コース＋参加(コースメンバー)コース」に拡張。各行に **主催 / 参加のバッジ**を表示。
- 各行に `コース.表示順` の**数値を表示**(読み取り専用)し、一覧はその数値昇順で並ぶ。**数値の入力・変更は行わない**(表示順の数値指定はコース詳細編集 A-MC2 で行う。一覧は確認と並びの反映のみ)。
- **行内上下ボタンも置かない**(自コースのみの部分ビューでは団体横断の絶対順を表現できないため。コースの並べ替えは A-C1 で行う)。

### 13.2 A-C1「団体コース 一覧」(閲覧集約 → 表示順の並べ替えを追加)

- 現状は閲覧集約として描かれているため、**描き直し対象**。
- 団体の全コースが `コース.表示順` 昇順で並ぶ。ここは表示順の正規スコープ(団体)全体が並ぶので、団体管理者が **各行の行内上下ボタン**で団体ポータル順を直接並べ替えできる(Q2=b の介入)。表示順の数値は各行に**表示**(読み取り専用)。
- **数値の直接入力・変更は行内では行わず**、コース詳細編集(A-C2)で行う(一覧は上下ボタンによる並べ替えと数値の表示のみ)。
- 主催者間の並びの相談はシステム外。最終調整の入口が本画面(上下)＋ A-C2(数値)。

### 13.3 A-MU1「マイユニット 一覧」

- 一覧の範囲を「自投稿ユニット＋自分が関与するコース(主催／参加)の帰属ユニット(他メンバー分含む)」に拡張(「マイ」=関与するもの)。**コースでグルーピング表示**(コースの塊ごと、塊内はコース内表示順。非帰属チョイは別塊)。各行に **所有 / 共同編集のバッジ**を表示(主催コースの他人ユニットも「共同編集」に含める=2区分)。
- 各行の操作(ダウンロード・削除・表示順)は所有・共同編集いずれも可(共同編集は連帯責任)。
- **表示順の編集(行内上下ボタン)が活性になるのは、帰属コースで絞り込んで単一コースの塊だけが並んでいるときに限る**。コース絞り込みなし(全体表示)やコース以外の絞り込み(種別・公開状態など)では非活性(グレーアウト)。
- コース詳細(A-MC2 / A-C2)から帰属ユニット一覧へ遷移する導線では、**遷移先を当該コースで絞り込んだ状態**で開き、その状態で表示順編集を活性化する。

### 13.4 表示順編集の活性条件(絞り込み状態で決まる・画面非依存)

ユニット表示順の上下ボタンが**活性になるのは、一覧が単一コースに絞り込まれているとき**に限る。これは画面(A-MU1 か A-U1 か)ではなく**絞り込み状態**で決まる:

- **単一コース絞り込み時 → 活性**。A-MU1(投稿者本人＋主催者＋当該コースのコースメンバー)でも、A-U1(団体管理者の介入。UC-28)でも上下で並べ替えできる。両者は対称で、操作主体が権限モデルで異なるだけ。
- **非絞り込み(横断表示)・コース以外の絞り込み(種別・公開状態など)→ 非活性**(グレーアウト)。表示順を反映して表示するのみ。コースをまたぐと大小関係が定義できず、部分集合を動かすと歯抜けが出るため。

**遷移時デフォルト絞り込み(両対称)**: コース詳細から帰属ユニット一覧へ遷移する導線は、遷移元コースで絞り込んだ状態で開き、上下を活性化する。主催者・コースメンバーは A-MC2 →(当該コース絞り込みの)A-MU1、団体管理者は A-C2 →(当該コース絞り込みの)A-U1。個々のユニットの数値入力は A-MU2 / A-U2。

なお **A-U1 団体ユニット一覧も、A-C1 と同様に現状は閲覧集約として描かれているため描き直し対象**。各ユニット行に上下ボタンを追加し、単一コース絞り込み時のみ活性(非絞り込み・コース以外の絞り込み時は非活性)とする。

### 13.5 注記

- **数値指定は詳細編集画面のみ**(コース=A-MC2、ユニット=A-MU2、管理者介入=A-C2 / A-U2)。一覧には数値入力フィールドを置かない(数値は表示のみ)。一覧上の操作は上下ボタンによる並べ替え(コース=A-C1、ユニット=単一コース絞り込み時の A-MU1)で、これは詳細編集の補助。
- 所有/主催と共同編集/参加のバッジは、既存の介入編集バナー等と同系統の視覚言語で揃える。
- パート/デッキの表示順はエクセル登場順由来(投稿データ_メディアパック仕様)で、本節の手動指定とは別系統。

※ 本節は既存ワイヤーフレームの変更を要しない(選択式 UI は描画済み)。
連動絞り込みは挙動仕様であり、実装向けの記録。**再レンダリング不要**。

- 対象: A-MU2(マイユニット 詳細/編集)・A-MU3(マイユニット 新規投稿)の
  カテゴリー/サブカテゴリー選択 UI(既存の選択式のまま)
- **連動絞り込み**: カテゴリー選択に応じてサブカテゴリーの選択肢が
  絞り込まれる(例: 「試験対策」を選ぶと「TOEIC」「英検」等が現れる。
  例は説明用で、実際の語彙はマスターに従う)
- カテゴリー未選択の間、サブカテゴリーは非活性
- カテゴリーを変更した場合、選択済みサブカテゴリーはクリアする
- 選択肢の実データはフロントエンド同梱の**静的 JSON** から供給する
  (マスター取得 API は設けない。単一情報源はユースケース仕様書「システム
  前提 / カテゴリー・サブカテゴリーの定義」)。ワイヤーフレーム上は
  ダミー語彙でよい
