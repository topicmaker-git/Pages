# ユーザー別学習状態・プリファレンスデータ保存／取得 要求仕様

## 1. 目的

本書は、英語学習教材サーバーに、認証ユーザーごとの学習状態データおよびプリファレンスデータを保存・取得する仕組みを追加するための要求を定める。

学習状態データは、教材のコース、ユニット、パート、デッキ、カード、センテンス、およびセンテンスと学習方法の組み合わせに関連付けたJSONデータとする。プリファレンスデータは認証ユーザー自身に関連付けたJSONデータとする。JSONの内容は学習アプリの機能と密結合であり、学習方法や学習アプリのバリエーションごとに異なる構造を使用できる。

本書はAPIおよびDBが満たすべき能力を定める。具体的なAPIパス、DBスキーマ、フレームワークおよび通信方式は規定しない。

本要求は、[「ちょい英語ミニブック投稿システム」概念モデル](https://topicmaker-git.github.io/Pages/mermaid.html?choi/%E3%81%A1%E3%82%87%E3%81%84%E8%8B%B1%E8%AA%9E%E3%83%9F%E3%83%8B%E3%83%96%E3%83%83%E3%82%AF%E6%8A%95%E7%A8%BF%E3%82%B7%E3%82%B9%E3%83%86%E3%83%A0_%E6%A6%82%E5%BF%B5%E3%83%A2%E3%83%87%E3%83%AB%E5%9B%B3.mermaid)に従って構築された教材サーバーの拡張である。教材投稿データは[「投稿データ / メディアパック仕様」](https://topicmaker-git.github.io/Pages/choi/%E6%8A%95%E7%A8%BF%E3%83%87%E3%83%BC%E3%82%BF_%E3%83%A1%E3%83%87%E3%82%A3%E3%82%A2%E3%83%91%E3%83%83%E3%82%AF%E4%BB%95%E6%A7%98.md)に従う。

本書の学習状態モデルは、学習者アプリ概念モデルB1（学習成果）の集約成績モデル（カード成績、デッキ成績、パート成績、ユニット成績およびコース成績）を置き換える。教材サーバー側に集約成績および成績履歴を持たず、保存された最新結果から学習アプリが導出する。ただし、B1の単語成績は本書の置き換え対象外であり、単語単位の成績管理は企画上保留である。

## 2. 基本モデル

### 2.1 保存単位

認証ユーザーごとに、次の8種類のJSONデータを独立して保存できる。

| 保存単位 | 完全な識別情報 |
|---|---|
| 認証ユーザー | 認証ユーザー |
| コース | 認証ユーザー + コースID |
| ユニット | 認証ユーザー + ユニットID |
| パート | 認証ユーザー + パートID |
| デッキ | 認証ユーザー + デッキID |
| カード | 認証ユーザー + デッキID + カードハッシュ |
| センテンス | 認証ユーザー + デッキID + カードハッシュ + センテンスハッシュ |
| センテンス×学習方法 | 認証ユーザー + デッキID + カードハッシュ + センテンスハッシュ + 学習方法識別子 |

同じ教材対象であっても、認証ユーザーが異なれば別のデータとして扱う。

センテンス×学習方法のデータは、学習方法識別子ごとに独立する。ある学習方法の書き込みによって、同じセンテンスに対する別の学習方法のデータを変更してはならない。

認証ユーザー単位のJSONは、そのユーザーが使用する学習アプリのプリファレンス保存先とする。コース以下の7種類のJSONは、それぞれの教材対象に関する学習状態データの保存先とする。

### 2.2 共通フィールドとJSONペイロード

各保存データは、サーバーが共通に管理する固定フィールドと、学習アプリに密結合した自由形式のJSONペイロードフィールドに分ける。

固定フィールドとして、次を保持する。

- 第2.1節で定めた完全な識別情報
- JSONペイロードの形式バージョン
- 最終更新日時

これらは概念上、保存レコードの独立したDBフィールドであり、自由形式JSONペイロードの一部ではない。物理的なテーブル構成、フィールド名およびデータ型は本書では規定しない。

JSONペイロードについては、次のとおりとする。

- ペイロードの項目および意味は学習アプリ側の仕様に従う。
- サーバーは、ペイロードが正しいJSONであることを確認する。
- サーバーは、ペイロードを解釈、変換せず、保存時の意味を失わせない形で読み出せるようにする。
- 読み出し時には、ペイロードとともに形式バージョンを取得できる。
- 形式バージョンが異なる既存ペイロードの解釈、移行、置換または破棄は学習アプリが決定する。サーバーによる自動変換は要求しない。
- 8種類すべての保存単位へ常にデータを作成する必要はない。学習アプリは、使用する保存単位だけにデータを保存できる。

JavaScriptからセンテンス×学習方法の保存レコードを読み出す場合は、概念的には次のようになる。

```javascript
const savedRecord = {
  userId: "authenticated-user-id",
  targetType: "sentence-learning-method",
  deckId: "deck-id",
  cardHash: "sha256-card-hash",
  sentenceHash: "sha256-sentence-hash",
  learningMethod: "word_order",
  payloadFormatVersion: 1,
  updatedAt: "2026-08-06T10:00:00Z",

  // このフィールドだけが学習アプリ密結合の自由形式JSONテキスト
  payload: '{"points":8,"maximumPoints":10,"errorCount":1,"outcome":"completed"}'
};

const learningState = JSON.parse(savedRecord.payload);

if (savedRecord.payloadFormatVersion === 1) {
  showScore(learningState.points, learningState.maximumPoints);
}
```

`payload` 以外は共通の固定フィールドである。`payload` の内容だけを学習アプリが解釈する。認証ユーザーは認証コンテキストによって確定し、クライアントから渡された `userId` の値だけを根拠にしてはならない。

このコードはデータ境界を示す概念例であり、プロパティ名、日時表現およびAPIの入出力形式を確定するものではない。

### 2.3 最新データ

各保存単位の完全な識別情報に対して、現在有効なJSONデータを1件保持する。

同じ完全な識別情報に再度書き込んだ場合は、既存データを新しいJSONデータで置き換える。全変更履歴または全学習試行履歴の保存は要求しない。

同じ完全な識別情報への並行書き込みは後着優先（last-write-wins）とする。書き込み順序の調停および競合検出は要求しない。

データが存在しない状態と、JSON内の値が `0`、`false`、空文字列または空配列である状態を区別できるものとする。

## 3. 教材対象の識別

### 3.1 恒久識別子とコンテンツハッシュ

- コース、ユニット、パートおよびデッキは、教材サーバーが管理する恒久識別子（本書ではコースID、ユニットID、パートID、デッキIDと呼ぶ）によって識別する。識別子の形式は本書では規定せず、教材サーバーの既存の設計・実装が持つ識別子をそのまま使用してよい。
- これらの識別子は、教材内容の編集および投稿データの差分更新を跨いで不変であるものとする。
- これらの識別子は、種別ごとに大域一意であり、上位階層の識別子を伴わずに単独で教材対象を同定できる。
- 投稿データ（エクセル）の編集IDは、更新対象行の同定（同じ行の内容の書き換え）のための識別子であり、特定の学習内容に対する学習状態の識別という本書のドメインには使用しない。
- カードは、カードを構成する全センテンスから生成したカードハッシュによって識別する。
- センテンスは、正規化後の英文から生成したセンテンスハッシュによって識別する。
- カードハッシュおよびセンテンスハッシュの生成にはSHA-256を使用する。

カードハッシュの生成では、センテンスの順序、話者の区別およびセンテンス間の境界を維持する。

### 3.2 センテンスの正規化

センテンスハッシュの生成前に、英文へ次の処理を記載順に適用する。

1. Unicode NFKCで正規化する。
2. BOM（U+FEFF）、ゼロ幅スペース（U+200B）およびソフトハイフン（U+00AD）を除去する。
3. 左右のシングルクォーテーション（U+2018、U+2019）をASCIIアポストロフィ（U+0027）へ変換する。
4. スラッシュ（U+002F）をASCIIスペース（U+0020）へ変換する。
5. Unicodeの `White_Space` プロパティに該当する文字をASCIIスペースへ変換する。
6. ASCII英大文字 `A`～`Z` を `a`～`z` へ変換する。
7. 連続するASCIIスペースを1個へ圧縮する。
8. 先頭および末尾のASCIIスペースを除去する。

句読点、ハイフン、ダイアクリティカルマーク、短縮形と展開形の違い、および語順は維持する。

### 3.3 ハッシュ生成規則

本規則のバージョンを `v1` とする。

センテンスハッシュは、正規化後の英文をUTF-8で符号化したバイト列にSHA-256を適用して生成する。

カードハッシュは、カード内の各センテンスを教材上の順序で並べ、次の要素を持つJSON配列として直列化した後、そのUTF-8バイト列にSHA-256を適用して生成する。

```json
[{"speaker":"a","sentence":"it's nice to meet you today."},{"speaker":"b","sentence":"i look forward to working with you."}]
```

直列化では次の規則を使用する。

- 配列要素の順序は教材上のセンテンス順序とする。
- 各要素のキーは `speaker`、`sentence` の順とする。
- `speaker` の値にも第3.2節の正規化を適用する。
- 話者を持たないセンテンス（例: デッキタイプ「文」の教材）では、`speaker` の値を空文字列とする。
- `sentence` の値には第3.2節で得た正規化後の英文を使用する。
- キー、文字列値、配列およびオブジェクトの区切り以外に空白を出力しない。
- 文字列内の引用符（U+0022）は `\"`、バックスラッシュ（U+005C）は `\\` としてエスケープする。
- U+0000～U+001Fは、小文字の16進数字を使用した `\u00xx` 形式でエスケープする。
- それ以外の文字は `\u` 形式へ変換せず、Unicode文字として出力する。
- 文字列をUTF-8で符号化し、BOMを付けない。

ハッシュ値の表現は、SHA-256の32バイトを小文字の16進数64文字で表したものとする。

ハッシュは、教材作成ツールおよび学習アプリが本書の規則に従って算出する。教材サーバーは、受け取ったハッシュ値を識別子として保持するのみとし、ハッシュの生成、再計算および検証は要求しない。

#### 3.3.1 検証用テストベクター

正規化およびハッシュ生成の実装は、次のテストベクターで照合できる。値は第6章のサンプル教材（`choi/ab/sample/sampleS_unit.xlsx`）の実データから、本書の規則により導出したものである。

**センテンスハッシュ**（サンプル教材カード1のセンテンス1）

- 原文: `It's nice / to meet / you today.`
- 正規化後: `it's nice to meet you today.`
- センテンスハッシュ: `353380bfc96b926ea44f670303b62de50bd6d492533435b408038db977be01f8`

**カードハッシュ**（サンプル教材カード1、6センテンス）

直列化結果（1行の文字列。話者には非ASCIIの `類似a` / `類似b` が現れる）:

```json
[{"speaker":"a","sentence":"it's nice to meet you today."},{"speaker":"b","sentence":"i look forward to working with you."},{"speaker":"類似a","sentence":"i'm glad to meet everyone here."},{"speaker":"類似b","sentence":"i'm excited to work together soon."},{"speaker":"類似a","sentence":"great to meet the team today."},{"speaker":"類似b","sentence":"let's learn from each other this month."}]
```

- カードハッシュ: `ddc949dcfe6ab02a100ca4d39e1ceb9074066760a9946532f8841e7ad39f012b`

### 3.4 教材データの成立条件

次の条件を満たさない教材データは、本書の識別体系のもとでは成立しない。

- カード内に、正規化後の内容が同一となるセンテンスが複数存在しない。
- 同一デッキ内に、同じカードハッシュとなるカードが複数存在しない。
- センテンスの正規化結果が空でない。
- センテンスの順序が確定できる。

これらの成立条件は、教材データを作成する側（今後予定されているAB会話データ変換ツール等の教材作成ツール）が保証する。教材サーバーによる登録時の検査は要求しない。

話者の欠如は不成立条件としない。話者を持たない教材では、第3.3節のとおり `speaker` を空文字列として直列化する。

これらが保証されるため、センテンスの位置番号を学習状態データの識別情報に含める必要はない。

なお、本要求の導入時点でプロジェクトは開発中であり、維持すべき既登録の教材および学習状態データは存在しない。既存データへの遡及的なハッシュ付与および移行は要求しない。

### 3.5 教材内容修正時の扱い

教材内容の修正によってカードハッシュまたはセンテンスハッシュが変化した場合は、成績記録対象の教材が入れ替わったものとして扱う。

- 新しいハッシュの教材と旧ハッシュの教材との間で、学習状態データの連続性を考慮しない。
- 旧ハッシュに関連付けられた学習状態データを、新しいハッシュへ移行しない。
- 旧ハッシュに関連付けられた学習状態データは削除せず、そのまま残置してよい。
- 旧ハッシュに関連付けられた学習状態データは、教材範囲を指定した一括読み出しに混在しうる。学習アプリは、自ら算出した現在のハッシュ集合と照合し、一致しないデータを現在の教材へ結び付けない（第5.6節の未登録判別と同じ扱い）。
- 学習アプリは、一致しないデータを削除してよい。旧ハッシュのデータの整理は学習アプリが行う。

なお、教材内容の修正による旧ハッシュデータの残置（本節）と、教材実体の削除による連鎖削除（第4章）とは非対称であるが、これは意図的である。サーバーはハッシュを不透明な識別子として保持するのみで、教材内容を知らず新旧を区別できないため残置する。一方、コース、ユニット、パートおよびデッキの削除は、サーバーが実体として管理する参照先の消滅であり、教材内容を知らなくても連鎖削除を実行できる。この差は学習者データの保護方針の違いではなく、サーバーの不可知性の境界に由来する。

### 3.6 識別情報の提供

学習アプリは、取得した教材に対応するコースID、ユニットID、パートIDおよびデッキIDを教材サーバーから参照できるものとする。パートを持たない教材ではパートIDを要求しない。コースに帰属しないユニットではコースIDを要求しない。

カードハッシュおよびセンテンスハッシュは、教材サーバーが提供するのではなく、学習アプリが取得した教材内容から第3.2節および第3.3節の規則（バージョン `v1`）に従って算出する。教材作成ツールも同一規則で算出し、第3.4節の成立条件を保証する。

## 4. 書き込み要求

- 認証ユーザー本人のデータとして、第2.1節の各保存単位へJSONを書き込める。
- 書き込み時にJSONペイロードの形式バージョンを指定する。
- 認証ユーザー単位には、教材対象を指定せずにプリファレンスJSONを書き込める。
- 書き込み対象のうち、教材サーバー上に実体を持つコース、ユニット、パートおよびデッキについては、存在することを確認する。カードおよびセンテンスはサーバー上に実体を持たないため、存在および帰属の確認は要求しない。
- 認証ユーザーが閲覧できない教材（コース、ユニット、パートまたはデッキ。閲覧可否の定義は第5.6節に同じ）への書き込みは受け付けない。存在の確認のみとした場合、識別子の試行により非公開の教材の実在を推測できるためである。ただし、認証ユーザー本人のデータの削除は、閲覧資格の有無にかかわらず受け付ける（旧データの整理を学習アプリの責務とする第3.5節との整合。削除要求への応答から、非公開の教材の実在を推測できる情報を返さない）。
- 書き込み対象の指定には、第2.1節の完全な識別情報のみを使用し、上位階層の識別子を併せて指定しない。第3.1節のとおり識別子は単独で教材対象を同定でき、所属関係は教材サーバーが保持するため、上位階層の識別子による帰属確認を要求しない。
- センテンス×学習方法では、学習方法識別子を指定して書き込める。
- 学習方法識別子は、ASCII英小文字（`a`～`z`）、数字（`0`～`9`）およびアンダースコア（`_`）で構成し、64文字以内とする。
- サーバーは、少なくとも10,000バイトのJSONペイロードを保存し、読み出せるものとする。サイズは、ペイロード本体のUTF-8エンコード後のバイト数で計測する。サーバーはこれを超える範囲で上限を定めてよい。上限を超過した書き込みは失敗させる。
- サーバーは、防護目的で、認証ユーザーとデッキの組み合わせごとに、カード、センテンスおよびセンテンス×学習方法の保存件数の上限を定めてよい。上限は、教材の構造（デッキ内のカード数、センテンス数および学習方法数）による正当な学習利用が到達しない十分大きな値とする。上限を超過する書き込みは失敗させる。認証ユーザーあたりの総保存件数の上限は定めない。利用量の割り当て（料金プラン等）は本書の範囲外とする。
- 認証ユーザー本人のデータについて、保存単位ごとに削除できる。削除後は、その完全な識別情報のデータが存在しない状態（未登録）へ戻る。
- 教材（コース、ユニット、パートまたはデッキ）が削除された場合、サーバーはその配下に紐づく学習状態データを削除する。デッキの削除により、配下のカード、センテンスおよびセンテンス×学習方法のデータもまとめて削除される。お気に入り・コメントの連鎖削除と同じ扱いとする。
- 認証ユーザーのアカウントが削除（退会）された場合、サーバーはそのユーザーの全学習状態データおよびプリファレンスデータを削除する。
- 教材の削除およびアカウントの削除に伴う上記の削除は、第1章の最新結果のみを保持するモデルに基づく意図的な設計であり、削除の猶予期間およびデータ保護期間は設けない。
- 他の認証ユーザーのデータを書き込み、削除してはならない。
- 書き込みまたは削除に失敗した場合、既存の有効なJSONデータを壊したり、不完全なデータで置き換えたりしてはならない。

## 5. 一括読み出し要求

認証ユーザー本人について、教材の学習に必要なJSONデータを次の単位で一括して読み出せる。

認証ユーザー自身に紐づくプリファレンスJSONは、教材階層とは独立して読み出せる。

### 5.1 認証ユーザー単位（全教材）

認証ユーザー本人について、全教材にわたる学習状態データ（コース、ユニット、パート、デッキ、カード、センテンスおよびセンテンス×学習方法の各JSON）を一括して読み出せる。

この読み出しでは、データが存在する保存単位のみを返してよい。教材全体を走査して未登録の保存単位を列挙することは要求しない。

### 5.2 コース単位

指定コースについて、次のデータを一括して読み出せる。

- コースJSON
- コースに属する各ユニットのユニットJSON
- 各ユニット配下のパートJSON、デッキJSON、カードJSON、センテンスJSON、およびセンテンス×学習方法JSON

### 5.3 ユニット単位

指定ユニットについて、次のデータを一括して読み出せる。

- ユニットJSON
- ユニットに属する各パートのパートJSON
- デッキJSON
- 各デッキに属するカードJSON
- 各カードに属するセンテンスJSON
- 各センテンスに属する、学習方法別JSON

パートに属さずユニット直下に置かれたデッキも存在できるため、ユニット単位の読み出しはパートの有無にかかわらず、そのユニットに属する対象デッキを取得できるものとする。

### 5.4 パート単位

指定パートについて、パートJSONと、そこに属する全デッキのデッキJSON、および各デッキ配下のカード、センテンス、センテンス×学習方法のJSONを一括して読み出せる。

### 5.5 デッキ単位

指定デッキについて、デッキJSONと、その配下のカード、センテンスおよびセンテンス×学習方法のJSONを一括して読み出せる。

### 5.6 一括読み出しの共通条件

- 返される各JSONが、どのコース、ユニット、パート、デッキ、カード、センテンスおよび学習方法に属するか判別できる。
- 各JSONペイロードについて、形式バージョンおよび最終更新日時を取得できる。
- 教材範囲を指定した読み出し（コース、ユニット、パートおよびデッキ単位）では、サーバー上に実体を持つ保存単位（コース、ユニット、パートおよびデッキ）について、データが存在しない場合に未登録であることを判別できる。カード、センテンスおよびセンテンス×学習方法については、データが存在するものだけを返してよい。教材内容を保持する学習アプリは、自ら算出したハッシュ集合との差分により未登録を判別できる。
- いずれの読み出しでも、認証ユーザーが閲覧できる教材（コース、ユニット、パートおよびデッキ）に属する学習状態データのみを返す。身元ゲート（非公開化、団体限定公開化、または外部公開ロックによる格下げ。正本は `choi/ちょい英語ミニブック投稿システム_ユースケース_画面一覧.md` の公開範囲の定義）により認証ユーザーが閲覧資格を失った教材のデータは返さない。閲覧可否の評価はサーバーの責務である（カードおよびセンテンスの新旧判別を学習アプリのハッシュ照合に置く第3.5節の扱いとは層が異なる。コース〜デッキはサーバーが実体と公開範囲を管理する層であるため）。
- この絞り込みは読み出し時のものであり、データは削除しない。サーバーが利用者の操作によらず学習状態データを削除するのは、教材実体の削除およびアカウントの削除（いずれも第4章）の場合のみであり、閲覧可否の変動は削除に関係しない。閲覧資格が回復した場合、その教材の学習状態データは再び返される。
- 参照（リンク・お気に入り等）を持つ会員がアクセスできる公開範囲（プライベート公開＝unlisted）は、閲覧可能な状態が続くため、この絞り込みの対象にならない。
- 同じセンテンスに複数の学習方法別JSONがある場合、それぞれを区別できる。
- 他の認証ユーザーのJSONを読み出してはならない。
- 一括読み出し時点で教材の所属関係（コースとユニットの帰属関係を含む）が変わっている場合は、読み出し時点の所属関係に従う。

### 5.7 分割取得（ページング）

第5.1節から第5.5節の各読み出しは、分割取得（ページング）に対応する。

- レスポンスには、続きの有無と、続きを要求するための継続情報が含まれる。継続情報は学習アプリにとって不透明であり、学習アプリはその内容を解釈せず、次の要求にそのまま渡す。継続情報は有効期限を持ってよい。失効または無効な継続情報による要求は失敗し、学習アプリは最初から取得し直す。
- 1回の読み出し（初回の要求から続きがなくなるまでの一巡）において、読み出し開始時点で存在し、一巡の完了まで存在し続け、かつ第5.6節の閲覧資格を保ち続けたレコードは、ちょうど1回返される。
- 一巡の途中で書き込みが行われた場合、取得中に新規作成されたレコードはその一巡では返されないことがある（次の読み出しで返される）。一巡の途中で更新されたレコードも、ちょうど1回返される（返される内容は更新前後のいずれでもよい）。一巡の途中で削除されたレコード、および閲覧資格を失った教材のレコードは、返されないことがある。一巡の結果がある瞬間の完全なスナップショットであることは要求しない（第2.3節の後着優先・競合検出非要求と整合する）。
- 1回の応答に含める件数（ページサイズ）はサーバーが定める。
- 教材範囲を指定した読み出しにおける未登録の判別（第5.6節）は、一巡の完了をもって確定する。

## 6. 現行プロトタイプでの利用例

サンプル教材一式（`choi/ab/sample/` の `sampleS_unit.xlsx` ほか）およびAB会話学習アプリのプロトタイプを、今回の学習アプリにおける具体例とする。教材の意味論は `choi/ab/AB教材規約.md` に従う。

サンプル教材は、パートを使用しない1デッキ、5カード、各カード6センテンスで構成される。1カードのセンテンスは、A、B、類似A 2件、類似B 2件である。

### 6.1 使用する保存単位

現行プロトタイプでは、汎用的な保存能力を次のように使用する。

- 認証ユーザーJSON：学習アプリのプリファレンス
- カードJSON：カードのお気に入り状態
- センテンス×学習方法JSON：語句並べ替えおよび発音の最新学習結果

現行プロトタイプでは、コースJSON、ユニットJSON、パートJSON、デッキJSONおよび学習方法を伴わないセンテンスJSONに固有の永続データを置くことを必須としない。

お気に入りの対象はカードであり、個々のセンテンスではない。

なお、コース、ユニット、パートおよびデッキに対するお気に入りは、概念モデルに定義済みの「お気に入り」（ポリモーフィック関連）として教材サーバー側で実装するものであり、本機構では扱わない。本機構をお気に入りに使用するのは、学習アプリがカードまたはセンテンスに対してアプリ私的なお気に入り機能を提供する場合に限る。

### 6.2 成績対象センテンス

1回の学習ページでは、AまたはBのうち今回の対象となるメインセンテンスと、同じ側の類似センテンス2件を成績対象とする。類似センテンスが存在しない場合、そのセンテンスの学習結果は要求しない。

相手側のセンテンスは会話の文脈として表示・再生するが、その学習ページでは成績対象としない。A側学習とB側学習は独立して成立する。

### 6.3 語句並べ替え

学習方法識別子は `word_order` とする。

最新結果のJSONには、次の値を保持する。

- 獲得ポイント
- 満点
- 誤答回数
- 終了結果

終了結果は、最後まで完成した `completed`、または3回の誤答で途中終了した `stopped_after_three_errors` のいずれかとする。

- メインセンテンスは、正解した1語につき2ポイントとする。
- 類似センテンスは、正解した1語につき1ポイントとする。
- 誤答しても、それまでの正解語と獲得ポイントを維持する。
- 誤答が3回に達した時点で問題を終了する。
- 満点は、対象センテンスの語数と1語あたりのポイントから算出する。
- 完成時または3回の誤答による終了時に結果を確定して書き込む。

### 6.4 発音

学習方法識別子は `pronunciation` とする。

最新結果のJSONには、次の値を保持する。

- 獲得ポイント
- 満点
- 一致語数

- 発音の満点は対象センテンスの語数とする。
- 音声認識された語を、正解文の語順を維持して照合する。
- プロトタイプで定義されている短縮形と展開形の対応を同等に扱う。
- 一致語数が3語以上の場合、一致語数を獲得ポイントとする。
- 一致語数が2語以下の場合、獲得ポイントを0とする。
- 音声認識結果の採点確定時に書き込む。
- 発音の更新によって、同じセンテンスの語句並べ替え結果を変更してはならない。

音声録音データおよび音声認識結果全文は永続保存しない。

### 6.5 集計と復習

センテンス総合得点は、最新の語句並べ替え得点と最新の発音得点の合計とする。カードおよびデッキの得点は、配下の成績対象センテンスの最新結果から導出し、独立した一次記録とはしない。

現行プロトタイプでは、発音が未実施の場合は獲得ポイントを0として扱い、発音満点を総合満点に含める。このような総合得点および総合満点の算出規則は学習アプリが決定し、教材サーバーが解釈または管理することは要求しない。

デッキ内の5カードのうち、1カードは扉ページのAB会話練習に使用し、残り4カードを成績記録対象とする。扉ページでの録音および音声認識結果は永続保存しない。

どの4カードを成績記録対象とするかは、教材構成と利用方法を密に知る学習アプリが決定する。教材サーバーが成績対象カードを選定または管理することは要求しない。

A側とB側は別々の学習単位とする。対象方向の成績記録対象4カードすべてに必要な最新結果がある場合、その方向のデッキ学習を完了済みと判定する。

自動復習判定は、一括取得した最新結果を使用して学習アプリ側で行う。全試行履歴を使用しない。

### 6.6 セッション内確認履歴

現在の学習セッションで学習済みページを確認するための履歴は、クライアント内で一時保持し、サーバーへ永続保存しない。

## 7. 想定規模

本章は容量・性能の見積り根拠として想定規模を示す。超過を禁止する規定ではない。

- ユニットの標準規模は、20デッキ、100カード、500センテンス程度とする。これがミニブックとしての「ユニット」の設計単位である（これを大きく超える教材は、複数ユニットからなるコースとして構成する）。
- 1ユニットあたりの学習状態レコード数は、現行プロトタイプの使用構成（第6.1節: カードおよびセンテンス×学習方法2系統）で最大1,100件程度となる。全保存単位を使用する場合は約1,600件強（パート数による）となる。
- JSONペイロードの実効サイズは100バイト級（第6.3節・第6.4節の成績項目）、設計上の目安は1レコードあたり1,000バイト程度とする。第4章の10,000バイトは、正当な学習利用が到達しない水準に置いた下限保証であり、平均サイズの想定ではない。
- 想定ユーザー数は当面1万人とする。現行enHackアプリの登録ユーザーが1万人であり、本システムはその一部の関心層からの立ち上がりとなるため、1万人を収容できれば十分である。これを超える成長への対応は、本章の見積りの改訂等の枠組みで行う。
- 第5章の一括読み出しは分割取得（第5.7節）により行う。ページサイズは1,000件前後を想定する。この規模では、ユニット単位（第5.3節）、パート単位（第5.4節）およびデッキ単位（第5.5節）の読み出しは1〜2回で一巡する。認証ユーザー単位（第5.1節）およびコース単位（第5.2節）の一巡回数は、学習状態を持つユニット数に比例する。
- 第5章は、読み出しの追加の絞り込みパラメータ（更新時刻による差分取得等）の提供を妨げない。
