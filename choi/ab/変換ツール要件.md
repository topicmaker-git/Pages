# 変換ライン要件(変換 / メディア生成 / 検査) — AB会話教材 → ミニブック投稿形式

## 0. 位置づけ

AB会話教材の元データ(7列 xlsx)を、ちょい英語ミニブック投稿システムの
投稿形式(投稿データ_メディアパック仕様。以下「投稿仕様」)へ変換・納品
する**教材作成ライン(3ツール)**の要件を定める。データの意味論(スキーマ・
記法)の正本は `AB教材規約.md`(同区画。以下「規約」)であり、本書は変換・
生成・検査の処理要件のみを定める。**実装本体は Pages 管理外の独立開発
ディレクトリ**(Claude Code 管轄)。設計14 の `sample/gen_sample_s.py` は
本要件の縮約実装(ID 1〜5・単一デッキ。下表の3工程を1本にまとめた形)で
ある。

ラインは次の3工程で構成し、本書の各節はそれぞれの工程に帰属する:

| 工程 | 入力 | 出力 | 本書の該当節 |
|---|---|---|---|
| 変換ツール | AB 7列 xlsx(1ユニット) | 投稿用14列エクセル(メディア3列・編集ID 3列は空欄) | §1・§2・§3 |
| メディア生成ツール | 変換ツールの出力エクセル | audio.zip / image.zip + メディア3列を記入したエクセル | §4・§5 |
| 検査ツール | エクセル + 2つの zip(+ メディア生成ログ) | 合否判定(全項目パスまで納品しない) | §6・§8 |

投稿(§7・UC-20)は従来どおりライン外である。

**ユースケース**: UI 検証済みのプロトタイプアプリによってデータ形式は
確定している。その形式を見本に、生成AIと人間が教材データを 7列 xlsx
として作成し、人間によるデータ校正(内容面)を経たファイルが本ラインの
入力となる。入力は**1ファイル = 1ユニット**であり、1回の変換で1ユニット分を
出力する(§1.1)。プロトタイプアプリのエクスポート機能が出力するファイルは
形式の見本であって、本ラインの入力ではない(見本の現物を
`sample/AB教材Excelパック_2026-09-01-08-21.xlsx` に収める)。本ラインは
§1 の入力契約(変換ツール)と §6 の出口検査(検査ツール)により、
量産データに対する機械的検査(形式面)の受け入れゲートを兼ねる —
記法違反・チャンク数不一致・ハッシュ重複等は人間校正では拾えず、
本ラインが全件検査で塞ぐ。変換結果の投稿システムへの投稿は本書の
要求範囲外である。

## 1. 入力

### 1.1 元データ(AB 7列 xlsx)

ヘッダーは次の7列で固定: **ID / カテゴリー / テーマ / 2会話 /
類似フレーズA / 類似フレーズB / AB会話の話者プロファイル**。
1データ行 = 1セット(1カード)。

**1ファイル = 1ユニット**とする。入力ファイルはカテゴリー列に単一の値のみを
持ち、それが1ユニットに対応する。複数カテゴリーの混在は変換エラーとして
停止する。ユニットは投稿の単位(投稿仕様 §5.3 のメディア名前空間の単位でも
ある)であり、変換もその単位で回す。

入力ブックのうち、ヘッダー行(1行目)がこの7列に完全一致するシートを
読む。該当シートが存在しない場合、および複数存在する場合は、変換エラー
として停止する(付帯シートの有無に依存しない同定規則)。

### 1.2 セル内記法(元形式)

| 列 | 記法 |
|---|---|
| テーマ | 2行(1行目 = 英名、2行目 = 和名) |
| 2会話 | 4行(`A：`英文 / `（`語順訳`）` / `B：`英文 / `（`語順訳`）`) |
| 類似フレーズA / B | 4行(英文 / `（`語順訳`）` × 2組) |
| AB会話の話者プロファイル | 2行(`A: ` / `B: ` 各1行の自由文) |

- **コロンの字種が列で異なる**点に注意: 「2会話」の発話マーカーは
  **全角コロン**(`A：` / `B：`)、「AB会話の話者プロファイル」の行頭は
  **半角コロン+空白**(`A: ` / `B: `)。マーカーは剥がして取り出す
- 語順訳は全角括弧`（…）`で囲まれ、区切りに全角空白(U+3000)を含みうる。
  変換で半角スペース1個に置換・圧縮・トリムする(投稿仕様 §1.7.1 の
  正規化と同等の処理を変換側で先行適用)
- 記法違反(行数不一致・接頭辞欠落・括弧不正)は**変換エラー**として
  停止する(黙って補正しない)
- **セル内改行コード**: セル内改行は LF とは限らず CRLF がありうる。
  CR は OOXML のエスケープ(`_xHHHH_` 形式)として格納され、Excel 本体は
  開くときに CR へ復号するが、**openpyxl 等のライブラリは復号せず、
  格納された綴りのまま literal 文字列として返す**。16進部の大小文字と
  文字列の格納方式は生成元に依存する(sample/ に収めた見本
  `AB教材Excelパック_2026-09-01-08-21.xlsx` は Excel の開閉保存を経た
  現物で、共有文字列方式・大文字 `_x000D_`。Excel を経る前の
  生エクスポート〈SheetJS 製〉はシート XML 直接埋め込み・小文字
  `_x000d_` — いずれも実測)。行分割の前に、literal `_x000D_` /
  `_x000d_` および生の CR(U+000D)を除去し、LF で行分割すること。
  除去を知らない実装は行数不一致の誤検出・行末ゴミを起こす
- **空行の読み飛ばし**: 行分割後、空行(空文字列の行、および空白類のみの
  行)は意味を持たない行として読み飛ばし、本節の行数・記法は**読み飛ばし後の
  行に対して**検査する。これは記法の解釈規則であって内容の補正ではない
  (「黙って補正しない」の対象外)。元データには実例がある(ID 76〜80 の
  テーマは 2会話・類似フレーズ各セルでペア間に空行を1行含む)

### 1.3 ID とデータ量

- **ID はユニット内で一意**であること。重複は変換エラーとして停止する。
  1 起点であること・連番であること・欠番がないことは要求しない(数値で
  ある必要もない)。ID はセット(カード)を入力内で同定するためのキーで
  あり、出力への現れ方は本書では規定しない
- **ユニット内のテーマ数、テーマ内のセット数は固定しない**。デッキ数・
  カード数はデータ次第であり、本ラインは数量を検査しない。教材階層の
  数量上限は投稿システム側のスキーマ制約(投稿仕様 §4.3)が持つ

> 旧規定(改訂前)は「1テーマ = 5セット固定、1カテゴリー = 20テーマ」を
> 元データの前提とし逸脱を変換エラーとしていたが、出所は設計12
> サンプルデータ作成指示書 §0 の範囲指定であり、サンプル1本のための
> 範囲指定が量産の停止条件へ昇格していた。教材構造上の根拠がないため
> 撤回した。「ID は元データ全体の通し番号(グローバル一意)」も、メディアの
> 名前空間はユニット単位(投稿仕様 §5.3 の
> `{ユーザーID}/{ユニットID}/{ファイル名}`)でありユニット内一意で
> 足りるため撤回した。

## 2. 展開規則

- **出力の単位**: 入力1ファイル(= 1ユニット、§1.1)から投稿用エクセル
  1本を出力する。メディアパック(`audio.zip` / `image.zip`)はメディア
  生成ツールが作る(§4・§5)。1ユニットの納品物は、エクセル1本・
  `audio.zip`・`image.zip` の3点が揃った一式である。ユニット名・
  category 属性は投稿 UI で設定(カテゴリー列の値を用いる)
- **行展開**: 元データ1行(1 ID)→ 6行(規約 §2 の話者・行順)。
  英文・語順訳の組は、2会話から A/B 各1、類似フレーズA から 類似A 2、
  類似フレーズB から 類似B 2 を取り、行順は A, B, 類似A(1), 類似B(1),
  類似A(2), 類似B(2)
- **チャプター名** = テーマ和名。**シーン名** = 「セット{k}」
  (k = デッキ内登場順連番・1起点。規約 §4)。**注意**: 縮約実装
  `gen_sample_s.py` は元 ID 基底(`セット{ID}`)であり、そのまま流用
  するとデッキごとに 1 から振り直されず規約 §4 違反となる(検査6 で
  捕捉可能だが、実装段階で修正すること)
- **デッキ属性・カード属性**: 規約 §3 のスキーマで組み立て、ミニファイ
  JSON をデッキ/カードの先頭行のみに記入(投稿仕様 §1.7.2)。
  カード属性の `speakers` はプロファイル2行の生文字列
- **和訳列**: 全行空欄(規約 §5。元データに対応データなし)

## 3. 出力形態(投稿用エクセル)

- **14列構成**(パート不使用)。列順とヘッダー名は設計14 サンプルの形を
  標準とする: デッキ編集ID / カード編集ID / センテンス編集ID /
  チャプター名 / シーン名 / 話者 / 英会話 / 手順3で作成した語順訳 /
  和訳 / 音声ファイル / デッキ画像 / カード画像 / カード属性 / デッキ属性。
  投稿仕様 §7 手順2 の DL 標準列構成(パート未使用14列)と**列順・
  列集合が同形**で、編集ID 3列は**ヘッダーのみ・全行空欄**
  (新規投稿 UC-20 用)。注: DL 側実装は語順訳列を「語順訳」の列名で
  出力する(投稿仕様自体も §1.2 は「手順3で作成した語順訳」、
  §9.2/§9.5 は「語順訳」と表記が揺れており、実装は両ヘッダーを既知
  として受理する)。本ラインの出力は §1.2 表記で統一し、ヘッダー名
  までの完全一致は要求しない
- **ヘッダー名は投稿仕様 §1.2 の既知ヘッダーを厳守**すること。特に
  語順訳列は「手順3で作成した語順訳」(投稿仕様 §4.1 により未知ヘッダーは
  無警告で読み飛ばされるため、誤記 = 無警告のデータ欠落となる)
- **全セルを文字列型で書き出す**(投稿仕様 §1.7.1 のセル型推奨)
- 出力値は正規化冪等であること — セル値に改行・タブ・連続空白・
  U+3000・前後空白を含まない(投稿仕様 §1.7.1)
- **メディア3列**(音声ファイル / デッキ画像 / カード画像)は、**変換
  ツールの出力時点では全行空欄**とし、メディア生成ツールが記入する
  (§4・§5)。編集ID 3列は最後まで全行空欄(UC-20)。メディア生成
  ツールがエクセルへ書き戻す際も、本節の器の規定(文字列型・正規化
  冪等・ヘッダー名)を崩さないこと(崩れると検査3・検査4 で落ちる)

## 4. 音声生成

本節は**メディア生成ツール**の要件である。入力は変換ツールの出力エクセル
1本で足りる — 音声生成の素である話者プロファイルはカード属性 `speakers`
(規約 §3.2)に、画像生成の素であるテーマ英名・和名はデッキ属性
`title_en` / `title_ja`(規約 §3.1)に保存済みであり、元データ(7列
xlsx)を再度読む必要はない。

- **方式**: 話者プロファイル(元データ由来)→ プロンプト → Gemini 音声
  生成 → mp3。レディメイドのボイス対応表方式は不成立(プロファイルは
  自由文のため)
- **数量**: 1カード6本。ユニットあたりの本数はカード数次第で、
  `sample/` の量産データ見本(3カテゴリー・各20テーマ×5セット)を
  ユニット単位に割った場合は 600本/ユニット・計 1,800本になる。
  現物生成済みは「よろしく、英語なら？」の30本のみ(`sample/audio.zip`)
- **命名**: 制約は**ユニット内で一意**であることと、文字集合が投稿仕様
  §1.6 に適合すること(実装の `filename` 制約 `^[A-Za-z0-9_\-\.]+$`)の
  2点のみ。規則は命名側の裁量とする。設計14 サンプルは
  `id{ID:03d}_{a|b}{0|1|2}.mp3`(ID 基底・ゼロ埋め3桁。`a`/`b` は話者側、
  `0` = 本会話・`1`/`2` = 類似の組番号)を採ったが、これは投稿システム
  検証用データ生成での便宜であって制約ではない。プロトタイプの
  `s{n}_{a|b}{0-2}.mp3` 型はテーマ内スコープ名であり、同一ユニット内の
  複数テーマで衝突するため一意制約を満たさない
- 「音声ファイル」列は全行記入・ユニット内で重複なし(1発話 = 1音声)。
  `audio.zip` はフラット構成で、列の参照集合と完全一致すること
  (投稿仕様 §2.2)

## 5. 画像生成

本節も**メディア生成ツール**の要件である(入力は §4 冒頭と同じく、変換
ツールの出力エクセル1本で足りる)。

- **テーマ画像**: 1テーマ1枚(枚数はテーマ数次第)。プロトタイプの
  coverSvg(実行時生成)相当を静的化する — SVG のラスタライズまたは
  Gemini 画像生成
- **命名**: ユニット内で一意であればよい(設計12 指示書 §6 の「一意名
  なら任意」のとおり。文字集合は投稿仕様 §1.6)。設計14 サンプルは
  `theme{デッキ先頭ID:03d}.png`(例: ID 1〜5 のテーマ → `theme001.png`)
- **参照**: 規約 §6 の多対一参照 — 各デッキの先頭行(デッキ画像列)と
  配下カードの先頭行(カード画像列)が同一のテーマ画像を参照する。
  `image.zip` はフラット構成(投稿仕様 §2.3)
- スプラッシュ画像はユニットカバーへ(投稿データ外・UI 設定)

## 6. 出口検査

本節は**検査ツール**の要件である。検査は最終形(メディア3列を記入済みの
エクセル × `audio.zip` × `image.zip`)に対して行う。§1 の入力契約の検査
(カテゴリー単一値・ID のユニット内一意・§1.2 の記法違反)は変換ツールが
入口で行うものであり、本節とは別のゲートである。変換ツール・メディア生成
ツールが自分の出力に対して本節の一部を先行実施することは妨げないが、
**合否の正本は検査ツール**とする。

生成のたびに全件検査し、**全項目パスするまで納品しない**。検査は条文単位で
実装する(設計14 実績。`sample/gen_sample_s.py` の検査部が実装例)。

| # | 検査 | 根拠条文 |
|---|---|---|
| 1 | 行数 = カード数 × 6、話者の並びが6行周期どおり | 規約 §2 |
| 2 | 各行で英文スラッシュ数 = 語順訳の半角スペース数 | 規約 §5 |
| 3 | 全セルが正規化冪等(改行・タブ・連続空白・U+3000・前後空白なし) | 投稿仕様 §1.7.1 |
| 4 | 全セルが文字列型 | 投稿仕様 §1.7.1 |
| 5 | 拡張属性2列: 先頭行のみ記入・JSON パース可・ミニファイ一致・スキーマ適合 | 投稿仕様 §1.7.2 / 規約 §3 |
| 6 | シーン名がデッキ内で「セット1」〜「セットn」の連番 | 規約 §4 |
| 7 | 音声参照: 全行記入・ユニット内重複なし・文字集合適合・`audio.zip` と集合一致・フラット | 投稿仕様 §1.6 / §2.2 |
| 8 | 画像参照: デッキ/カード先頭行のみ記入・多対一参照が規約どおり・`image.zip` と整合 | 投稿仕様 §1.5 / §2.3 / 規約 §6 |
| 9 | 隣接デッキのチャプター名が重複しない(同名テーマの隣接によるデッキ融合の防止) | 投稿仕様 §1.3(境界判定) |
| 10 | ハングル混入なし(全セル) | 運用ルール |
| 11 | 編集ID 3列が全行空欄 | 本書 §3 |
| 12 | 音声実体の対応検証: 生成ログ(または対応表)と「音声ファイル」列の全件突合 | 本書 §4 |
| 13 | カード内に、規則 v1 の正規化後の内容が同一となるセンテンスが複数ない | 要求仕様 §3.4 / 本書 §8 |
| 14 | 同一デッキ内に、同じカードハッシュとなるカードが複数ない | 要求仕様 §3.4 / 本書 §8 |
| 15 | 全センテンスについて、規則 v1 の正規化結果が空でない | 要求仕様 §3.4 / 本書 §8 |
| 16 | 全セルに literal `_x000D_` / `_x000d_` および生 CR(U+000D)が残っていない | 本書 §1.2 |

- 検査12 の設計14 版は manifest.json との30件全件突合
  (`sample/audio_rename_map.tsv` が対応表)。全量変換では生成ログとの
  突合に置き換える
- 検査13〜15 は学習状態 API の識別体系の成立条件検査であり、依拠・規則の
  正本・実装上の注意は §8 で定める(「要求仕様」の指す文書も同節)

## 7. 投稿パラメータ

- メディアパックモード本線(投稿仕様 §3)。API パラメータとしては
  `audio_mode=pack` / `image_mode=pack`(名称の正本は API ドキュメント
  =実装サイド管轄。投稿仕様 §3 の呼称は日本語)
- 投稿は UC-20(新規)を想定。更新(UC-22)する場合は UC-23 の DL
  エクセルを起点とし、本ラインの再出力で上書きしない(編集ID の保全)

## 8. 成立条件の保証(ハッシュ規則 v1)

学習状態 API の識別体系
(`ユーザー別学習状態・プリファレンス保存取得_要求仕様.md`。以下
「要求仕様」)は、カードをカードハッシュ、センテンスをセンテンスハッシュで
識別する。要求仕様 §3.4 は、この識別体系の成立条件の保証を教材データを
作成する側(本ラインを含む教材作成ツール)に課しており、教材サーバーに
よる登録時の検査は要求されていない。本ラインは次のとおりこの責務を負う。
成立条件の検査(出口検査13〜15)は検査ツールが実施する。

- **成立条件の検査**: 要求仕様 §3.4 の成立条件のうち、条件1(カード内に
  正規化後の内容が同一となるセンテンスが複数存在しない)・条件2(同一
  デッキ内に同じカードハッシュとなるカードが複数存在しない)・条件3
  (センテンスの正規化結果が空でない)は、出口検査 13〜15(§6)で全件
  検査する。違反は変換エラーとして停止し、元データ側の修正で解消する
  (黙って補正しない)。条件4
  (センテンスの順序が確定できる)は、出力形態(1データ行 = 1センテンス、
  規約 §2 の固定行順)が構造的に保証するため、検査を設けない
- **規則の正本**: 正規化は要求仕様 §3.2(8手順)、ハッシュ生成は
  要求仕様 §3.3(規則 `v1`)が正本であり、本書には転記しない。同節の
  「正規化」はハッシュ算出用の規則であって、本書 §3 の「正規化冪等」
  (投稿仕様 §1.7.1。セル値の器の規則)とは別物である。両者は適用対象も
  内容も異なる(例: 規則 v1 はスラッシュを空白化し英大文字を小文字化
  するが、セル値はどちらもしない)
- **参照実装**: `vibe/STATUS.md`(choi 配下)§3 の正準実装のうち
  `normalize` / `quote` / `sha256hex` / `sentenceHash` / `cardHash` は同一
  規則の実装であり、そのまま転用できる(テストベクター再現を検証済み)。
  `sentenceHash` / `cardHash` は `sha256hex` を呼ぶため、これを外した移植は
  成立しない。直列化を
  言語の標準関数(`JSON.stringify` 等)へ委ねると、制御文字の短縮
  エスケープ(`\b` 等)が規則の `\u00xx` 固定とずれるため、参照実装と
  同様に独自エスケープを用いること
- **テストベクター照合**: 実装は要求仕様 §3.3.1 の検証用テストベクター
  2件(センテンスハッシュ・カードハッシュ各1。本区画のサンプル教材
  `sample/sampleS_unit.xlsx` の実データ由来)との照合に合格すること。
  ただしテストベクターの通過は規則全体の一致を保証しない(ベクターが
  踏まない分岐がある)ため、規則との差分検査の省略根拠にしない
- **ハッシュは納品物に含めない**: ハッシュ算出は出口検査のための内部
  処理である。投稿データにハッシュの列は存在しない。学習アプリが教材
  内容から同一規則で自ら算出する(要求仕様
  §3.6)ため、ハッシュ一覧(マニフェスト)を納品しても照合の受け手が
  存在しない。生成ログとして残すかは実装裁量とし、本書は要求しない
