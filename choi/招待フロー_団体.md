## 招待状態の遷移

```mermaid
stateDiagram-v2
    [*] --> 送信済: 団体管理者が招待を送信 (create)
    送信済 --> 承諾済: 被招待者が承諾 (accept)
    送信済 --> 辞退: 被招待者が辞退 (decline)
    送信済 --> 期限切れ: 有効期限超過 / 管理者が取消 (cancel)
    期限切れ --> 送信済: 管理者が再招待 (resend)
    辞退 --> 送信済: 管理者が再招待 (resend)
    承諾済 --> [*]: 会員として正式所属
```

> 招待 API にレコード削除(delete)は無いため、辞退・期限切れからの「レコード
> 削除」遷移は持たない。取消(cancel)は送信済 → 期限切れ の状態変更であり、
> レコードは残る。辞退・期限切れはいずれも再招待(resend)で送信済に戻せる。

## 招待状態の表示と操作(A-M4 発行済み招待一覧 / UC-52)

会員一覧(A-M1)には、承諾済みで団体に所属している会員のみを表示する。
発行済みの招待(送信済・期限切れ・辞退、および承諾済の履歴)は、A-M1 から
[招待の一覧]で遷移する発行済み招待一覧(A-M4)で管理する。招待は会員とは
別のライフサイクルを持つため、両者を画面で分離する。

A-M4 のステータス表示と操作(団体招待 API に対応):

| status | A-M4 での表示 | 可能な操作(対応API) |
|---|---|---|
| sent(送信済) | 「招待中」バッジ | 取消(`cancel`) |
| expired(期限切れ) | 「期限切れ」バッジ | 再招待(`resend`) |
| declined(辞退) | 「辞退」バッジ | 再招待(`resend`) |
| accepted(承諾済) | 「承諾済み」バッジ(履歴) | なし(会員として A-M1 に存在) |

- レコードの物理削除は無い(招待 API に delete が無いため)。`cancel` は
  送信済 → 期限切れ に状態を変えるのみで、レコードは残る
- 送信済(sent)の再送信は無い。`resend` の対象は期限切れ / 辞退のみ

## 重要な設計ポイント

1. **アカウント既存/未取得の判定はシステム側で行わない（アカウント軸）**
   - 被招待者自身が「お持ちの方はログイン / 未取得の方は新規作成」を選択する
   - これにより、アカウントの有無を判定して導線を出し分ける中間判定画面が不要
   - ここで省くのは**アカウント有無の判定**のみ。所属(1会員1団体)の照合とは別軸であり、設計ポイント2 の発行時チェックを妨げない

2. **1会員1団体制約（メンバーシップ軸）**
   - 招待時のバリデーションと、被招待者の承諾時の二段階でチェック
   - 招待時: 入力された会員ID／メールが既存アカウントに解決でき、別団体所属が判明したら招待送信をブロック(**会員ID指名・メール・CSV いずれも照合する**。未登録メールは所属が無いので通す)
   - 承諾時: 招待発行後の所属変化や、未登録メールが後でアカウント作成＋別団体加入したケースに備え、承諾時にも再チェック(`POST /accept` の `ALREADY_JOINED`)

3. **CSV一括 = 招待メールの一括送信**
   - CSV の1行ごとに独立した招待レコード・トークンを発行
   - 各行について個別にメール送信を行う
   - 行単位でバリデーションを実施

4. **二重 pending の禁止（発行時ブロック）**
   - 同一メールアドレス(解決できる場合)×同一団体に、**有効(`sent`)な招待が既にある場合、新規発行を弾く**。重複みなしは `sent` のみ(`expired` / `declined` は新規発行可)
   - エラー文言の趣旨: 「このメールアドレスには既に有効な招待があります。A-M4 で取消のうえ再発行、または期限切れ・辞退分を再招待してください」
   - 「届かない/紛失したのでもう一度送りたい」は、新オペレーションを設けず**既存導線で対応**する: A-M4 で当該 `sent` を取消(`cancel` → `expired`)してから新規発行、または `expired` / `declined` からの再招待(`resend`)。状態 enum・状態遷移・操作は現状維持(`lost` 等の新状態は作らない)

5. **団体所属 = 全アセット管理下の明示**
   - 団体に所属すると、被招待者のすべてのコンテンツ資産(所属前に作成したユニットを含む)が団体の管理下に置かれる
   - 承諾前のランディング(IV-1)でこれを明示する。外部公開ロックが有効(≠ off)な団体では、退出時のコース非帰属ユニットの管理者への移譲(UC-05)も併せて明示する(ワイヤーフレーム修正仕様 §8.6)
   - 原則の単一情報源はユースケース仕様書「システム前提 / 会員と団体の関係」

## 設計判断が必要な事項

1. **招待トークンの仕様**: UUIDv4 / 有効期限付きJWT / ワンタイムトークン 等
2. **期限切れの再招待**: 同じトークンを再送するか、新規トークンを発行して既存レコードを差し替えるか
3. **辞退の取り扱い**: 辞退レコードを一定期間保持するか、即時削除するか。同一メールで再招待を許すか
4. **CSV 一括招待の失敗処理**: 100 件中 3 件失敗した場合、97 件は送信するか、全体をロールバックするか
5. **既存会員ID指名招待時**: 招待メールは送らずに対象会員の「招待通知一覧」的な画面で通知するか、それともメールは送るか
6. **アカウント作成後の招待承諾への復帰**: アカウント作成完了後に招待承諾画面に戻る導線の具体設計(トークンの引き回し方、セッション/クエリパラメータ等)
7. **被招待者が辞退後、同じ団体から再招待された時の扱い**: 拒絶するか、再度案内するか

## 本フェーズ対象外 / 将来拡張

- 招待リンクのセキュリティ強化(デバイス検証、IPフィルタリング等)
- 招待履歴の監査ログ
- 招待数の上限管理(団体の契約プランに応じて)
