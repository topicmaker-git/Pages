# AIProxy 別紙2　成功条件テストの書き方（案）

この別紙は、生成AIの応答が期待どおりかを検査する成功条件テストについて、定義スタッフの書き方、保存される形、評価と記録の方法を、案として示す。用語とユースケースは `AIProxy_requirements.md` に従う。

## 1. 2種類のテスト

| 種類 | 何を検査するか | 誰が定めるか |
|---|---|---|
| 自動で決まるテスト | 応答が、応答形式の求める形になっているか | 応答形式から自動で決まる |
| 値の条件 | 応答の中の値が、指定の条件を満たすか | 定義スタッフが書く |

自動で決まるテストは、応答形式によって次のようになる。

| 応答形式 | 自動で決まるテスト |
|---|---|
| JSON（応答スキーマあり） | スキーマ適合。応答が、応答スキーマの定めるキーと型に合っているか |
| JSON（応答スキーマなし） | 応答が、JSONとして読めるか |
| 自由文 | なし |

応答スキーマは生成AIにも渡すが、出力が途中で切れた場合などに構造が壊れることがあるので、検査は省かない。

応答スキーマを使わないことは、定義スタッフが応答形式として明示して選ぶ。プロバイダやモデルが応答スキーマの指定に対応していない場合や、キーが実行ごとに変わる応答のように固定の応答スキーマで書けない場合に選ぶ。この場合、クライアントアプリに保証されるのは、応答がJSONとして読めることまでである。

成功条件テストは、検査の規則を機械的に当てるものである。生成AIに合否を判定させることはしない。

## 2. 応答スキーマの定め方

応答形式が「JSON（応答スキーマあり）」の場合、応答スキーマは、試行の応答から起こす。

1. 定義スタッフが試行する。
2. システムが、応答を読み、キーと型の一覧を起こして表示する。
3. 定義スタッフが、一覧を確認し、応答スキーマとする。

応答スキーマをまだ定めていない試行では、システムは、JSONで応答することだけを指定して生成AIを呼び出す。この試行の試行ログでは、応答スキーマの写しは空になる。応答スキーマを定めた後の試行では、応答スキーマも生成AIに渡す。

応答形式と応答スキーマは、入出力の層に属する。入出力バージョンが未確定の間は、変えて保存できる。入出力バージョンが確定した後は、その入出力バージョンのもとで同一でなければならない。応答スキーマを定める前の内容も保存できるが、有効にするには、応答スキーマが定まっている必要がある。

## 3. 値の条件の書き方

### 3.1 1件のテストが持つ項目

| 項目 | 内容 |
|---|---|
| 名前 | テストの名前。実行ログがこの名前で結果を記録する。1つのAIクエリの中で重複させない。 |
| 対象 | 応答の中の位置。 |
| 条件の種類 | 決まった種類の中から1つ。 |
| 比較相手 | 固定の値、またはテンプレート変数の参照。「空でない」のように、比較相手を持たない条件もある。 |

### 3.2 対象の書き方

| 書き方 | 指すもの |
|---|---|
| `questions` | 最上位のキー `questions` の値 |
| `questions[*].answer` | 配列 `questions` のすべての要素の、キー `answer` の値 |
| （応答全体） | 自由文の応答の全体 |

`[*]` を含む対象では、すべての要素が条件を満たすときに合格とする。1つでも外れれば不合格である。

### 3.3 条件の種類

| 条件の種類 | 対象の型 | 比較相手 | 変数の参照 |
|---|---|---|---|
| 値が等しい | 文字列、数値、真偽 | 値 | できる |
| 列挙のいずれか | 文字列、数値 | 値のリスト | できない |
| 数値の範囲 | 数値 | 下限と上限 | できない |
| 文字数の範囲 | 文字列 | 下限と上限 | できない |
| 正規表現に一致 | 文字列 | 正規表現 | できない |
| 指定の文字列を含む | 文字列 | 文字列 | できない |
| 指定の文字列を含まない | 文字列 | 文字列 | できない |
| 空でない | 文字列、配列 | なし | — |
| 要素数が等しい | 配列 | 整数 | できる |
| 要素数の範囲 | 配列 | 下限と上限 | できない |

### 3.4 比較相手

比較相手は、次のどちらかである。

- **固定の値**：定義のときに決めた値。
- **テンプレート変数の参照**：その実行でクライアントアプリが送った変数値。実行ごとに期待値が変わる。

変数を参照できるのは、最初の実装では「値が等しい」と「要素数が等しい」の2種類とする。「5問を求めたのに4問しか返ってこない」という失敗は、応答スキーマでも、固定の値の条件でも検出できない。変数の参照によって検出できる。

条件の種類と、変数を参照できる種類は、後から増やせる。成功条件テストは改訂ごとに保存されて変更されないので、種類を増やしても既存の改訂には影響しない。

## 4. 例

### 4.1 AIクエリ

問題を作るAIクエリを例にする。テンプレート変数に「問題数」（整数、1〜10）がある。応答は次の形である。

```json
{
  "questions": [
    {
      "text": "...",
      "choices": ["...", "...", "...", "..."],
      "answer": 2
    }
  ]
}
```

### 4.2 成功条件テストのリスト

| 名前 | 対象 | 条件の種類 | 比較相手 |
|---|---|---|---|
| 問題数が指定どおり | `questions` | 要素数が等しい | 変数「問題数」 |
| 選択肢は4つ | `questions[*].choices` | 要素数が等しい | 4 |
| 正解番号が範囲内 | `questions[*].answer` | 数値の範囲 | 1〜4 |
| 問題文が空でない | `questions[*].text` | 文字数の範囲 | 1〜200 |

### 4.3 保存される形

AIクエリは、成功条件テストをJSONのリストとして持つ。キーの名前は例であり、実装設計で定める。

変数を参照するテスト：

```json
{
  "name": "問題数が指定どおり",
  "target": "questions",
  "condition": "length_equals",
  "expected": { "var": "問題数" }
}
```

固定の値と比べるテスト：

```json
{
  "name": "選択肢は4つ",
  "target": "questions[*].choices",
  "condition": "length_equals",
  "expected": { "value": 4 }
}
```

比較相手を持つ条件では、比較相手は `{ "value": … }` か `{ "var": … }` のどちらかの形を取る。範囲の条件では、下限と上限のそれぞれがこの形を取る。

## 5. 定義スタッフの書き方

### 5.1 画面で書く

1. 試行すると、応答がキーの一覧として表示される。
2. 条件を付けたいキーを選ぶ。対象の位置は、選ぶだけで決まる。
3. そのキーの型に合う条件の種類が、選択肢として出る。
4. 比較相手に、固定の値を入力するか、テンプレート変数を選ぶ。
5. 名前を付ける。
6. その場で、表示中の応答と、過去の試行の応答に当てて、合否を見る。

### 5.2 JSONを貼り付ける

成功条件テストの実体はJSONのリストなので、JSONを貼り付けて定めることもできる。定義スタッフは、手元の生成AIに応答の例を見せてテストのリストを書かせ、貼り付けることを想定する。画面で1件ずつ足した場合と、結果は同じである。

## 6. 保存時の検査

AIクエリを保存するとき、システムは成功条件テストについて次を検査する。合わない場合は、保存を拒否する。

- 名前が重複していない。
- 条件の種類が、決まった種類のいずれかである。
- 対象が、応答スキーマに存在する位置である。応答形式が自由文の場合は、対象が応答全体であることを検査する。応答形式が「JSON（応答スキーマなし）」の場合と、応答スキーマをまだ定めていない場合は、この検査を行わない。実行のときに対象が応答に存在しなければ、不合格になる。
- 条件の種類が、対象の型に合っている。
- 参照している変数が、そのAIクエリのテンプレート変数に存在する。
- 参照している変数の型が、条件の種類に合っている。「要素数が等しい」の比較相手なら整数である。

## 7. 実行時の評価

変数値として「問題数：5」が送られた実行で、「問題数が指定どおり」を評価する手順は次のとおりである。

1. 対象をたどり、応答の `questions` を取り出す。
2. 比較相手の変数参照を、この実行の変数値で解決する。5になる。
3. 配列の要素数と5を比べる。

- 対象が応答に存在しない場合、または型が合わない場合は、不合格とする。エラーにはしない。
- すべてのテストを評価する。1つが不合格でも、残りの評価を続ける。
- 全体の合否は、すべてのテストが合格のときに合格とする。

## 8. テスト結果の記録

実行ログには、テストごとに結果を記録する。自動で決まるテストも、1件のテストとして記録する。

| 項目 | 内容 |
|---|---|
| テスト名 | テストの名前。 |
| 合否 | 合格または不合格。 |
| 期待値 | 比較相手を解決した値。変数の参照なら、その実行での変数値。 |
| 実際の値 | 応答から取り出して比べた値。要素数の条件なら、要素数。 |
| 外れた要素の位置 | `[*]` を含む対象で、最初に条件を外れた要素が、配列の何番目か。 |

- `[*]` を含む対象では、最初に条件を外れた要素について、その位置を「外れた要素の位置」に、その値を「実際の値」に記録する。「3番目の問題の選択肢が3つ」と分かる。
- 期待値、実際の値、外れた要素の位置は、不合格のときに記録する。
- 実際の値が長い文字列になる条件（正規表現、含む、含まない）では、値は記録しない。値そのものは、実行ログの応答に残っている。

変数を参照するテストは、期待値が実行ごとに変わる。期待値と実際の値を残すことで、不合格の原因を後から調べられる。

試行ログには、テスト結果を記録しない。成功条件テストは応答を見た後に書き直すので、試行の応答には、その都度当て直す。

## 9. 自由文の応答

応答形式が自由文のAIクエリでは、自動で決まるテストはない。値の条件の対象は、応答全体の1つだけになる。使える条件の種類は、文字数の範囲、正規表現に一致、指定の文字列を含む、指定の文字列を含まない、空でない、である。
