# AIProxy 要求概要とユースケース

AIProxy は、Webアプリに生成AIを使った機能を組み込むための共通基盤の開発コードネームである。この文書は、実装担当者に向けて、AIProxy の目的、用語、アクター、ユースケース、要求をまとめる。関連する文書は次のとおりである。

| ファイル | 内容 |
|---|---|
| `AIProxy_classes.mmd` | クラス図 |
| `AIProxy_appendix1_model_parameters.md` | 別紙1　プロバイダ、モデル、パラメータの入力 |
| `AIProxy_appendix2_success_tests.md` | 別紙2　成功条件テストの書き方（案） |

## 1. 目的と前提

### 1.1 AIProxy が担うこと

- ログイン中のエンドユーザーからのリクエストだけを受け付ける。
- サーバーに登録された定義（AIクエリ）に従ってプロンプトを組み立て、生成AIを呼び出す。
- 生成AIの応答を検査し、合否とともにクライアントアプリへ返す。
- すべての実行を記録し、課金の根拠と原価の把握に使える形で残す。

### 1.2 前提

この機能をどのような商品として提供するか、つまりAI機能利用者ロール（利用権限と制限）の構成と課金の方法は定まっていない。AIProxy は、それらが後から決まっても記録の形を変えずに対応できる基盤として、先行して実装する。

## 2. 基本方針

### 2.1 プロンプトはサーバーに置く

クライアントアプリは、プロンプトの文面も生成AIのパラメータも送らない。送るのは、AIクエリの識別子、入出力バージョン、テンプレート変数に入れる値の3つである。サーバーは、登録済みのテンプレートに変数値を展開してプロンプトを完成させる。

### 2.2 事実の記録と方針の判断を分ける

- 実行ログは、起きた事実だけを記録する。誰が、いつ、どの定義で、どんな変数値で実行し、結果がどうで、何トークン消費したか。金額や、課金の対象かどうかは記録しない。料金は、実行ログから後で計算する。
- 利用できるかどうかの判断は、1か所の判定に集める。AI機能利用者ロールの構成と、ロールごとの利用枠が決まったら、その判定の中身として実装する。

### 2.3 定義はデータである

AIクエリはソースコードではなくデータであり、企画・運用の担当者がスタッフ用Web UIで登録する。リポジトリの変更やデプロイを必要としない。

### 2.4 ステージ

開発、プレビュー、本番の3つのステージがあり、データベースはステージごとに独立している。AIクエリも、実行ログも、ステージごとに存在する。クライアントアプリのコードはステージの間を移動するので、コードに書かれる値（識別子と入出力バージョン）は、全ステージで同じ意味を持たなければならない。

## 3. 用語

| 用語 | 意味 |
|---|---|
| AIクエリ | 生成AIへの1種類の問い合わせの定義。識別子と改訂番号で1件が決まる。 |
| 識別子 | AIクエリの名前。定義スタッフが付ける文字列で、全ステージで共通。付けた後は変更せず、使わなくなっても別の用途に再利用しない。形式は、Linuxのファイル名に準じる。 |
| 入出力バージョン | クライアントアプリから見た入口と出口の形を定める番号。テンプレート変数のセット、応答形式、応答スキーマを固定する。定義スタッフが採番し、全ステージで共通。WebAPIでいうAPIバージョンに当たる。 |
| 改訂番号 | 識別子ごとの通し番号。入出力バージョンをまたいで1本の連番になる。ステージごとに採番する。 |
| 派生元の改訂番号 | そのAIクエリを作るときに、読み込んで出発点にした改訂の番号。何も読み込まずに作ったものでは空。 |
| テンプレート | プロンプトの文面。テンプレート変数の差し込み位置を含む。 |
| テンプレート変数 | テンプレートに差し込む値の定義。名前、型、制約を持つ。 |
| 変数値 | 実行のたびにクライアントアプリが送る、テンプレート変数に入れる値。 |
| 応答形式 | 生成AIに求める応答の形式。自由文またはJSON。 |
| 応答スキーマ | 応答形式がJSONのときの、キーと型の定義。 |
| プロバイダ | 生成AIを提供する事業者のサービス。AIProxy が呼び出す相手。 |
| モデル | プロバイダが提供する生成AIの種類。モデル名で指定する。 |
| パラメータ | 生成AIの呼び出しに付ける設定値のセット。プロバイダとモデルの組み合わせごとに指定できる項目が違う。JSON形式で持つ。 |
| 成功条件テスト | 応答が期待どおりかを検査する条件。名前、対象、条件の種類、比較相手を持つ。 |
| 有効 | エンドユーザーの実行に使われる状態。識別子と入出力バージョンの組ごとに、有効なAIクエリは最大1件。 |
| 実行 | エンドユーザーの操作を起点とする、1回のリクエストの処理。 |
| 試行 | 定義スタッフが、保存前の入力内容で生成AIを呼び出して応答を確かめること。 |
| 実行ログ | 実行ごとの記録。 |
| 試行ログ | 試行ごとの記録。 |
| ステージ | 開発、プレビュー、本番のいずれかの設置環境。 |
| AI機能利用者ロール | エンドユーザーがAI機能を使ううえでの、利用権限と制限のまとまり。Webアプリ本体が定義し、エンドユーザーに割り当てる。定義スタッフや運用・課金担当が持つスタッフとしての権限とは別のものである。 |
| 利用枠 | 特定のAI機能利用者ロールに定義される、利用の量の上限。 |

### 定義とソースコードの対応

AIクエリは、データとして、ステージごとのデータベースに登録される。一方、AIクエリを呼び出すクライアントアプリはソースコードであり、バージョン管理され、開発、プレビュー、本番の各ステージへデプロイされる。同じソースコードが、どのステージでも、そのステージのデータベースにある対応する定義に行き着かなければならない。識別子と入出力バージョンの決まりは、この対応を保つためにある。

**識別子を自動採番にしない理由**

データベースの連番は、ステージごとに別々に進む。開発で3番になった定義が、本番でも3番になる保証はない。ソースコードに書いた値が全ステージで同じ定義を指すように、識別子は定義スタッフが付ける文字列とし、全ステージで同じものを使う。

**入出力バージョンが必要な理由**

ソースコードは、送る変数の名前と型、受け取る応答の形を前提にして書かれる。定義の側でこれらが変わると、ソースコードは動かなくなる。プロンプトの文面、プロバイダ、モデル、パラメータの変更は、ソースコードに影響しない。そこで、ソースコードが前提にしている部分にだけ番号を付け、ソースコードはその番号を指定して呼び出す。この番号が入出力バージョンである。文面の改良は、入出力バージョンを変えずに行えるので、ソースコードの変更もデプロイも伴わない。

**同じ識別子に複数の入出力バージョンが併存する理由**

変数や応答の形を変えるときは、定義とソースコードの両方を変えることになるが、両者は同時には切り替わらない。定義は各ステージの画面で登録され、ソースコードはデプロイで届く。デプロイの後も、利用者の手元には改修前のクライアントアプリがしばらく残る。そこで、新しい入出力バージョンを先に登録しておき、改修前のクライアントアプリが使われなくなってから、古い入出力バージョンを無効にする。その間、同じ識別子のもとに新旧の入出力バージョンが併存する。

**属性の3つの層**

以上から、AIクエリの属性は、ソースコードとの関係によって3つの層に分かれる。

| 層 | 属性 | ソースコードとの関係 | 同一でなければならない範囲 |
|---|---|---|---|
| 名前 | 識別子 | ソースコードに書かれる | 全ステージ |
| 入出力 | 入出力バージョン、テンプレート変数、応答形式、応答スキーマ | 入出力バージョンはソースコードに書かれる。残りはソースコードが前提にする | 識別子と入出力バージョンが同じもの全部。全ステージ |
| 中身 | 改訂番号、派生元の改訂番号、テンプレート、プロバイダ、モデル、パラメータ、成功条件テスト | ソースコードからは見えない | 1件ごと。ステージごと |

### 入出力バージョンと改訂番号の関係

同じ識別子のもとに、複数の入出力バージョンが併存できる。改訂番号は識別子ごとの通し番号なので、入出力バージョンの間で入り混じる。どの改訂を元にして作られたかは、番号の並びからは読み取れないので、AIクエリごとに派生元の改訂番号を記録する。

識別子 `quiz-gen` の、あるステージでの例：

| 改訂番号 | 入出力バージョン | 派生元 | 有効 |
|---|---|---|---|
| 1 | 1 | | |
| 2 | 1 | 1 | |
| 3 | 2 | 2 | ✓ |
| 4 | 1 | 2 | ✓ |
| 5 | 2 | 3 | |

この例の経緯は次のとおりである。

1. 改訂1を作り、文面を直して改訂2とした。
2. 変数を変える必要が生じ、改訂2を元に、入出力バージョン2の改訂3を作った。
3. その後、入出力バージョン1を使い続けるクライアントアプリのために、改訂2を元に文面を直して改訂4とした。
4. 改訂3を元に、入出力バージョン2の文面を直した改訂5を保存した。まだ有効にしていない。

入出力バージョン1を指定するクライアントアプリには改訂4が、入出力バージョン2を指定するクライアントアプリには改訂3が使われる。

## 4. アクター

| アクター | 説明 |
|---|---|
| エンドユーザー | Webアプリにログインして、AI機能を使う人。 |
| 定義スタッフ | AIクエリを定義する企画・運用の担当者。スタッフ用Web UIだけで作業する。 |
| 運用・課金担当 | 実行ログと試行ログを調べ、集計する人。 |

クライアントアプリは、エンドユーザーの操作を取り次ぐものであり、アクターとしない。その状態と責務は、ユースケースの事前条件、事後条件、責務として記述する。生成AIのプロバイダは、AIProxy から呼び出される外部システムである。

## 5. ユースケース

### U1　AIクエリを実行する

**アクター**：エンドユーザー

**事前条件**
- クライアントアプリは、識別子、入出力バージョン、そのテンプレート変数の名前と型、応答スキーマに合わせて実装されている。
- 実行先のステージに、その識別子と入出力バージョンを持つ有効なAIクエリがある。
- エンドユーザーはログインしている。

**基本の流れ**
1. エンドユーザーが、クライアントアプリ上でAI機能を使う操作をする。
2. クライアントアプリが、識別子、入出力バージョン、変数値を送信する。
3. システムが、ログイン状態と利用可否を判定する。
4. システムが、識別子と入出力バージョンから有効なAIクエリを選ぶ。
5. システムが、変数値を検証し、テンプレートに展開する。
6. システムが、生成AIにプロンプトを送り、応答を受け取る。
7. システムが、応答を成功条件テストにかける。
8. システムが、実行を実行ログに記録し、応答、テストの合否、実行IDをクライアントアプリに返す。

**別の流れ**

| 起きる箇所 | 状況 | クライアントアプリに返すもの | 実行ログの結果 |
|---|---|---|---|
| 3 | ログインしていない、または利用不可と判定された | 拒否理由 | 拒否 |
| 3 | システム保護の上限を超えた | 拒否理由 | 拒否 |
| 4 | 識別子または入出力バージョンが登録されていない | 拒否理由 | 拒否 |
| 4 | 登録はあるが、有効なものがない | 拒否理由 | 拒否 |
| 5 | 変数値が定義に合わない | 拒否理由 | 拒否 |
| 6 | 生成AIが失敗した、または時間切れになった | エラー | 失敗 |
| 7 | 成功条件テストに不合格 | 応答、合否、実行ID（基本の流れと同じ） | 応答あり |

成功条件テストに不合格の応答も、そのまま返す。システムは自動で再試行しない。

**事後条件**
- 実行は、応答あり、拒否、失敗のどの結果でも、実行ログに記録されている。
- クライアントアプリは、応答・合否・実行ID、または拒否理由かエラーを受け取っている。

**クライアントアプリの責務**
- 変数値を組み立てて送る。
- 不合格の応答をエンドユーザーにどう見せるかを決める。
- 拒否理由に応じた案内を表示する。
- 再試行するかどうかを決める。再試行は、別の実行として記録される。

### S1　新しいAIクエリを作る

**アクター**：定義スタッフ

1. 定義スタッフが、スタッフ用Web UIで識別子を決める。
2. テンプレート変数の名前・型・制約と、応答形式を定める。
3. 使用する生成AIのプロバイダとモデルを決める。モデルは、過去に指定されたものの選択肢から選ぶか、モデル名を直接入力する。
4. そのプロバイダとモデルに合わせたパラメータを、JSON形式で入力する。
5. テンプレートを書き、S2（試行する）を行う。
6. S3（保存する）を行い、最初の入出力バージョンを採番する。

プロバイダ、モデル、パラメータの入力の方法は、別紙1に示す。

### S2　試行する

**アクター**：定義スタッフ

1. 定義スタッフが、識別子を選ぶ。保存済みのAIクエリ、または過去の試行ログを読み込んで出発点にしてもよい。
2. テンプレート、プロバイダ、モデル、パラメータ、変数値を入力して試行する。
3. システムが、生成AIを呼び出し、応答を表示し、試行を試行ログに記録する。
4. 応答形式がJSONの場合、定義スタッフは、システムが応答から起こしたキーと型の一覧を確認し、応答スキーマとする。
5. 定義スタッフが、成功条件テストを書き、表示中の応答や過去の試行の応答に当てて合否を確かめる。
6. 満足できるまで、2から5を繰り返す。

応答スキーマと成功条件テストの書き方は、別紙2に示す。

**事後条件**
- 試行の内容と応答は、試行ログに残っている。
- AIクエリは、まだ作られていない。

### S3　保存する

**アクター**：定義スタッフ

1. 定義スタッフが、入出力バージョンを指定して、試行した内容を保存する。入出力バージョンは、既存のものを選ぶか、新しく採番する。
2. システムが、同じ識別子と入出力バージョンを持つ既存のAIクエリと、テンプレート変数、応答形式、応答スキーマが一致することを検査する。一致しなければ保存を拒否し、違いを表示する。
3. システムが、テンプレートが使っている変数が、定義されたテンプレート変数に含まれることを検査する。
4. システムが、新しい改訂番号を付けて、AIクエリを1件作る。試行の出発点として保存済みのAIクエリを読み込んでいた場合は、その改訂番号を派生元として記録する。

**事後条件**
- 新しいAIクエリが、有効でない状態で存在する。
- 既存のAIクエリは、変わっていない。

作業を中断するときも、保存を使う。有効にされないままのAIクエリが残ることは許容する。

### S4　有効にする・無効にする

**アクター**：定義スタッフ

1. 定義スタッフが、保存済みのAIクエリを1件選び、有効にする。
2. システムが、同じ識別子と入出力バージョンを持つ、それまで有効だった1件を無効にする。

ある入出力バージョンの提供をやめるときは、有効な1件を無効にする。その入出力バージョンへのリクエストは、以後、拒否される。

### S5　入出力バージョンを追加する

**アクター**：定義スタッフ

**事前条件**
- 変数または応答の形を変える必要があり、クライアントアプリの改修が予定されている。

1. 定義スタッフが、既存の識別子に対して新しい入出力バージョンを採番する。
2. 新しいテンプレート変数のセットと応答形式を定める。
3. S2、S3、S4を行う。

**事後条件**
- 新旧の入出力バージョンが併存している。改修前のクライアントアプリは旧バージョンを、改修後のクライアントアプリは新バージョンを指定する。

### S6　定義を別のステージへ移す

**アクター**：定義スタッフ

1. 定義スタッフが、移す元のステージでAIクエリを選び、ファイルに書き出す。
2. 移す先のステージで、そのファイルを取り込む。
3. システムが、識別子と入出力バージョンが同じものが移す先にあるかを調べ、あれば、テンプレート変数、応答形式、応答スキーマを照合する。内容が違う場合は取り込みを拒否し、違いを表示する。
4. システムが、移す先のステージの新しい改訂番号を付けて保存する。有効にはしない。改訂番号はステージごとの採番なので、移す元での派生元は引き継がず、空とする。

ステージごとに、定義を手で入力して登録することもできる。2つ目以降のステージでは、取り込みを標準の手順とする。

### S7　削除する

**アクター**：定義スタッフ

定義スタッフが、保存済みのAIクエリを削除する。削除できるのは、実行ログから一度も参照されていないものに限る。

### O1　ログを調べる

**アクター**：運用・課金担当

運用・課金担当が、期間、ユーザー、識別子、入出力バージョン、結果、合否で実行ログを絞り込み、個々の実行の内容を見る。実行IDから1件を引くこともできる。実行ログの1件から、その実行に使われたAIクエリの内容を引ける。試行ログも同様に調べられる。

### O2　利用を集計する

**アクター**：運用・課金担当

運用・課金担当が、ユーザー別、識別子別、入出力バージョン別に、実行回数、トークン数、合格率、拒否の件数を出す。

- 課金の根拠は、実行ログから出す。
- 原価は、実行ログと試行ログのトークン数の合計から出す。
- 入出力バージョン別の利用数は、改修前のクライアントアプリがまだ使われているかを判断する材料になる。

## 6. 要求

### 6.1 識別子の形式

- 識別子の形式は、定義スタッフのチームが、運用しやすいように自由に決める。
- システムが課す形式上の制約は、Linuxのファイル名に準じる。
  - 大文字と小文字を区別する。
  - 文字列として完全に一致するものだけを、同じ識別子とみなす。正規化や空白の除去など、入力された文字列を書き換える処理は行わない。
  - 使えない文字は、`/` とNUL文字だけである。
- データベースの実装の都合で、長さに上限を設けてよい。
- 照合の実現方法は、実装設計で定める。データベースの文字列比較が標準で大文字と小文字を区別しない場合は、識別子について区別する設定にする。

### 6.2 AIクエリの不変性

- 保存されたAIクエリの内容は、変更できない。内容を変えるときは、新しい改訂番号で保存する。変えられるのは、有効かどうかだけである。
- 保存されたAIクエリは、有効でなくなった後も、削除されない限り、参照できる形でそのステージに残る。
- 実行ログから参照されているAIクエリは、削除できない。したがって、実行ログに記録された改訂番号からは、その実行に使われたテンプレート、プロバイダ、モデル、パラメータ、成功条件テストを必ず引ける。
- 識別子と入出力バージョンが同じAIクエリは、テンプレート変数、応答形式、応答スキーマが同一でなければならない。
- 識別子と入出力バージョンの組ごとに、有効なものは最大1件とする。
- 削除されたAIクエリの改訂番号は、再利用しない。
- 派生元の改訂番号は、経緯の記録である。派生元のAIクエリが削除された後も、番号はそのまま残す。

### 6.3 テンプレート変数と変数値の検証

**型と制約**

テンプレート変数の型は、JSONの型に揃える。変数値はクライアントアプリからJSONで届き、応答スキーマもJSONの型で書くので、定義スタッフが覚える語彙と、検査の仕組みが1つで済む。

| 型 | 制約 | テンプレートへの差し込み方 |
|---|---|---|
| 一行の文字列 | 最大文字数（必須）、最小文字数、列挙、正規表現 | そのまま差し込む。改行を含む値は拒否する |
| 複数行の文字列 | 最大文字数（必須）、最小文字数 | そのまま差し込む |
| 整数 | 最小、最大 | 数字の文字列にして差し込む |
| 数値 | 最小、最大 | 数字の文字列にして差し込む |
| 真偽 | なし | `true` または `false` として差し込む |
| 配列（要素は上のいずれかの型） | 要素数の最小と最大、要素ごとの制約 | JSONの配列として差し込む |

- 文字列を一行と複数行に分けるのは、自由文の入口を、必要な変数だけに絞るためである。
- 文字列の最大文字数は必須とする。入力トークン数の上限が、定義の時点で決まる。
- 選択肢が決まっている変数には、列挙を使う。定義にない値を拒否できる。

**含めないもの**

- 入れ子のオブジェクト。必要な場合は、変数を分ける。
- 任意の変数と既定値。すべてのテンプレート変数は必須とし、省略時の値はクライアントアプリが送る。
- テンプレートの中の条件分岐と繰り返し。差し込みは、単純な置換だけとする。式を評価する仕組みに変数値を通さない。

**変数値の検証**

- 変数値は、テンプレート変数の型と制約に照らして、サーバーで検証する。
- 定義にない変数が送られた場合、および変数が欠けている場合は、拒否する。
- 複数行の文字列は、利用者が任意の指示を書き込める入口になる。テンプレートの中では、指示の文面と区別できる位置に差し込む。

### 6.4 プロバイダ、モデル、パラメータ

- AIクエリは、生成AIの呼び出し先として、プロバイダとモデルを持ち、呼び出しの設定値としてパラメータを持つ。
- プロバイダは、そのステージに接続設定があるものから選ぶ。
- モデルは、過去に指定されたものの選択肢から選ぶか、モデル名を直接入力する。
- パラメータは、JSON形式で入力する。
- プロンプト、モデル名、応答スキーマなど、AIProxy が組み立てて送る項目は、パラメータでは指定できない。

入力の方法とシステムの検査は、別紙1 `AIProxy_appendix1_model_parameters.md` に示す。

### 6.5 応答の検査

- 成功条件テストは、検査の規則を機械的に当てるものである。生成AIに合否を判定させることはしない。
- 成功条件テストには、応答スキーマから自動で決まるスキーマ適合と、定義スタッフが書く値の条件の2種類がある。
- 値の条件は、名前、対象、条件の種類、比較相手の4項目で書く。コードは書かない。
- 比較相手には、固定の値のほかに、その実行で送られた変数値を指定できる。
- 応答スキーマは、試行の応答からシステムがキーと型の一覧を起こし、定義スタッフが確認して定める。
- 実行ログには、テストごとに、テスト名、合否、期待値、実際の値を記録する。全体の合否は、すべてのテストの合格で決まる。

書き方、保存される形、評価と記録の方法は、別紙2 `AIProxy_appendix2_success_tests.md` に案として示す。

### 6.6 実行ログ

- 実行ごとに1件を記録する。拒否と失敗も記録する。
- 記録した内容は変更しない。
- 記録する項目：実行ID、日時、ユーザー、実行時の文脈、AIクエリ識別子、AIクエリ入出力バージョン、AIクエリ改訂番号、変数値、結果（応答あり・拒否・失敗）、拒否理由、応答、テストごとの結果、入力トークン数、出力トークン数。
- AIクエリ識別子とAIクエリ入出力バージョンは、クライアントアプリが指定した値をそのまま記録する。登録されていない値への拒否も、これで記録できる。AIクエリ改訂番号は、使うAIクエリが決まった場合だけ記録する。
- 実行時の文脈は、その時点のエンドユーザーのAI機能利用者ロールなどの写しである。割り当てられたロールも、ロールの内容も、後から変わりうるので、実行時点の状態を残す。実行ログは写しを保存するだけで、その中身を解釈しない。
- 金額と、課金の対象かどうかは、記録しない。
- 変数値と応答には、個人情報が含まれうる。その前提で、保存と閲覧の方法を設計する。

### 6.7 試行ログ

- 試行ごとに1件を記録する。
- 試行は保存前の内容に対して行うので、試行ログは内容をAIクエリから引かず、テンプレート変数、応答形式、応答スキーマ、テンプレート、プロバイダ、モデル、パラメータの写しを自前で持つ。
- 入出力バージョンと改訂番号は保存のときに決まるので、試行ログは持たない。
- 保存済みのAIクエリを読み込んで出発点にした試行では、その改訂番号を「元にしたAIクエリ改訂番号」として記録する。AIクエリのどの段階で行われた試行かを、これでたどれる。何も読み込まずに始めた試行では空とする。
- 成功条件テストは応答を見た後に書き直されるので、合否は記録しない。記録するのは応答までである。
- 記録する項目：試行ID、日時、試行した定義スタッフ、AIクエリ識別子、元にしたAIクエリ改訂番号、上記の写し、変数値、結果（応答あり・失敗）、応答、入力トークン数、出力トークン数。

### 6.8 利用可否の判定

- 利用できるかどうかは、ユーザーの固定の属性ではなく、リクエストの時点での判定の結果である。
- 判定は1か所に集める。入力は、ユーザー、AIクエリ、実行時の文脈。出力は、可否と拒否理由。
- 最初の実装は、ログインしていれば可とする。
- 利用枠は、特定のAI機能利用者ロールに定義される。判定は、エンドユーザーのロールに定義された利用枠と、実行ログの集計を照らし合わせて、可否を決める。AIProxy は、集計の手段を提供する。
- 判定の中身と、実行時の文脈に入れる項目は、商品と課金の設計が決まってから定める。

### 6.9 拒否理由

拒否理由は、クライアントアプリが案内を出し分けられるように、種類を区別して返す。

商品と課金の設計によらず存在する種類は、次のとおりである。

- ログインしていない
- 識別子または入出力バージョンが登録されていない
- 登録はあるが、有効なAIクエリがない
- 変数値が定義に合わない
- システム保護の上限を超えた

利用不可と判定された場合の内訳（権限がない、利用枠を超えた、など）は、商品と課金の設計が決まってから定める。種類は、後から増やせる形にしておく。

### 6.10 システム保護

AI機能利用者ロールに定義される利用枠とは別に、システムを守るための上限を最初から設ける。この上限は、ロールによらず全ユーザーに適用する。

- ユーザーあたりの、単位時間の実行回数
- 同時に実行できる数
- 出力トークン数の上限

### 6.11 試行の権限

試行は、任意のプロンプトを生成AIに送れる入口である。定義スタッフの権限を持つユーザーに限定し、エンドユーザーの実行とは別の経路にする。

### 6.12 ステージ間の整合

- 識別子と入出力バージョンが同じAIクエリは、どのステージにあるものも、テンプレート変数、応答形式、応答スキーマが一致していなければならない。
- 一致を求める単位は、識別子と入出力バージョンの組である。あるステージにだけ存在する識別子や入出力バージョンがあってよい。開発のステージで作成中のものが、これに当たる。
- クライアントアプリのソースコードをあるステージにデプロイする時点で、そのソースコードが指定する識別子と入出力バージョンを持つ有効なAIクエリが、そのステージに存在していなければならない。
- スタッフ用Web UIは、識別子と入出力バージョンの組ごとに、テンプレート変数、応答形式、応答スキーマの内容から計算した短い符号を表示する。定義スタッフは、ステージの間でこの符号を見比べて、一致を確かめられる。
- 不一致が残った場合、U1で変数値の不正による拒否として現れる。拒否理由が実行ログに残るので、プレビューでの確認と O1 で検出できる。

## 7. 拡張可能性の受け入れ条件

次のどの方式が後から選ばれても、実行ログの項目を変えずに、利用可否の判定と料金計算の追加だけで実現できること。

- 実行回数に応じた課金
- トークン数に応じた従量課金
- 月額プランと月ごとの上限
- 前払いのクレジット
- 組織単位の請求
- AIクエリごとの単価
- 不合格または失敗の実行を課金しない扱い
- AI機能利用者ロールごとに、使えるAIクエリが違う構成
- AI機能利用者ロールごとに、利用枠が違う構成

## 8. 範囲外

- 料金の計算、請求、プランの管理
- AI機能利用者ロールの定義と、エンドユーザーへの割り当て（Webアプリ本体が持つ）
- スタッフとしての権限の定義と管理（Webアプリ本体が持つ）
- エンドユーザーに何を表示するか（クライアントアプリが決める）
- 利用可否の判定に、汎用のルール記述の仕組みを持たせること
- ログイン中のエンドユーザーの操作を起点としない実行（定時処理など）

| 項目 | 内容 |
|---|---|
| 利用可否の判定の中身 | AI機能利用者ロールと利用枠を、どう評価して可否を決めるか。 |

### 9.2 実装設計で定めること
